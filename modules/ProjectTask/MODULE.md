# ProjectTask runtime ownership

- The existing ProjectTask → Project percentage UI-type inheritance selects Core's optional header progress-bar template. Header inline saves update the existing progress, label and tooltip nodes; detail/edit values and workflow calculation stay numeric percentages.

- registerSummaryWidgets declares the default Checklist widget with the stable field name checklists and right-column sequence 5. Core_Install_Model::updateSummaryWidgets() owns normal install/update registration, preserving existing disabled block:// URLs and customer sequence. No migration or separate registration path is added. Core supplies value rendering and permissions, accepting both field names and legacy numeric ids; ProjectTask adds no separate summary controller or persistence path.

- `ProjectTask_Install_Model` registers the optional `checklists` UI-type-34 MEDIUMTEXT field in the base table `vtiger_projecttask`, after `description` in the ordinary Description block through its standard field configuration. It defines no Checklist block, block-conversion migration or content transfer from the custom-field table. The field contains one checklist as plain item text, one line per item. Core owns metadata, record/field permissions, the matching detail/edit widget, AJAX and normal-save reconciliation. ProjectTask has no separate checklist save path or module version. Completion never changes task status or `projecttaskprogress`.

- ProjectTask is a system entity module installed by `ProjectTask_Install_Model`, without a separate `$moduleVersion`. Its records use `vtiger_projecttask`, its custom-field table and `vtiger_crmentity`; ordinary entity persistence remains owned by Vtiger's record/module flow.
- `projecttaskprogress` is editable percentage UI type 9 with whole values 0–100, using `ProjectTask_Percentage_UIType` to inherit the existing Project integer-percentage contract. Normal requests accept any whole percentage rather than only ten-percent picklist steps and reject fractions. The install schema declares a nullable INT column through Core_DatabaseTable_Model. No percent-suffix parsing, edit-value conversion or progress picklist remains. ProjectTask_Field_Model inherits ordinary field behavior; its percentage UI inherits edit and nonzero display from Vtiger, retaining only Project_ProgressCalculator_Model whole-percentage validation and explicit zero display.
- `VTProjectProgressTask` is an immediate standard workflow task, registered by the module install model from `models/ProgressTask.php`. The default Calculate project progress workflow runs on every save without conditions; standard registration preserves existing workflow enablement, conditions and task settings. Administrators can disable the action or workflow. It never locks Project.progress or changes ProjectTask progress/status.
- The Progress task form starts with a closed native details disclosure for its brief calculation explanation, separated from settings by Bootstrap border-bottom and spacing utilities. Clicking the HTML-escaped summary reveals trusted module language copy with Markdown bold and blank lines rendered through Core_Utils_Helper::markdownToHtml(). Keep the plain-language explanation aligned with Project_Progress_Model, without formulas or an alert background.
- Each progress action setting has translated, HTML-escaped Bootstrap form-text directly below its label in the left column, linked from the native input/select with aria-describedby. Hint keys follow the existing label plus _HELP; keep all four locale keys aligned.
- `VTProjectProgressTask::getSettingFields()` is the single ordered definition of setting names, labels and control types. getFieldNames() derives serialized names from it; the form uses one shared row loop and retrieves status options once. Preserve the four persisted property names and their defaults when extending this configuration.
- `ProjectTask_Progress_Model` resolves persisted and VTEntityDelta previous project IDs so relation changes recalculate both projects, then delegates calculation/persistence to Project_Progress_Model. Workflow settings contain completed/excluded status values and positive hours/day and fallback hours (both default 8); Completed and Canceled are initial defaults, independent of chart closed-status configuration.
- `ProjectTask_Progress_Handler::handleEvent()` only delegates to `ProjectTask_Progress_Model::handleEvent()`. The model owns the complete delete-event flow, including legacy workflow bootstrap, module filtering, cache handling and static pendingDeletions snapshots shared across model instances. It captures matching active every-save/on-modify progress tasks before deletion and executes only those tasks afterwards with workflow history attribution. Unrelated actions never run on deletion. Normal workflow afterrestore registration covers restoration. Disabling the workflow/action prevents deletion recalculations as well. The module install/custom-link lifecycle registers/unregisters the handler without deleting workflow definitions.
- Validation: PHP lint, task/UI inheritance and serialization, changed locale keys and Smarty form rendering; verify save/move/delete/restore, disabled workflows/actions and no-op audit history in an authenticated CRM/database environment.
- `ProjectTask_Record_Model::save()` validates optional date-only `startdate`/`enddate` values before delegating to `Vtiger_Record_Model::save()`. At this boundary, submitted dates still use the current user's date format; unchanged stored values may be ISO. `Vtiger_Base_UIType::getRequestValue()` validates/trims but does not convert date fields. Convert validation copies through `DateTimeField::__convertToDBFormat()`, check real calendar dates and compare padded ISO copies. Do not overwrite model values: `CRMEntity` performs the actual storage conversion later. Empty/legacy zero dates represent missing boundaries, an end cannot precede a start, and equality is a one-day task. No time-zone conversion or timestamp-duration division belongs in this validation.
- `ProjectTask_SaveTask_Action` serves chart dragging and quick edit. It checks submitted field editability and inherits ordinary `Vtiger_Save_Action::saveRecord()` so mandatory-field checks, field/status record-action rules, history and normal save hooks are retained. Exceptions reach the central WebUI handler unchanged.
- `ProjectTask_QuickEditAjax_View` checks record type and both DetailView/EditView permissions before loading a record. A supplied parent project must match the task. `ProjectTask_GanttQuickEditRecordStructure_Model` includes project, milestone and both date fields independently of Quick Create defaults, omits hidden fields and receives Core field/status locks. `QuickEdit.tpl` presents noneditable values as escaped plain text without form controls.
- Project owns chart presentation, project-range warnings and persisted task dependencies. Task saves do not reschedule milestones, project boundaries or dependent tasks.
- `ProjectTask_Record_Model::getDateValidationError()` is shared by persistence and form validation. Known task boundaries must lie within the linked Project's inclusive `startdate`/`targetenddate` and on/before a dated milestone deadline; a milestone must belong to the task's project. Missing boundaries impose no date limit. Active related records are read independently of chart filters/field visibility, but errors never disclose their values. Dates use `Core_DateOnly_Helper` without mutating submitted values. Ordinary/chart saves enforce these rules, including relation changes, without advisory locks or automatic rescheduling. Existing outside-range tasks remain viewable but require correction before saving.
- `ProjectTask_ValidateDates_Action` is a read-only validation endpoint. It requires task CreateView or existing DetailView/EditView access, retains omitted/locked persisted fields, and permits newly selected relations only with matching record type and DetailView access. It returns true or a localized error through the standard response envelope; it never saves records or returns related dates. `getLatestMilestoneTaskDate()` owns the active linked-task aggregate used when saving a milestone; it must include hidden/filtered tasks and exclude deleted records and missing/zero boundaries.
- `ProjectTask_Edit_Js extends Vtiger_Edit_Js` registers date checks through the existing jQuery `remote` validator during `registerBasicEvents()`, covering full Edit, Quick Create, overlays and chart QuickEdit (which extends it). Rules and namespaced change/reference listeners belong to each form and register once. Relation/date changes invalidate remote caches. Unique per-form request ports isolate nested forms; failures release pending validation, and detached forms cannot submit on late responses. No independent submit handler, synchronous request, global hook or browser date parser is added. Parent views load the module Edit resource through their standard script lists.
- Chart saves use the normal record lifecycle without revision tokens, stale-edit rejection or advisory locks. `getRecordSnapshots()` supplies only persisted values for chart projection consistency; it must not reintroduce a save guard based on entity/view metadata.
- The Project chart uses the standard ProjectTask Edit overlay and SaveAjax; QuickEditAjax remains available to other consumers. QuickEdit forms own escaped field-metadata JSON and a one-time controller registration; no global quick-create metadata or document handlers are introduced. Reuse standard reference autocomplete, selection, clearing and creation events rather than attaching a full-page controller to the project screen. Status settings replace their namespaced submit listener and guard pending saves.
- `ProjectTask_ClosedStatus_Model` owns `df_projecttask_closed_status` keyed by stable picklist status IDs. `installTables()` only creates schema. `registerDefaultClosedStatuses()` registers the configured `registerClosedStatuses` values through INSERT IGNORE after picklist creation; `addCustomLinks()` invokes it during installation, updates and enable events. Registration skips all writes whenever ClosedStatus_Model::hasClosedStatuses() detects any stored row, preserving nonempty administrator selections. An empty table is initialized with defaults on the next registration, including after an administrator clears all selections. Repeated registration is a no-op once any row exists. Runtime uses configured IDs, including custom/renamed statuses. The administrator-only ChartSettings view/action edits this metadata without changing task statuses or progress.
- Validation: lint affected PHP, load child declarations with real parents, verify missing/equal/reversed/leap-day dates, field locks and record access, quick-edit saves and ordinary full saves. Live persistence/history verification requires an authenticated CRM/database environment.

- ProjectTask Edit narrows milestone popup selection through the standard related-parent parameters and autocomplete through parent-module/id parameters. Both target the selected project. Standard Edit overlays retain module-local remote date validation and the chart refreshes after SaveAjax without navigation.

- The linked milestone date is the inclusive task deadline, not a lower start bound. Validate both known task boundaries against it through hasDatesBeforeMilestoneEnd(); the milestone save aggregate includes the latest known start/end even for partially scheduled or hidden tasks.

- tests/gantt user-run fixtures create tasks through Vtiger_Save_Action and the module record validation, convert ISO fixture calendar dates to the acting user format, and finalize statuses only after dependency creation. They do not bypass custom record rules, add users or alter production schema.

- Fixed date-validation reference modules, date field lists and quick-edit chart fields are typed static configuration on their owning action/model; loops retain the configured field order.

- `ProjectTask_Install_Model::getBlocks()` owns the `assigned_user_id` field label `LBL_TASK_ASSIGNEE`; module language files translate it as Assignee (Riešiteľ in Slovak). Core installation/update applies the label to existing fields without changing assignment storage or permissions.

- The VARCHAR-to-INT schema conversion uses the existing non-strict PearDatabase session: numeric percent prefixes retain their integer value, empty text becomes zero and NULL remains NULL. It introduces no separate content UPDATE, global SQL-mode change or progress recalculation. Validate stored values before applying this conversion to another installation.

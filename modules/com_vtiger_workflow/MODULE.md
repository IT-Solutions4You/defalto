# Workflow execution and record persistence

- `Workflow::setNewRecord()` and `isNewRecord()` delegate creation context to `VTJsonCondition`, whose flag defaults to false. `Workflow::getEvaluationClone()` clones both the workflow and its condition strategy. `VTWorkflowEventHandler` uses this method for evaluation and sets the save event's creation flag on that copy. Completion tracking and tasks use the original workflow; its creation context remains unchanged even if evaluation throws. Related-record conditions exclude this context through their referred source entity. Only `has been set or changed` accepts creation, using `VTWorkflowEntity::hasInitialFieldValue()` (null, empty string, and empty array are excluded; zero and false are values). `has changed`, `has changed to`, and `has changed from` are false on creation. Never infer creation from a missing delta snapshot; verify clone isolation on success and exceptions when reusing workflow objects.
- On updates, `has changed` and `has been set or changed` share `VTWorkflowEntity::hasFieldChanged()`: require both snapshots and field keys, compare explicit null transitions strictly (including null to zero or empty string and the reverse), and delegate non-null values to shared `VTEntityDelta::hasChanged()`. Missing fields are not null values. `has changed to` and `has changed from` retain their legacy update behavior. The shared null-value `isset()` gate and `getDataDelta()` empty-to-zero behavior remain unchanged. The shared API also serves inventory, Contacts, HelpDesk, and WSAPP. Validate creation, null/empty/zero transitions, unchanged saves, changed target values, related records, and calls without creation context separately.
- `VTWorkflowEventHandler` applies execution mode before conditions: first-save, every-save, and eligible once-only workflows can evaluate on creation; modify-only workflows cannot. `WorkFlowScheduler::addWorkflowConditionsToQueryGenerator()` skips change operators during scheduled query construction; save-event change semantics must not be inferred for scheduled workflows.

- `VTCreateEntityTask::getFieldInfo()` receives the source module from the workflow editor and retains every source owner field in the parent-owner option group. Option values are source field names, stored as `rawtext`; `doTask()` resolves them from the source record when assigning `assigned_user_id`, preserving user or group IDs. The optional module argument retains compatibility for existing single-argument callers.

- `VTTrashTask` in `models/TrashTask.php` is a standard non-immediate task loaded through the legacy registry. `getContents()` supplies the nonempty queue marker. Execution delegates to `Vtiger_Record_Model::delete()`, preserving normal module deletion handlers and RecycleBin restore support; missing records and recursive calls for the same record are ignored. The persisted `deletionMode` defaults to `trash` for new and legacy tasks; only the exact value `permanent` enables `isPermanentDelete()`. Permanent mode calls `RecycleBin_Module_Model::deleteRecords()` only after normal deletion succeeds, reusing its existing cleanup semantics (including its outstanding module-table cleanup TODO). It does not register a deletion trigger or change other task execution.
- `Install_InitSchema_Model::registerTrashWorkflowTask()` registers only the task type idempotently. Initial workflow setup and migration `20260915120000` share it. Validate with PHP lint, loading against the real VTTask parent, queue-content and serialization checks, Smarty rendering, and live execution through the normal workflow cron.

- `VTWorkflowManager.inc` owns workflow definitions and immediate execution through `Workflow::performTasks()`. Settings management lives in `modules/Settings/Workflows`.
- `VTCreateEntityTask` and `VTUpdateFieldsTask` resolve owner names using exact user/group lookups, then a single HTML-decoded fallback when neither exists. This supports legacy encoded names during execution before an editor resave. Exact literal entity-like names retain precedence; unresolved names retain the existing source-owner fallback. Keep the editor's owner-name resolution in `Settings/Workflows/views/EditV7Task.php` consistent.
- `WorkFlowScheduler.php::queueScheduledWorkflowTasks()` executes immediate scheduled tasks and queues other tasks. `cron/modules/com_vtiger_workflow/com_vtiger_workflow.php::vtRunTaskJob()` executes queued tasks. All three execution paths delegate task execution to `ModTracker_History_Helper::processTask()` to scope workflow/task attribution.
- `VTUpdateFieldsTask` executes immediately even for scheduled workflows, so its scheduled history does not depend on the queue runner. The queue runner still needs the attribution wrapper for non-immediate tasks; queue storage retains task IDs but not an active PHP execution context. `VTEmailTask` is a non-immediate task that can save an email record.
- Definitions, tasks, and pending work use `com_vtiger_workflows`, `com_vtiger_workflowtasks`, and `com_vtiger_workflowtask_queue`. Initial event and cron registration lives in `Install_InitSchema_Model`.
- Scheduled selection compares `nexttrigger_time` with a single scheduler-start timestamp in the active administrator's time zone. `queueScheduledWorkflowTasks()` updates each workflow's next trigger after record processing and immediate tasks, before the cron entry point calls `vtRunTaskJob()` for queued tasks. This timestamp is not proof that queued emails were sent.
- `Workflow::getNextTriggerTimeForHourly()` owns the hourly calculation; like the other interval methods, it uses the time zone selected by `getNextTriggerTime()`.
- The scheduler passes the stored planned trigger through `VTWorkflowManager::updateNexTriggerTime()` to `Workflow::getNextTriggerTime()`. Hourly recurrence advances that reference by local calendar hours in the active administrator's time zone until strictly after the calculation time, skipping missed intervals without accumulating processing delays. PHP local-hour arithmetic skips nonexistent spring-forward hours and does not schedule both occurrences of a repeated autumn hour. Missing or unparseable references fall back to current time plus one hour. Other schedule types ignore the reference; editor calls without a reference retain their existing recalculation behavior. The stored local datetime has no UTC offset and cannot distinguish repeated-hour occurrences.
- `VTWorkflowManager::save()` delegates new definition inserts to `Settings_Workflows_Workflow_Model`, which assigns server-owned `createdtime` (database time zone) and `creator` (current execution user, nullable). Existing-definition updates do not overwrite creation metadata. `Workflow::setup()` hydrates it when selected; template/export payloads do not carry the source creation identity into new definitions.
- `VTJsonCondition::evaluate()` groups rows by `groupid` (missing means 0), joins rows using `joincondition` (missing/empty means and), and combines groups using `groupjoin` (missing/empty means and). Legacy normalization must preserve these semantics, not merely set the editor marker.
- `VTWorkflowManager::save()` delegates condition normalization to `Settings_Workflows_Condition_Model`, persisting compatible conditions with `filtersavedinnew=6` and retaining unsupported expressions with marker 5. Export/import preserves the marker; importing older payloads also passes through normalization. Workflow template instantiation uses `deserializeWorkflow()`.
- `VTUpdateFieldsTask::doTask()` uses `ModTracker_History_Helper::saveRecord()` for source and referenced records. This retains `CRMEntity::saveentity()` semantics while sharing the after-save history writer. `VTCreateEntityTask` uses `save()` for new records and inherits the current task context through the normal history handler.
- ModTracker flushes the initiating save before task execution and advances its own baseline after task writes; `VTEntityDelta` workflow condition baselines are not replaced. Both immediate and scheduled field updates produce separate attributed history.
- Audit integration must account for immediate, scheduled, and queued execution, referenced records, and overlapping changes to the same field. Replacing `saveentity()` with `save()` also invokes workflow events and changes execution behavior.
- Validate changes with PHP lint and manual execution of all three task paths, including multiple workflows updating the same field and no-op updates.
- `VTEmailTask::getContents()` substitutes workflow variables through VTSimpleTemplate after EMAILMaker prepares HTML/styles. transformToUserFormat() delegates text fields to the owning Vtiger_Field_Model::getInstance(...)->getDisplayValue(), returning immediately to prevent a second newline conversion. Vtiger_Text_UIType owns isHtmlField() and text formatting. Missing field models retain the legacy conversion fallback; other data types retain their existing owner-based formatting. Separately appended signatures and final WF paragraph cleanup remain downstream.
- HTML variables retain their full value unchanged. Other fields and comment bodies use Core_SimpleHtmlDom_Helper::convertNewlinesToHtml() so source newlines before p or /p do not create additional br elements. The entity cache already decodes webservice strings; no extra decoding is introduced here.
- The generated email record carries source `WF`. ITS4YouEmails normalizes existing br runs at paragraph boundaries only in the final processed HTML, after recipient rendering. This covers inline variables and the separately appended signature; the task still preserves both when configured, and does not remove document wrappers.

- Save-event `VTEntityData::getData()` may return `TrackableObject`, not an array. `hasFieldChanged()` unwraps each snapshot through `getColumnFields()` before checking field keys, preserving explicit null values and leaving tracking untouched. Validate with the real TrackableObject class as well as array snapshots; array-only fixtures do not cover the save path.

- `has been set or changed to` matches the current value on creation or a null-aware update; `has been set or changed from` requires an update and matches the old snapshot. They use `VTWorkflowEntity::hasFieldValue()` with decoded string comparison (numeric zero matches the editor literal "0"); an empty target matches null or empty string. Both require comparison inputs, are excluded for related fields and skipped by scheduled query construction. The from operator is unavailable for creation-only workflows. They accompany the corresponding legacy to/from operators in field metadata.

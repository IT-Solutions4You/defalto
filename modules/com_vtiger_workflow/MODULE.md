# Workflow execution and record persistence

## Purpose and ownership

- `VTWorkflowManager.inc` owns workflow definitions and immediate execution through `Workflow::performTasks()`. Management UI, the condition and task editors, and the list live in `modules/Settings/Workflows`.
- Definitions, tasks and pending work use `com_vtiger_workflows`, `com_vtiger_workflowtasks` and `com_vtiger_workflowtask_queue`. Initial event and cron registration lives in `Install_InitSchema_Model`.
- `VTWorkflowManager::save()` delegates new definition inserts to `Settings_Workflows_Workflow_Model`, which assigns the server-owned `createdtime` (database time zone) and `creator` (current execution user, nullable). Updates never overwrite them. `Workflow::setup()` hydrates them when selected; template and export payloads do not carry the source creation identity into new definitions.
- `VTWorkflowManager::save()` also delegates condition normalization to `Settings_Workflows_Condition_Model`: compatible conditions are stored with `filtersavedinnew=6`, unsupported expressions keep marker 5. Export/import preserves the marker, older payloads pass through normalization, and template instantiation uses `deserializeWorkflow()`.

## Conditions

- `VTJsonCondition::evaluate()` groups rows by `groupid` (missing means 0), joins rows with the outgoing `joincondition` and groups with the outgoing `groupjoin` (missing or empty means and). AND takes precedence over OR at both levels, matching saved-list SQL. Start from actual condition results, not true, when combining OR groups, and keep group encounter order.
- `WorkFlowScheduler::addWorkflowConditionsToQueryGenerator()` builds the scheduled selection with the same semantics: it drops unsupported change predicates before building groups, uses the previous surviving row's outgoing connector (first rows have none, group boundaries use the previous group's connector) and wraps all groups in an outer group to keep the caller's constraints. Validate SQL construction and event evaluation against the same mixed AND/OR truth tables.

### Change comparators

- Creation context: `Workflow::setNewRecord()`/`isNewRecord()` delegate to `VTJsonCondition` (flag defaults to false). `Workflow::getEvaluationClone()` clones the workflow and its condition strategy; `VTWorkflowEventHandler` evaluates that copy and sets the save event's creation flag on it. Completion tracking and tasks use the original workflow, whose creation context stays unchanged even when evaluation throws. Related-record conditions exclude this context through their referred source entity. Never infer creation from a missing delta snapshot.
- On creation only `has been set or changed` (and its `to` variant) can match, using `VTWorkflowEntity::hasInitialFieldValue()` (null, empty string and empty array do not count; zero and false do). `has changed`, `has changed to`, `has changed from` and `has been set or changed from` are false on creation.
- On updates `has changed` and `has been set or changed` share `VTWorkflowEntity::hasFieldChanged()`: both snapshots and the field key must exist, explicit null transitions are compared strictly (including null to zero or empty string and the reverse), and non-null values go to `VTEntityDelta::hasChanged()`. A missing field is not a null value. `has changed to`/`from` keep their legacy `VTEntityDelta` behavior.
- `has been set or changed to` matches the current value on creation or on a null-aware update; `from` requires an update and matches the old snapshot. Both use `VTWorkflowEntity::hasFieldValue()` with decoded string comparison (numeric zero matches the editor literal "0"; an empty target matches null or empty string) and require a comparison value.
- Save-event `VTEntityData::getData()` may return a `TrackableObject`; `hasFieldChanged()` unwraps each snapshot through `getColumnFields()` before checking keys, so explicit nulls survive. Test with the real class, not only array snapshots.
- The shared null `isset()` gate and `getDataDelta()` empty-to-zero behavior are unchanged; the same `VTEntityDelta` API serves inventory, Contacts, HelpDesk and WSAPP.
- `VTWorkflowEventHandler` applies the execution mode before conditions: first-save, every-save and eligible once-only workflows can evaluate on creation; modify-only workflows cannot. The scheduler skips all six change operators (`has changed`, `has been set or changed`, and the `to`/`from` variants of each), so scheduled workflows must not rely on save-event change semantics. Related-record fields do not get these operators in the editor.

## Scheduling

- Scheduled selection compares `nexttrigger_time` with a single scheduler-start timestamp in the active administrator's time zone. `queueScheduledWorkflowTasks()` executes immediate tasks, queues the others, and updates each workflow's next trigger after record processing, before the cron entry point calls `vtRunTaskJob()` for queued tasks. The timestamp is not proof that queued emails were sent.
- The scheduler passes the stored planned trigger through `VTWorkflowManager::updateNexTriggerTime()` to `Workflow::getNextTriggerTime()`; `Workflow::getNextTriggerTimeForHourly()` owns the hourly calculation. Hourly recurrence advances the reference by local calendar hours in the active administrator's time zone until it is strictly after the calculation time, skipping missed intervals without accumulating processing delay. PHP local-hour arithmetic skips nonexistent spring-forward hours and does not schedule both occurrences of a repeated autumn hour. A missing or unparseable reference falls back to current time plus one hour. Other schedule types ignore the reference; editor calls without one keep the existing recalculation. The stored local datetime has no UTC offset, so it cannot distinguish repeated-hour occurrences.

## Tasks

- `VTCreateEntityTask::getFieldInfo()` receives the source module from the workflow editor and keeps every source owner field in the parent-owner option group. Option values are source field names stored as `rawtext`; `doTask()` resolves them from the source record when assigning `assigned_user_id`, preserving user or group ids. The module argument is optional for single-argument callers.
- `VTCreateEntityTask` and `VTUpdateFieldsTask` resolve literal owner names by exact user/group lookup, then one HTML-decoded fallback when neither exists, so legacy encoded names work before an editor resave. Exact literal names keep precedence; unresolved names fall back to the source owner. Keep the editor's resolution in `Settings/Workflows` (`TaskRecord_Model`, `views/EditV7Task.php`) consistent.
- `VTSimpleTemplate` accepts native `$field` and PDFMaker-compatible `$field$` variables, including supported related-field tokens; the editor inserts the trailing-dollar form. `VTUpdateFieldsTask` and `VTCreateEntityTask` render `rawtext` mappings through it against the source entity before destination-type handling; field-name and expression mappings keep their own paths. Email, SMS, notification and Calendar tasks that use `VTSimpleTemplate` inherit the syntax.
- `VTUpdateFieldsTask::doTask()` saves source and referenced records through `ModTracker_History_Helper::saveRecord()`, which keeps `CRMEntity::saveentity()` semantics while sharing the after-save history writer. Replacing `saveentity()` with `save()` would also fire workflow events and change execution behavior. `VTCreateEntityTask` uses `save()` for new records and inherits the task context through the normal history handler.
- `VTTrashTask` (`models/TrashTask.php`) is a standard non-immediate task loaded through the legacy registry; `getContents()` returns the nonempty queue marker. It calls `Vtiger_Record_Model::delete()`, so module deletion handlers and RecycleBin restore keep working; missing records and recursive calls for the same record are ignored. `deletionMode` defaults to `trash` for new and legacy tasks and only the exact value `permanent` enables `isPermanentDelete()`; that mode calls `RecycleBin_Module_Model::deleteRecords()` after normal deletion succeeds, with its existing cleanup semantics (including its outstanding module-table cleanup TODO). It registers no deletion trigger.
- `Install_InitSchema_Model::registerTrashWorkflowTask()` idempotently registers only the task type; initial workflow setup and migration `20260915120000` share it.
- `VTEmailTask` is a non-immediate task that can save an email record with source `WF`. `getContents()` substitutes variables through `VTSimpleTemplate` after EMAILMaker prepares the HTML and styles.

### Email and text formatting

- `VTSimpleTemplate::transformToUserFormat()` delegates `text` fields to `Vtiger_Field_Model::getDisplayValue()` and returns immediately, so newlines are not converted twice. `Vtiger_Text_UIType` owns the HTML-versus-plain-text decision, so HTML variables keep their full value. If no field model exists the legacy conversion applies; other data types keep their existing formatting (dates use the record owner's format). Other fields and comment bodies use `Core_SimpleHtmlDom_Helper::convertNewlinesToHtml()`, so source newlines before `p` or `/p` do not add `br` elements. The entity cache already decodes webservice strings; no extra decoding is added.
- `ITS4YouEmails_Record_Model` normalizes `br` runs at paragraph boundaries (`convertParagraphBreaks()`) only for source `WF`, in the final processed HTML after recipient rendering. This covers inline variables and the separately appended signature, which the task still preserves when configured. Document wrappers are not removed.

## Execution paths and audit history

- Immediate execution (`VTWorkflowManager.inc`), scheduled immediate tasks (`WorkFlowScheduler.php::queueScheduledWorkflowTasks()`) and queued tasks (`cron/modules/com_vtiger_workflow/com_vtiger_workflow.php::vtRunTaskJob()`) all run tasks through `ModTracker_History_Helper::processTask()` to scope workflow/task attribution. Queue storage keeps task ids but no PHP execution context, so non-immediate tasks need the wrapper.
- `VTUpdateFieldsTask` executes immediately even for scheduled workflows, so its history does not depend on the queue runner.
- ModTracker flushes the initiating save before task execution and advances its own baseline after task writes; `VTEntityDelta` condition baselines are not replaced. Immediate and scheduled field updates both produce separate attributed history.

## Validation

- PHP lint, plus manual runs of all three execution paths (immediate, scheduled, queued) including referenced records, several workflows updating the same field, and no-op updates.
- Condition changes: truth tables for mixed AND/OR in both `VTJsonCondition` and the scheduler SQL; creation, null/empty/zero transitions, unchanged saves, changed targets, related records and calls without creation context for change comparators; clone isolation on success and on exceptions.
- Trash task: loading against the real `VTTask` parent, queue-content and serialization checks, Smarty rendering, and live execution through the normal workflow cron.

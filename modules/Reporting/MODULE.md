# Reporting

- Report definitions are stored in `df_reporting` and `df_reportingcf`. `Reporting_Install_Model` extends `Core_Install_Model` for fields and widgets; `Reporting::$moduleVersion` controls install and update versioning.
- `Reporting_Fields_Model` owns both persisted module-field metadata and the synthetic report fields `id` and `label`. Resolve either kind through `Reporting_Fields_Model::getField()`; referenced synthetic fields do not exist in `Vtiger_Module_Model::getField()`. `id` requires module view access, and `label` additionally requires every entity-name field to be viewable.
- Report field choices and saved field-based configurations are restricted through `Reporting_Fields_Model::getViewableFields()` and `getViewableFieldsByType()`. Both the primary reference field and the selected related-module field must remain viewable to the current user; permission-derived field metadata caches are keyed by user and module.
- `Core_QueryGenerator_Model` applies the primary module's sharing query. Before table rendering, `Reporting_Record_Model` also rejects primary records without `DetailView` permission, while `Reporting_Table_Model` rejects inaccessible referenced records before either traversal or reference-label formatting. Keep these checks shared by previews, widgets, charts, PDF, and XLS output.
- `Reporting_Record_Model::getFilter()` removes conditions whose direct or referenced field is not viewable by the current user. Query execution and PDF filter summaries must consume this sanitized representation, not the raw stored JSON.
- Report preview and execution use `Core_QueryGenerator_Model::parseAdvFilterList()`, which owns terminal connector cleanup, empty-group removal and outer grouping. `Reporting_Record_Model::getFormatedFilters()` returns the stored filter groups and connectors unchanged, so saved filters may keep an outgoing connector on the last group or have empty or sparse groups. Normalize only at the shared query boundary, never with a two-group assumption.
- `Reporting_Field_Model::getReportTypeOptions()` supplies the fixed technical values `tabular` and `summary` with central Reporting translations. Normal and editable picklist accessors both use it, so no picklist tables or seeded values are needed. Existing record values stay unchanged.
- `Reporting_Edit_View` owns the editor and the `renderTable` preview. Frontend assets are under `layouts/d1/modules/Reporting` (`resources/Edit.js`, `Table.js`, `Detail.js`); Chart.js is loaded in both the normal and overlay flows.
- Chart configuration: the X axis is the first grouping field (`Reporting_Record_Model::getChartConfiguration()`); series are limited to enabled calculations (`count` plus `sum`, `avg`, `min`, `max`) and valid numeric fields. `Reporting_Edit_Js` derives the Y-axis options from the enabled calculation checkboxes. With no enabled calculation it disables the selector and shows `chartCalculationWarning`, and hides the warning again when options become available.
- `Reporting::save_module()` delegates sharing persistence to `Core_SharingRecord_Model`: `all` shares view access with the base role and subordinates, `selected` with the chosen members, `private` with nobody. The edit list is always empty.
- `max_entries` is stored but not applied: the query generator runs with `setLimit(0)` and `getMaxEntries()` is not used.
- PDF and XLS exports (`Reporting_PDF_Model`, `Reporting_XLS_Model`) are generated under the configured temporary directory through `Core_Storage_Model::initTemporaryFileDirectory()`. They must not use persistent attachment storage.
- Validate with `node --check layouts/d1/modules/Reporting/resources/Edit.js`, ITS4You ScriptsValidator (`source_module=Reporting&only_errors=1`) and `php -l` on changed PHP files; check inherited signatures for field-model changes. Manually check an empty calculation selection, enabling and disabling calculations, and report type choices without seeded picklist values.

# Appointments

- `Appointments_Install_Model` inherits `Core_Install_Model::install()` so post-install, enable, and post-update flows call both `addCustomLinks()` and `updateSummaryWidgets()`. Do not restore a module-local lifecycle override that omits the shared summary-widget registration. Appointments summary widgets are persisted as `DETAILVIEWWIDGET` links and are removed by the inherited pre-uninstall flow.
- `VTCalendarTask` is the Appointments-owned workflow task registered by `Appointments_Install_Model`. Its runtime implementation is in `workflow/VTCalendarTask.php`, while its editor template and task-specific UI behavior are under `layouts/d1/modules/Appointments/taskforms`.
- The task stores its standard calendar values as task properties. Required additional Appointments fields retain their legacy task properties; optional and custom field mappings are stored in `field_value_mapping` as JSON entries containing `fieldname`, `value`, and `valuetype`.
- Mapped destination fields must be active, editable, optional Appointments fields outside `ignoredFieldNames`. Runtime revalidates the stored field name before assigning it so removed, disabled, or protected fields are skipped.
- Subject, description, required additional fields, and raw-text mapped values are rendered with the shared `VTSimpleTemplate` against the workflow source record. Both the native `$field` form and the PDFMaker-compatible `$field$` form are accepted. Field mappings may also use the workflow editor's field-name and expression value types.
- The value modal and variable insertion are owned by Settings/Workflows (`FieldExpressions.tpl`, `Edit.js`). Subject and description are restricted to `rawtext`; dynamic mappings keep the field-name and expression modes. Mapping controls without a native popup, such as picklists, use the shared template-edit trigger; a destination field can be mapped only once.
- Date and time placement remains owned by `VTCalendarTask::getDateTime()`, and the source record relation remains selected by `getRelationField()`.
- Calendar drag-and-drop and resize persistence is owned by `Appointments_Calendar_Action::UpdateDates()`. It must enforce record-level `Save` permission through the boolean `Users_Privileges_Model::isPermitted()` API before changing any appointment fields; the legacy global `isPermitted()` returns string values and must not be used as a boolean.
- FullCalendar runs with the current user's named time zone and, without a named-time-zone plugin, exposes UTC-coerced native `Date` markers. Calendar request and drag/resize values must read both date and time through UTC getters so the user's wall-clock value remains intact; `UpdateDates()` then converts that value once from user format to database UTC during record save.
- Calendar popovers and event-info refreshes must retrieve records through `Appointments_Events_Model::getViewableRecordModel()`. This shared boundary resolves the record's actual module and requires record-level `DetailView` permission before any record data is rendered or returned.
- Event-type definitions are shared rows with per-user settings. Only administrators may delete default definitions. Deleting a custom type removes the current user's association and removes the shared definition only when no users remain; an existing custom type may be edited only through an associated user. Mutating event-type requests must use write-access validation.
- Validation: PHP lint on touched files (`workflow/VTCalendarTask.php`, `actions/Calendar.php`); JavaScript syntax check and the ITS4You ScriptsValidator for touched resources; a manual create-calendar workflow covering literal values, source variables, expressions, custom fields, and all-day dates; permitted and denied drag/resize checks that confirm both persistence and UI reversion; drag/resize checks around midnight in UTC, Europe/Bratislava, a negative-offset zone, and a high positive-offset zone, including DST boundaries.
- `Appointments_InvitationEmail_Model` sends invitations only when at least one invited user exists and writes the `.ics` attachment to `test/upload` under a generated name (`invitation_<recordId>_<uniqid>.ics`). Never build that path from the subject or other user input; the file is removed in a `finally` block, and a failed write must be logged and skipped without aborting the record save. Text values are escaped and lines folded according to RFC 5545.
- Appointment `datetime_start` values are stored in the database time zone (UTC). The reminder cron query must compare them with `UTC_TIMESTAMP()` so database or server session time-zone settings cannot shift the eligible reminder window.
- All-day appointment boundaries are the exception to normal appointment time-zone handling. `datetime_start` and `datetime_end` store exactly the calendar dates entered by the user, both at `00:00:00`; they are floating dates encoded in the UTC database format and must never pass through a time-zone conversion. `Appointments::requiresDateTimeConversion()` disables the final generic `CRMEntity` datetime conversion only for these two all-day fields. FullCalendar and iCalendar require an exclusive end, so their output adapters add one day without changing the stored value. Normal `Save`, quick-create `SaveAjax`, workflow, drag/drop, recurrence, invitation, reminder, detail, edit, list, summary, and calendar-feed flows must preserve this invariant. Timed appointments continue to convert exactly once between the user's time zone and UTC.
- `Appointments_Install_Model::migrateAllDayDates()` repairs legacy UTC-shifted all-day boundaries once during a module update, using the creator's time zone only to recover the original date, and persists both entered dates at `00:00:00`. Runtime all-day reads are always literal and never perform a time-zone conversion.
- `Appointments_QueryGenerator_Model` keeps the top-bar "today" selection split by semantics: all-day records are compared with the user's literal calendar date, while timed records are compared with the corresponding UTC day interval. Do not route all-day boundaries through datetime filter conversion.
- Monthly recurrence rules are evaluated as user-calendar dates and converted back to the database time zone for record creation. A requested day beyond the target month's length is clamped to that month's last day; first/last weekday rules stay within the intended user-calendar month, including when the UTC date falls in an adjacent month.
- `Appointments_Save_Action` normalizes recurrence start/end values from either the split edit controls or the combined `datetime_start`/`datetime_end` values before the record save, because the CRM entity persists recurrence metadata during that save. Afterward, `saveRepeatEvents()` reads timed values through `DateTimeField`, but reads all-day values through the record model's date-only API. This keeps quick-create and all-day requests from passing empty or time-zone-shifted values into recurrence conversion.

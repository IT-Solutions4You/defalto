# Vtiger shared runtime

This module holds shared base behavior inherited by other modules. It has no standalone installable module version; the sections below only record the invariants that are easy to break.

## Summary widgets

- `Vtiger_Link_Model::getTranslatedLabel()` translates a widget label in the module named by the link's `linkName` (links without a related-module owner use the source record module). When the related module does not define the label it falls back to the source module, because custom widget labels are registered there. `SummaryViewWidget.tpl` uses the resolved label for both the heading and the add action.
- `SummaryViewWidgets.tpl` treats a missing or empty `DETAILVIEWWIDGET` link group as a valid empty layout. `getDetailViewLinks()` does not guarantee a key for link types without links, so guard the collection before iterating.
- A summary widget link URL with `headerActions=1` lets the widget's own module (`module` URL parameter) add actions to the widget header: `Vtiger_DetailView_Model::getWidgets()` sets `headerActionsModule` and `SummaryViewWidget.tpl` includes `SummaryWidgetHeaderActions.tpl` of that module (used by InventoryItem). Do not hard-code module-specific buttons in the shared header.

## Shared utilities and storage

- The running application version is owned by `version.php` as `$defalto_current_version`. Shared runtime code must use that value and must not restore the removed `vtiger_current_version` global.
- `Vtiger_Header_View::getHeaderLinks()` builds only application-owned settings, user, and registered header links. Do not restore hard-coded upstream vtiger feedback, documentation, video, or marketing URLs.
- Legacy layout help links must target the Core `Documentation` redirect route; never link directly to upstream vtiger documentation.
- `Vtiger_Base_UIType::getRequestValue()` is the shared server-side field-value validation boundary used by `Save` and `SaveAjax`. `Vtiger_Util_Helper::validateFieldValue()` rejects empty mandatory fields, malformed email and numeric values, and unavailable picklist values with an exception; it must never silently coerce an invalid submitted value. New records also validate every editable mandatory field in `Vtiger_Save_Action::saveRecord()`, including fields omitted from the request; non-editable generated fields remain owned by the persistence lifecycle. Partial edits retain omitted values from the existing record.
- `Vtiger_Functions::validateImage()` and `validateImageMetadata()` are compatibility facades over `Core_ImageValidation_Helper`; keep validation logic out of the legacy utility.
- The global `isPermitted()` in `include/utils/UserInfoUtil.php` is a compatibility facade for the Users-owned permission model. Keep module, action, ownership and sharing evaluation in `Users_Privileges_Model`.
- Shared record downloads and `Vtiger_ShowFile_Helper` resolve `vtiger_attachments.path` through `Core_Storage_Model`, which accepts legacy relative paths and configured absolute paths outside the web directory. Browser-visible images must use `Core_Storage_Model::getAttachmentPublicUrl()` and never expose the physical path. Persistent attachment writers keep using `decideFilePath()`; temporary generated files use the Core temporary-directory flow.
- `Vtiger_Field_Model::isHtmlField()` checks the field name against the public instance array `$htmlFields` (empty by default). Owning module field models override it, and callers can set `set('htmlFields', ['field_name'])` on one object. It is runtime configuration only: it neither enables an editor nor sanitizes HTML, and HTML semantics must not be inferred from textarea uitypes or content. `getCleanInstance($fieldName, $moduleName)` resolves the owning field model without database hydration and keeps its default list, so workflow substitution uses the module definition; changing one field instance does not configure others.
- `Vtiger_Text_UIType::getDisplayValue()` owns HTML-versus-text formatting through the owning field model's `isHtmlField()`. HTML values pass through unchanged and `commentcontent` keeps its legacy pass-through. Other text fields keep the removeTags/sanitization order and then use `Core_SimpleHtmlDom_Helper::convertNewlinesToHtml()`. Field-model `getDisplayValue()` delegates here for text fields.

## Mass-email recipient preferences

- `Vtiger_RecipientPreference_Model` owns the per-user, per-source-module recipient field preference in `vtiger_emails_recipientprefs`. MailManager and the module mass-email views use this model and do not persist preferences themselves.
- It follows `Core_DatabaseData_Model`: `$table`, `$tableId` and `$columns` are instance metadata and `getRecipientPreferenceTable()` is the CRUD boundary. `save()` and `delete()` keep the parent's `void` contract; database failures propagate to the central WebUI exception handler.

## CRM Settings menu

- `Settings_Vtiger_MenuItem_Model::$defaultMenuItemLinks` owns the standard CRM Settings items. The Inventory section links the Product block templates (`LBL_PRODUCTBLOCKTPL`) to the Core-owned `index.php?module=Core&view=ProductBlocks`. Migration `20261023143000` calls `installLink('LBL_PRODUCTBLOCKTPL')`, so existing installations get the item idempotently without rebuilding every settings link.

## Record header, quick preview and tooltips

- Read-only record actions use `Core_Readonly_Model::isMakeReadonlyPermitted()` for the same decision as the Core action. Administrators see lock or unlock according to state; a non-administrator sees Lock only for a directly assigned record that the user may edit.
- Vtiger.js keeps the shared preview request launcher and its stale-response counter. After the modal's `SCRIPTS` run, the callback calls Core QuickPreview's static `registerPreview()`. Do not load Core QuickPreview globally or initialize it inline in Smarty.
- `getQuickPreviewHeaderScripts()` declares the base and module-specific Detail/RelatedList dependencies followed by Core QuickPreview. Overrides must keep Core QuickPreview last, because `RecordQuickPreview::process()` only assigns the returned list without merging extra resources. `ListViewQuickPreview.tpl` consumes the ordered, cache-busted `SCRIPTS` at the end of the modal markup. Escaped field JSON belongs to a hidden control and scoped container data, not a global `quick_preview_uimeta`. Core owns modal actions and cleanup, including removing its script elements and class on close.
- `RecordQuickPreview` requests are AJAX, so WebUI skips `Detail::preProcess()`; `process()` must assign `REQUEST_INSTANCE` and `IS_AJAX_ENABLED` itself before rendering the shared header. Header edits (ordinary fields, checkbox switches, Assigned To) use the record and module from their nearest form or the scoped Detail instance, never the underlying page.
- All record delete links go through `Vtiger_Detail_Js.deleteRecord(url, handler)`; keep the link model independent of preview context and JavaScript controller selection. The handler is either a success callback `(params, result)` or an object with optional `hasRecord(params)`, `onSuccess(params, result)` and `onError(error, params)`. `registerDeleteRecordHandler()`/`removeDeleteRecordHandler()` manage a modal-scoped handler without referencing QuickPreview or a modal selector. A registered handler is chosen only for its matching record and rechecked after confirmation. Pending state prevents duplicate requests, and success callbacks never run after cancellation or a failed response.
- Without a matching handler, Detail keeps the host controller's `remove()` entry point so module overrides still work; the base `remove()` uses the same flow and redirects to the returned list URL. Core's handler closes its own modal and refreshes the source screen instead.
- Detail tab lookup, AJAX response targets, related-list events, pagination, roll-up comment controls and form bindings are scoped through the active Detail controller's container or content holder. `Vtiger_RelatedList_Js` must render responses only into its initialized `relatedContentContainer`; never use a page-wide `.details` or `.relatedContainer` target. Preview actions such as showing more comments or related records must never find, update or activate content belonging to the full-page record underneath the preview, and overlay or quick-preview tab loads must not update the browser URL.
- `vtUtils.enableTooltips()` reuses Bootstrap instances through `getOrCreateInstance()`, because full-page and dynamic preview initialization can revisit the same elements and a second instance leaves orphaned handlers. `DetailViewHeaderTitle.tpl` action tooltips use the hover trigger and accessible button labels; a click must not keep the tooltip visible through focus after the pointer leaves.

## Select2

- `vtUtils.showSelect2ElementView()` in `resources/Utils.js` initializes shared Select2 fields (including `uitypes/Owner.tpl`) on full pages and overlays; `JSResources.tpl` loads vendor Select2 4 before it. When there is no `select.select2` element it must return the empty jQuery collection unchanged, and selected-result registration must tolerate a missing Select2 instance. A throw here interrupts the shared document-ready queue, including the later page-ready timing callback.
- `registerSelect2SelectedResults()` wraps the results adapter's `setClasses()` to hide selected results and exhausted optgroups on each native selection refresh. Restore marked results before recalculating, and remove `aria-selected` from hidden results because the adapter uses it for keyboard navigation. Preserve option values, selected labels, custom templates and vendor files. Check single/multiple selection, optgroups, search, deselection, keyboard navigation and AJAX results when changing it.

## List view

- `Vtiger_ExportData_Action` is the shared export query boundary for entity modules. A requested field must resolve to module field metadata, and its sort direction is normalized and restricted to `ASC` or `DESC` before it is appended to `ORDER BY`; malformed directions raise an `Exception` and never reach SQL.
- The column configuration dialog in `List.js` allows any number of fields with a minimum of one, and submits the complete ordered `columnslist` through the existing save flow.
- Standard `ListViewContents.tpl` uses the Core-owned Bootstrap filter toolbar instead of the column search row. `List.php` assigns untouched `LIST_FILTER_PARAMS` before adding legacy field-name keys to `SEARCH_DETAILS`, and `Vtiger_List_View::setListFilterData()` (call it first, for the base list and initializers such as Documents) supplies toolbar state, the flat `LIST_FILTER_FIELDS` and the Core-owned block-grouped `LIST_FILTER_FIELD_GROUPS`. `List.js::getListSearchParams()` reads the toolbar state when present and keeps the legacy path for specialized list templates; resetting a saved view clears both, and post-load rendering restores chips from the server response.
- The filter dropdown toggle sits beside `listColumnFilterContainer` in the first header cell and applied conditions stay inside the dropdown. Its empty owner form is outside `listedit`, with HTML `form` attributes associating the header controls, which also keeps form ownership when floatThead moves the header.
- `loadListViewRecords()` rejects failed requests without replacing the table and resolves after the new content is installed. Filter changes reset paging and selection only after success; export and mass actions keep using `getListSearchParams()`.
- Temporary `search_params` belong to the current request/URL. `Vtiger_ListView_Model` excludes them from shared sort-session writes and returns an empty search fallback when reading legacy session arrays. List JavaScript pins the rendered `viewname` and conditions in the URL on initialization and after each successful refresh, preserving PJAX history metadata; empty filters stay explicit so another tab's conditions are never restored. Switching saved views uses the existing reset flow.
- `Vtiger_Util_Helper::transferListSearchParamsToFilterCondition()` converts list and advanced-search conditions for the query generator. Legacy source group 0 uses AND within the group and group 1 uses OR; modern groups carry their own within-group operator. Empty groups are not emitted, but their source positions are kept when choosing legacy defaults, and groups holding only connector metadata are ignored so no column at index -1 appears. Every non-empty group keeps an explicit `condition` connector, which allows more than two groups; missing connectors default to first-group AND / second-group OR.
- `Vtiger_ListAjax_View::showSearchResults()` loads the entries and separately requests the total through `Vtiger_List_View::getListViewCount()`; both need valid conditions without a trailing group connector.
- ListView (including popups), ExportData and MiniList use `Core_QueryGenerator_Model` by default. ListView resolves a module-owned `<Module>_QueryGenerator_Model` when it extends Core, allowing domain-specific structured conditions without modifying completed SQL; Appointments uses this for mixed all-day date and timed UTC ranges. `parseAdvFilterList()` takes the source module's `Core_Filter_Model`, normalizes the conditions and then calls the unchanged Enhanced parser. The shared model normalizes time endpoints and date-only datetime ranges while keeping symbolic periods, empty operators and monetary precision; storage and timezone conversion stay with their owners.
- `Vtiger_ListView_Model` must pass `Core_QueryGenerator_Model::getQueryParameters()` to both entry and count queries. Structured module conditions use placeholders; executing those SQL strings with an empty parameter list breaks module-owned date-range and other parameterized filters.
- Filter creation persists through CustomView; applying a top-bar filter uses the shared list search flow.

## Advanced filter editor

- `AdvanceFilter.tpl` and `AdvanceFilterCondition.tpl` are the single condition layout for saved lists, advanced search, report conditions and workflows (workflow templates are compatibility includes; see Settings/Workflows). `FILTER_EDITOR` supplies field columns, field metadata, translated operators, source and translation modules and the default-row policy through `Core_FilterEditor_Model` or a subclass; the template default keeps the legacy source-module and column-method inputs. Reset the selected field for every row including hidden clone rows, and escape option and input values. Change styling here, without workflow-specific branches.
- Condition field structures get their blocks from `Core_FilterEditor_Model::getConditionBlocks()`. The block `LBL_ITEM_DETAILS` comes after the module's other blocks in advanced search, saved filters, list filters and report conditions; edit and detail layouts are unchanged.
- Default rows: `Vtiger_BasicAjax_View::showAdvancedSearch()` supplies one empty one-based criteria group and `AdvanceSearch.tpl` enables default conditions, so opening it or selecting another module shows one selectable row (the Home module-selection placeholder is separate). `AdvanceFilter.tpl` renders a blank row when default conditions are on and the group's `columns` are empty. Check `columns`, not the whole group, because CustomView supplies empty groups that carry connector metadata. Populated groups get no extra row; keep the `SHOW_DEFAULT_CONDITIONS` opt-out. Empty criteria keep a first group, and the adapter decides whether it has a visible blank row.
- Rows expose `column_condition` AND/OR selectors. `refreshConditionConnectors()` hides and disables the last visible row's selector after initialization, insertion and deletion, and serialization clears the last included condition's connector even when trailing blank rows are skipped. Keep the group-operator fallback for specialized templates without `.rowConditionConnector`; group-to-group joins are separate. `Vtiger_SearchAdvanceFilter_Js` clears only the last populated group connector, so empty intermediate groups must not erase the preceding one.
- Connectors and delete buttons are translated through Core `LBL_AND`/`LBL_OR` and the Core JavaScript `LBL_DELETE`; verify both PHP and JavaScript dictionaries when auditing editor labels. Cloned rows and groups and dynamically created buttons must keep the same classes as the server-rendered markup. Group deletion is rendered for every saved group after the first (`GROUP_KEY > 1`), matching dynamically added groups; the first group stays as the base for cloning.
- Add-condition clicks are delegated from the filter container to `.addCondition button`, because cloned groups have no direct bindings. `Vtiger_AdvanceFilter_Js::init()` must keep only `.filterContainer` elements when the collection also contains editor wrappers (CustomView passes nested `.filterConditionsDiv`); binding both would process a click twice and add duplicate groups.
- `AdvanceFilter_Field_Js::getUiTypeSpecificHtml()` normalizes root and nested text-like inputs and textareas to Bootstrap `form-control` and marks readonly controls with `bg-body-secondary text-body-secondary`; hidden inputs, checkboxes, radios and buttons are excluded. Calculated date previews are `readonly`, not disabled, so saved-view serialization and quick-filter submission still include their values.
- `AdvanceFilterCondition.tpl` supplies per-field operator labels from `Core_FilterOperator_Model`; `AdvanceFilter.js` uses them and keeps the legacy mapping fallback for other templates. The Core quick filter reuses the shared date/datetime renderer, and the time range renderer serializes two picker inputs through one named hidden value. `AdvanceFilter_Currencylist_Field_Js` emits currency ids as option values, matching the Core toolbar and numeric currency query contract, and restores a selection by id or legacy name, so older saved filters migrate to ids on the next save.
- Time handling: `getTimeValueWithSeconds()` splits AM/PM from the clock before defaulting missing seconds, which preserves noon and midnight for save and list-filter conversion; it accepts literal AM/PM case-insensitively, so editable values must not contain translated suffixes. Standalone time fields are wall-clock values without timezone conversion. `Time.tpl` passes the same user hour format to `getEditViewDisplayValue()` and the timepicker's `data-format`; translated suffixes belong only in display output. Fix edit-value preparation rather than making save parsing accept translated labels. Shared validation enforces 12/24-hour ranges with optional seconds.

## Dashboard layout persistence

- Dashboard tab reads and mutations are scoped to the current user in `Vtiger_DashBoard_Model`; never trust a requested tab id as proof of ownership, including when adding a widget to a tab. Notebook updates use the id loaded by `Vtiger_Notebook_Model::getUserInstance()` and retain the user condition in the write, rather than re-reading `widgetid` from the request. Dashboard tab and notebook text are plain text and must be escaped at every HTML sink, including dynamically added tabs.
- Home inherits the shared Vtiger dashboard view. `DashBoard.js` initializes Gridster from the widget position and size attributes rendered by `DashBoardTabContents.tpl` and passes the saved column and row to `add_widget()` for positioned widgets; automatic placement is only for new widgets or positions outside the current viewport. Initialization must not save positions, so responsive reflow never overwrites the stored layout; drag and resize completion save all affected widgets.
- `saveWidgetLayout()` shows the shared saving indicator and one translated result notification after all position/size requests finish; a failed request prevents the success notification. While a widget is dragged or resized its content is hidden behind a status placeholder (moving/resizing, saving, loading; labels from the shared Core language files) until all writes finish, then `loadWidget(widget, true)` regenerates the full server-rendered widget with the usual post-load initialization and chart sizing. Replacement destroys old Chart.js instances, clears cached widget instances and lifecycle listeners, and keeps the Gridster node and resize handle. Failed saves or reloads keep the existing content and report the error, and the placeholder is removed on success and failure. The ordinary refresh button keeps the widget-specific flow.
- `SaveWidgetPositions` delegates to `Vtiger_Widget_Model::updateWidgetPosition()`. Updates to `vtiger_module_dashboard_widgets` are scoped by current user and dashboard tab, including ordinary widgets identified by link id; MiniList, Notebook and chart widget ids use a compound DOM id. Iterate the native `positionsmap` request array: `vtlib_array()` returns an ArrayAccess-only `Vtiger_GuardedArray` with private storage, so `foreach` over it silently processes no positions. Reject malformed maps and missing tab ids instead of reporting a successful no-op.
- `Vtiger_Module_Model::getOwnerWhereConditionForDashBoards()` is the shared owner-filter boundary for HelpDesk and Leads dashboard queries. A non-empty owner must validate as a positive integer before it enters SQL and a malformed value raises an `Exception`; an empty value keeps the all-accessible-records behavior.

## Record update history

- `RecentActivities.tpl` uses the ModTracker-owned `Workflow.tpl` partial for workflow create/update entries; history persistence, workflow lookup and administrator-only links belong to ModTracker. For those entries the heading holds only the ModTracker workflow dropdown (the actor is inside it) and the timeline icon is `fa-cogs` instead of the actor icon or avatar; ordinary entries keep their actor and action text.
- `VTEntityDelta::getDataDelta()` exposes the existing field comparison for ModTracker's independent audit snapshots; workflow condition deltas keep their own original save baseline.

## Validation

- PHP lint of touched files; the JavaScript syntax check and the ITS4You ScriptsValidator for touched resources.
- Record saves: valid and invalid required, email, integer, decimal, picklist and multipicklist values through both full save and detail `SaveAjax`; confirm rejected values leave the record and its label unchanged.
- Mass-email preferences: class loading, retrieval, insert, update and reset, then open a mass-email recipient dialog and confirm the saved selection returns.
- Quick preview and tooltips: repeated preview opens, action confirmation and cancellation, header edits from the preview.
- Filters: empty and populated groups, two tabs with different temporary conditions, reload, clearing, view switching and failed AJAX requests.
- Dashboard: drag then refresh, resize then refresh, independent tabs holding the same widget, and narrow/wide viewport reloads.

# Record action permissions

- `Save`/`SaveAjax` (`saveRecord()`), `MassSave`, `MassDelete`, the list row actions, `Detail` and `Edit` (locked fields in `blocks/Fields.tpl`, denied picklist values in `uitypes/Picklist.tpl`, a denied form shown as `Core/RecordActionDeniedPage.tpl` in the layout, a refused full save shown again in the form) apply `Core_RecordActionPermission_Model` rules; see `modules/Core/MODULE.md` (Record action permissions) for the owner, the checks and the validation scenario.

# LayoutEditor

## Ownership

- LayoutEditor administers module fields, blocks and layout settings. `Settings_LayoutEditor_Index_View` exposes the modes `showFieldLayout` (default, `FieldsList.tpl`), `showHeaderFieldsLayout`, `showRelatedListLayout`, `showRelatedListSettings`, `showPopupSettings`, `showFieldEdit` and `showDuplicationHandling`.
- The editor uses `Settings_LayoutEditor_Module_Model`, `_Block_Model` and `_Field_Model`. Editor-specific presentation, such as `getFieldDataTypeLabel()`, belongs to the editor field model, not ordinary module field models. Persistence stays in these models.
- This shared Settings component has no independent module version or schema.

## Runtime model handling

- `Module_Model::getInstanceByName()` copies the module's metadata but resets the copied `fields` and `blocks` caches, so the editor loads its own models instead of reusing runtime module models.
- `Block_Model::getFields()` converts every field to a `Settings_LayoutEditor_Field_Model`, whether freshly loaded or pre-populated through `setFields()` (as `showFieldLayout()` does), and keeps existing editor instances.

## Custom fields

- Entity modules offer the `Checklist` field type in any ordinary block. `getTypeDetailsForAddField()` maps it to Core UI type 34 and MEDIUMTEXT with V~O. addField() uses the ordinary requested properties without Checklist-specific overrides or a separate type-defaults config. Defaults for the built-in ProjectTask field belong to ProjectTask's install configuration. Core owns widget operations and permissions; translated type names remain in Core locales.

- `Block_Model::isAddCustomFieldEnabled()` blocks custom-field creation only in `LBL_TICKET_RESOLUTION` and `LBL_COMMENTS` (HelpDesk), `LBL_COMMENT_INFORMATION` (Faq) and `LBL_ITEM_DETAILS` of every inventory module from `InventoryItem_Utils_Helper::getInventoryItemModules()`. Item details are rendered by InventoryItem; other blocks of inventory modules must still allow document-level custom fields.
- `Module_Model::addField()` names the column `cf_<fieldid>` and stores it in the entity's `customFieldTable[0]` if defined, otherwise `vtiger_<module>cf`. Fields added to inventory modules always get quick-create value 3.

## Validation

- Run `php -l` on changed PHP. Check cold and pre-populated block fields, repeated access, and module conversion with populated runtime caches; editor field lists must expose editor-specific methods without modifying the original runtime module objects.

## Registered links

- LinkSettings_View extends the shared Settings_Vtiger_Index_View directly and renders LinkSettingsPage.tpl with LinkSettings.tpl as its action-list partial. LinkSettings_Model uses the existing module getLinksForExport() API (initialized link objects without executing handlers), missing registerCustomLinks declarations from installed modules and runtime actions. Installation models are instantiated without executing their lifecycle. Core isCustomLinkDeletion() excludes delete: directives from default definitions; stored obsolete rows remain ordinary nondefault links until module setup removes them. Defaults match module/type/label, including cross-module declarations; code origin alone is not a default.
- Only DETAILVIEWBASIC, DETAILVIEWADVANCED, DETAILVIEW, LISTVIEWBASIC, LISTVIEWMASSACTION and LISTVIEW are visible. getLinkSections() produces two headings with three persistent responsive boxes each; no optional-section flags are needed. Removing an item updates only its group and the overall empty message, never removing a group. Widget, relation, navigation and settings types are excluded, as are parent=Settings routes and standard keyed/translated Edit, Delete, Duplicate, generic Add record and tag actions. Module-specific related-record creation remains visible. The same visibility rule protects direct deletion.
- getRuntimeLinks() resolves actual module DetailView/ListView classes with a clean record id 0 and calls their link providers without saving records or executing URLs. getModuleBasicLinks() adds module-header actions such as Import under LISTVIEWBASIC. Registered basic labels are not added again through the header provider; remaining runtime links are deduplicated by type/label/decoded URL. List mass actions retain their returned rendering group even when their internal type is LISTVIEW. Record query parameters become literal $RECORD$ placeholders. This record-independent preview respects current settings/permissions; existing-record-value conditions can differ on an actual detail screen.
- All installation defaults, missing declarations and runtime actions have can_delete=false and no dropdown. isDefaultLink() matches the selected module’s declarations by type/label in both getLinks() and the direct deletion guard. is_installed reflects a persisted linkid; defaults use green checks when installed and red checks when missing, with localized state tooltips. DeleteLink inherits Settings admin checks and requires POST/CSRF. The requested ID is looked up within the selected module; deletion delegates to the existing module deleteLink(type, label, URL) API. Identical registrations share that standard deletion key. getLinks() returns a read-only replacement if code or install declarations still provide the deleted action; otherwise AJAX removes the row. CRM records are never deleted, and no migration or automatic cleanup occurs.
- Both card headings and native closed metadata disclosures use the prepared translated title from getLinks(); never render the raw linklabel as the action heading. Link identifiers used for default matching and deletion remain unchanged. Default check icons precede translated names; Actions buttons are icon-only. Whitelisted metadata captions belong to Core in every locale, including existing Quick Create/full-form captions. getIconClass() allows plain class tokens or a strict i/span class wrapper with optional aria-hidden=true; unknown icon formats remain escaped text. URLs/handlers are never executed. AJAX replacement reuses prepared captions and icon_class.
- Validate PHP inheritance and syntax, locale parity, Smarty escaping, all supported module providers, project Quick Create/full-form metadata, six persistent boxes, excluded types/actions, administrator and CSRF checks, and AJAX deletion/replacement. LinkSettings.js exposes Settings_LayoutEditor_LinkSettings_Js. The unrelated LayoutEditor.js legacy class-name mismatch remains pre-existing.

- The Settings Module Manager menu declares LBL_LINK_SETTINGS and installs it through MenuItem::installLink() in migration 20261127143000. Its distinct LayoutEditor LinkSettings view is independent of the field editor tabs. LinkSettingsPage.tpl owns the heading and module selector; LinkSettings.js owns selection and deletion events, inherits only shared Vtiger components and keeps view=LinkSettings in the URL. Module selection requests contentsOnly=1, replaces only the action list, and disables selection/deletion during loading. The default is the first translated module in alphabetical order; explicit unsupported module names retain the model permission error. LayoutEditor Index no longer exposes or renders a link-settings tab. Shared labels remain in Core locales. The standalone view sets its persisted menu field/block before shared preprocessing, preventing the LayoutEditor module-name fallback from selecting the field editor entry.

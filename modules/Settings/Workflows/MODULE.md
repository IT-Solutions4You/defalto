# Workflow management

## Purpose and ownership

- This Settings module manages workflow definitions, conditions and task editors. Execution, scheduling, task classes and the task queue belong to `modules/com_vtiger_workflow` (see its MODULE.md).
- Definitions and tasks are persisted through the legacy workflow and task managers. Workflow management and execution are installed by `Install_InitSchema_Model`; there is no root installable module version.
- `workflowname` is the workflow name and `summary` its description; the legacy record model `getName()` returns `summary`. A task's `summary` is its user-supplied title; its task type provides the action label.
- `VTCalendarTask` is owned by Appointments. This module only supplies the shared task editor lifecycle and the language keys it uses.

## Language contract

- Every task type needs three identifiers in `languages/<locale>/Settings/Workflows.php`: the persisted task-type `label` (action selector and task list), `LBL_<tasktypename>` (workflow list summary) and `<tasktypename>` in `$jsLanguageStrings` (AJAX task rendering). Core and extension-owned task types (`VTCalendarTask`, `VTEMAILMakerMailTask`, `VTReadonly`) follow the same contract.
- Keep every full locale file that owns `Settings/Workflows.php` key-compatible with `en_us`.
- Comparator labels come from the `Settings:Workflows` translation scope supplied by the editor model; stored operator identifiers are never translated. `sk_sk` defines the full `Field_Model::getAdvancedFilterOptions()` map itself instead of inheriting Core labels.

## Condition editor

- `Settings_Workflows_FilterEditor_Model` extends `Core_FilterEditor_Model` and supplies workflow column identifiers, translated comparators, related-field restrictions, document field metadata and the empty-editor policy. `Settings_Workflows_Field_Model` owns the operator definitions per field type. Both Edit and EditAjax assign `FILTER_EDITOR`.
- Keep `COLUMNNAME_API=getWorkFlowFilterColumnName` assigned alongside `FILTER_EDITOR` in both Edit and EditAjax. Older or compiled workflow templates still read it; without it their option values fall back to saved-list column identifiers that do not match persisted workflow field names. When legacy options lack `data-condition-operators`, the workflow JS falls back to its own type/operator map, which keeps the related-field restrictions.
- Condition blocks for the source and referenced modules come from `Core_FilterEditor_Model::getConditionBlocks()`. Ordinary blocks keep their configured order and `LBL_ITEM_DETAILS` goes last; this is presentation only and does not affect field identifiers or execution.
- Workflow `AdvanceFilter.tpl` and `AdvanceFilterCondition.tpl` are compatibility includes. All group, row and button markup belongs to the shared Vtiger templates; do not copy design markup into workflow templates or branch on workflow module names in shared templates.
- `Workflows_AdvanceFilter_Js` inherits row/group creation, deletion and connector visibility from the shared editor. `loadConditions()` delegates per-field operator rendering to the parent and then applies the creation-trigger restrictions. Workflow serialization, expressions and specialized value renderers stay here. A new row starts with no field selected.
- `AdvanceFilter.tpl` renders only saved criteria. An empty group keeps Add Condition and the hidden `.basic` clone row but no visible placeholder. An empty comparison value is valid (for example `is added`) and is not a missing condition.
- Rows reuse the shared `.rowConditionConnector` visibility lifecycle. `getValues()` keeps each row connector and clears the last serialized row after omitting placeholders; save conversion uses the actual last column key because browser column indexes span groups.

### Operators

- Operator availability is defined per field type in `Settings_Workflows_Field_Model`. `has been set or changed` has no value input (`comparatorsWithNoValueBoxMap` in `AdvanceFilter.js`); the `to`/`from` variants require one. The set-or-changed variants are also defined for the text-like types `salutation`, `text`, `url`, `email` and `phone`, not only `string`.
- `FilterEditor::getOperators()` removes `has changed`, `has been set or changed` and its `to`/`from` variants for related-record fields. Their execution semantics are in `modules/com_vtiger_workflow/MODULE.md`.
- When the checked trigger radio is creation-only (1), the editor hides unselected `has changed`, `has changed to`, `has changed from` and `has been set or changed from`. Already selected incompatible comparators stay visible with a localized error and block modern-editor submission until corrected; saved criteria are never replaced or removed automatically. Trigger changes restore options without firing the comparator value-editor change handler, so target values and types survive. Restrictions are refreshed after AJAX condition loading and field changes. Legacy condition reuse keeps its own save flow.
- Picklist conditions map stored values to translated labels through `Vtiger_Field_Model::getPicklistValues()`. `Workflows_Picklist_Field_Js` inherits `AdvanceFilter_Picklist_Field_Js::getOptions()`/`setSelected()`: option values remain database keys while labels are localized, and `getValues()`, `Record_Model::transformAdvanceFilterToWorkFlowFilter()` and `SaveWorkflow` store the value untranslated. Unknown saved values are appended as selected options, so an already translated condition survives resaving and needs correcting. Do not infer stored values from visible labels.

## Condition persistence

- Modern conditions use `filtersavedinnew=6`; unsupported legacy expressions keep marker 5. Each row has an outgoing `joincondition` and each group an outgoing `groupjoin` to the next group; `groupid` may be any non-negative integer. The editor shows non-empty groups in encounter order as Group 1, Group 2 and so on, and saves group N as `groupid` N-1. Never sort groups by id: their order defines the expression.
- `Condition_Model::getEditableConditions()` preserves mixed AND/OR row connectors and outgoing group connectors, including legacy flat lists and null values. It rejects invalid operators, interleaved groups, inconsistent group connectors and empty placeholders, keeps order, values and value types, and is idempotent.
- Saving derives operators and group ids from the editor group containers. Empty groups do not produce a placeholder condition, so Any-only workflows stay executable.
- `Record_Model::isFilterSavedInNew()` normalizes compatible existing conditions in memory for editing; persistence happens only through the normal save flow. Unsupported conditions keep the legacy choice. Recreate shows blank criteria without selecting fields, and toggling back preserves the draft. Use existing conditions reads the persisted conditions on the server.
- The list summary (`Record_Model`) labels a condition All when its `groupid` is empty/0 and Any otherwise; it does not evaluate `groupjoin`.
- `Workflow_Model::migrateConditions()` restores legacy conditions from `registerWorkflowTasks` during module data migration. It matches by module and workflow name and skips duplicate definitions, duplicate stored matches, missing matches and unsupported defaults. Rows marked 6 with complete modern group metadata are kept (the marker alone does not prove the modern format). It updates only `test` and `filtersavedinnew`, using a conditional write against the values it read, so concurrent edits survive; repeated runs are idempotent and user workflows without a matching definition are untouched.

## Task editors

- Variable insertion is shared by `Edit.js`: `normalizeTemplateVariables()` converts inserted `$field` tokens to the PDFMaker-compatible `$field$` form in task text selectors and template-enabled value modals. `FieldExpressions.tpl` accepts `ENABLE_TEMPLATE_VARIABLES` and `RAW_TEXT_ONLY`; Update Fields, Create Entity and Calendar mappings enable variables, condition modals do not. Mapping controls without a native popup get the shared template trigger and are converted to the generic serializable popup input only on demand. `VTCalendarTask` reuses this lifecycle (subject and description use raw-text-only); see Appointments/MODULE.md for its task-specific behavior.
- `CreateEntity.tpl` passes the source workflow `MODULE_MODEL` to `VTCreateEntityTask::getFieldInfo()` for saved mappings, mandatory fields and newly added fields, so parent-owner options come from the source module while ordinary user/group choices stay those of the destination field.
- `TaskRecord_Model::isOwnerNameMapping()` identifies nonempty, nonnumeric literal owner mappings; `isParentOwnerField()` tells whether a value names an owner field of the source module, so the editor keeps that selection. `retrieveOwnerByName()` tries the exact user/group name first and then one HTML-decoded lookup, only when the name is unresolved and decoding changes it; it returns null for a missing owner and never modifies stored mappings.
- `EditV7Task` resolves literal create-record owner names to ids with that lookup. Numeric ids, expressions, field references and parent owner-field selections stay unchanged; a missing owner must not be dereferenced or reuse another mapping's owner. Keep this normalization at the workflow boundary and consistent with `VTCreateEntityTask`/`VTUpdateFieldsTask` in com_vtiger_workflow.
- `VTTrashTask` uses the standard task selector/editor and `Tasks/VTTrashTask.tpl`. The `deletionMode` select (`trash` default, `permanent`) is saved through the task's `getFieldNames()` contract. Labels and descriptions live in this module's language files; execution is in com_vtiger_workflow.
- Date handling in the editor: `Edit.js::loadFieldSpecificUi()` uses date display values only for `rawtext`. `Workflows_Date_Field_Js` shows expressions and field references from the serialized mapping value and assigns input values through the DOM. Never date-format expression source, and HTML-escape template input values so quoted expressions survive. `Workflows_Field_Js::getUiTypeSpecificHtml()` assigns `fieldname` and `expression` source through `.val()` after building the controls; literal `rawtext` keeps the renderer's formatting.
- `Workflows_Email_Field_Js` delegates control rendering to `Vtiger_Email_Field_Js` and calls the inherited `addValueTypeInput(html)`. That method reads `workflow_valuetype` from the field data, checks root and nested controls, adds a hidden `valuetype` only when missing, and defaults to `rawtext`. Popup save and task serialization depend on this input; without it field references and expressions are saved as `rawtext`. Other specialized renderers provide their own input.
- `history_task_id` deep links are handled by `Edit.js::showHistoryTask()` after the action container loads; only an existing task of the current workflow opens, once per editor instance, through the existing overlay handler and its V7 URL.

## Definitions, list and scheduling

- `models/Record.php::getEditViewUrl()` gives the base edit URL. The editor requires `mode=V7Edit` (appended by `ListViewContents.tpl`); without a mode the controller enters the legacy `step1()` flow. Any link to the editor must include this mode and the server must enforce Settings access.
- `actions/SaveWorkflow.php` recalculates the next trigger for recurring scheduled workflows through `Record_Model::updateNextTriggerTime()` and `VTWorkflowManager::updateNexTriggerTime()`. Editor calls pass no reference time, so hourly workflows get current time plus one hour; saving in the editor therefore resets the cadence that cron otherwise preserves.
- The name column shows the description (`summary`) below the name in `small text-secondary`; the list query selects `summary` separately and empty descriptions render no extra line. Description and creator values are escaped plain text; the description uses the existing list-length limit.
- The creator/time column is last, after Actions, in the header and every row. The query selects `createdtime` separately from the visible fields. `Record_Model::getDisplayValue()` shows the active administrator (`Users::getActiveAdminId()`) when the stored creator is empty, without changing stored data, formats the timestamp through `Vtiger_Datetime_UIType` in the current user's time zone and hour format, and shows an em dash for a missing timestamp.
- `Record_Model::createTables()` adds nullable `createdtime` and `creator` columns to `com_vtiger_workflows` through `Core_CreateTables_Config`. `Workflow_Model` inserts new definitions through `Core_DatabaseData_Model` with the database-time-zone instant and the authenticated user id (null without a user). Existing definitions keep null metadata, updates preserve both values, imports and copies get fresh metadata.

## Validation

- PHP lint, the ITS4You ScriptsValidator for touched JavaScript, and a real editor round trip: save, reopen and re-save with mixed AND/OR connectors, empty and sparse groups, picklist values in SK and EN, and all three value types (`rawtext`, `fieldname`, `expression`) including popup save and reload.
- Check normalization against the real `VTJsonCondition` evaluator, installation definitions, and old-template/new-controller combinations as well as the current shared template.

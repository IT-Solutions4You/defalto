# Workflow management

- Add-condition and add-group buttons share the saved-list editor's standard `btn btn-outline-secondary` size with inline flex alignment and `gap-2` for the plus icon. The add-group button explicitly uses `border`. Only individual condition groups have panel borders; the editor has no outer bordered wrapper. Never use `table table-bordered` on filter containers: table descendant rules override borders on nested controls.
- `AdvanceFilter.tpl` reuses the shared skin's `filterConditionContainer` header and row spacing and full-width controls. Condition rows use the saved-list editor's 4/3/flexible/auto column layout: the value fills remaining space and the delete button occupies only its own width. Keep this markup in `AdvanceFilterCondition.tpl` so saved rows and cloned rows match; workflow comparator and value-type contracts remain separate from list filters.

- The condition editor uses a wrapping flex header with a nonwrapping group title and `w-auto` small operator select. Group delete buttons use `btn-sm`, matching the shared dynamic-group renderer. Connector padding owns inter-group spacing; keep group bottom margins zero and the add-group button's top margin separate. Use Bootstrap utilities in the template rather than inline style overrides.

- `CreateEntity.tpl` passes the source workflow `MODULE_MODEL` to `VTCreateEntityTask::getFieldInfo()` for saved mappings, mandatory fields, and newly added fields. Parent owner options must come from the source module, while ordinary user/group choices remain those of the destination field.

- `VTTrashTask` uses the standard task selector/editor and `Tasks/VTTrashTask.tpl`. The `deletionMode` select is saved through the task getFieldNames contract and defaults to trash; permanent deletion is explicitly selected and described as non-restorable. Labels and explanations belong to Settings/Workflows language files. Task execution belongs to `modules/com_vtiger_workflow`; trigger selection and task filtering retain their existing behavior. Workflow execution/management have no root installable module version.

- This Settings module manages definitions executed by `modules/com_vtiger_workflow`; it is not the task execution owner.
- `actions/SaveWorkflow.php` recalculates the next trigger when saving recurring scheduled workflows through `Record_Model::updateNextTriggerTime()` and `VTWorkflowManager::updateNexTriggerTime()`. Editor calls omit the optional scheduling reference, so hourly creation and edits retain current time plus one hour. Cron execution supplies the previous planned trigger to preserve hourly cadence between runs; saving in the editor resets that cadence.
- `TaskRecord_Model::isOwnerNameMapping()` identifies nonempty, nonnumeric literal owner mappings for name lookup. Views delegate this reusable mapping check to the task model; `isParentOwnerField()` checks whether a value names an owner field in the source module so the editor can preserve that selection for task execution.
- `TaskRecord_Model::retrieveOwnerByName()` owns editor owner lookup: exact user/group name first, then one HTML-decoded lookup only when the original name is unresolved and decoding changes it. It returns null for a missing owner and does not modify stored mappings.
- `EditV7Task` resolves literal create-record owner names to IDs, trying the exact user/group name before a single HTML-decoded fallback for legacy mappings. Numeric IDs, expressions, field references, and parent owner-field selections stay unchanged. Missing owners must not be dereferenced or reuse another mapping's owner. Keep name normalization at the workflow boundary rather than changing global group/user lookup semantics.
- `models/Record.php::getEditViewUrl()` provides the base workflow edit URL. The current editor requires `mode=V7Edit`, as appended by `ListViewContents.tpl`; without a mode, the controller enters the legacy `step1()` flow. Audit UI links must include this mode and enforce Settings access on the server.
- Workflow definitions and task persistence use the legacy workflow manager and task manager. Execution entry points and save-event boundaries are documented in `modules/com_vtiger_workflow/MODULE.md`.
- Picklist condition metadata maps stored values to translated labels through `Vtiger_Field_Model::getPicklistValues()`. `Workflows_Picklist_Field_Js` inherits `AdvanceFilter_Picklist_Field_Js::getOptions()` and `setSelected()`: option values remain database keys, while labels are localized. `Workflows_AdvanceFilter_Js::getValues()` serializes the selected value; `Record_Model::transformAdvanceFilterToWorkFlowFilter()` and `SaveWorkflow` preserve it without translation. Unknown saved values are appended as selected options, so an already translated condition survives resaving and requires correction. Validate both canonical and already translated values through the real renderer and serializer in SK and EN; do not infer persistence values from visible labels or reverse-map ambiguous translations.
- Modern editor conditions use `groupid=0` for All and `groupid=1` for Any; `joincondition` connects rows and `groupjoin` connects groups. List display uses the same normalized groups as the editor, not `groupjoin`.
- Modern condition groups may use any non-negative `groupid`; each group has a homogeneous row join and its `groupjoin` connects it to the next group. The editor displays all non-empty groups sequentially as Group 1, Group 2, and so on.
- `Condition_Model::getEditableConditions()` normalizes homogeneous AND/OR groups joined by AND, including legacy flat lists and null values. It rejects mixed operators, interleaved groups, incompatible group merges, and empty condition placeholders. It preserves condition values and value types; normalization is idempotent.
- `Workflow_Model::migrateConditions()` restores legacy conditions from `registerWorkflowTasks` during module data migration. Match by both module and workflow name, and skip duplicate definitions, duplicate stored matches, missing matches, or unsupported defaults. Preserve rows marked 6 with complete modern group metadata; a marker alone does not prove modern format. Update only `test` and `filtersavedinnew`, using a conditional write against the previously read values to preserve concurrent edits. Repeated migration is idempotent; user workflows without matching definitions are untouched.
- `Record_Model::isFilterSavedInNew()` normalizes compatible existing conditions in memory for editing; persistence occurs only through the normal save flow. Unsupported conditions retain the legacy choice. Recreate reveals blank criteria without selecting fields automatically, and toggling back preserves the draft. Use existing conditions reads persisted conditions on the server.
- Saving editor groups derives operators and group IDs from the group containers. Empty All groups do not generate a false placeholder condition, so Any-only workflows remain executable. Validate normalization with the real `VTJsonCondition` evaluator, editor/save round trips, installation definitions, PHP lint, and the existing ScriptsValidator.
- `AdvanceFilter.tpl` renders only saved criteria in each visible condition list. Empty groups retain Add Condition and the hidden `.basic` row used for cloning, without creating a visible placeholder. An empty comparison value is valid for operators such as `is added` and must not be confused with a missing condition.
- `workflowname` is the workflow name and `summary` is its description; the legacy record model `getName()` returns `summary`. Task `summary` is its user-supplied title/description; its task type provides the action label.
- The workflow name column renders the description below the name using `small text-secondary`. The list query fetches `summary` separately from visible fields; empty descriptions render no extra line.
- The list template places the combined creator/time column last, after Actions, in both the header and each data row.
- The list's `creator` column displays the user label with `createdtime` below it; the list query selects the timestamp separately from visible fields. `Record_Model::getDisplayValue()` displays the active administrator from `Users::getActiveAdminId()` when the stored creator is missing or empty, without changing persisted provenance. It formats database timestamps through `Vtiger_Datetime_UIType` in the current user's time zone and hour format; missing timestamps display an em dash. Templates escape these display values as plain text; do not convert the stored timestamp before formatting it.
- The list renders `summary` as escaped plain text with the existing list-length limit. `Workflow_Model` owns new definition inserts through `Core_DatabaseData_Model`; `Record_Model::createTables()` adds nullable `createdtime` and `creator` columns through the existing `Core_CreateTables_Config` installation/update flow. Existing definitions retain null metadata. Creation records the current instant in the database time zone and the authenticated execution user's ID (null without a user); updates preserve both values, and imports/copies receive fresh metadata.
- `history_task_id` deep links are handled by `Edit.js::showHistoryTask()` after the action container loads. Only an existing task link in the current workflow can open, through the existing overlay handler and its V7 URL; the task opens once per editor instance.
- `resources/Edit.js::loadFieldSpecificUi()` uses date display values only for `rawtext`. `Workflows_Date_Field_Js` in `resources/AdvanceFilter.js` displays expressions and field references from their serialized mapping value and assigns input values through the DOM; never date-format expression source or prefer an empty display value over it. Template input values must be HTML-escaped to preserve quoted expressions.
- `Workflows_Email_Field_Js` extends `Workflows_Field_Js`, delegates email control rendering to `Vtiger_Email_Field_Js` with the same field data, and calls the inherited `this.addValueTypeInput(html)`. The base workflow renderer also uses this instance method, which reads `workflow_valuetype` from its own field data, checks root and nested controls, adds a hidden `valuetype` only when missing, and defaults to `rawtext`. Popup save and task serialization depend on this input; without it, field references and expressions become `rawtext`. Other specialized workflow renderers provide their own input. Ordinary record email fields remain unchanged. Verify popup save/reopen and serialized mapping reload for all three value types.
- `Workflows_Field_Js::getUiTypeSpecificHtml()` assigns `fieldname` and `expression` source through `.val()` after building field controls, preserving quotes and bypassing display formatting. Literal `rawtext` retains the field renderer's formatting. Workflow management and execution are system-installed by `Install_InitSchema_Model`, with no separate root module version.

- `has been set or changed` is a no-value workflow comparator, available for the same field types as `has changed` and excluded from related-record fields in the editor. It accepts an initial nonempty value (including zero/false) on creation and uses the same null-aware update detection as `has changed`. Scheduled query construction skips both operators. Stored operator identifiers are untranslated; labels belong to Settings/Workflows language files.

- The modern condition editor hides unselected `has changed`, `has changed to`, and `has changed from` options when the checked workflow trigger radio is creation-only (1). Selected incompatible comparators remain visible with a localized error and block modern-editor submission until corrected; never replace or remove saved criteria automatically. Trigger changes restore options without firing the comparator value-editor change handler, preserving target values and value types. Refresh restrictions after AJAX condition loading and field changes. Legacy condition reuse retains its existing save flow.

- `AdvanceFilter.tpl` translates comparator labels with `QUALIFIED_MODULE` (`Settings:Workflows`), not `MODULE` (`Workflows`). The resulting map serves both saved condition rows and JavaScript dropdowns; using the unqualified module misses Settings-owned translations.

- Slovak comparator labels are owned by `languages/sk_sk/Settings/Workflows.php`, covering the complete `Field_Model::getAdvancedFilterOptions()` map without inheriting untranslated Core labels. The set-or-changed label omits the word for value; keep the creation-only validation message consistent with its displayed name.

- `has been set or changed to` matches the current value on creation or a null-aware update; `has been set or changed from` requires an update and matches the old snapshot. They use `VTWorkflowEntity::hasFieldValue()` with decoded string comparison (numeric zero matches the editor literal "0"); an empty target matches null or empty string. Both require comparison inputs, are excluded for related fields and skipped by scheduled query construction. The from operator is unavailable for creation-only workflows. They accompany the corresponding legacy to/from operators in field metadata.

- Set-or-changed to/from comparators are also available for scalar text field types `salutation`, `text`, `url`, `email`, and `phone`; do not limit their metadata to the `string` type. Creation-only filtering still hides the from comparator.

# Core UI ownership

## Read-only records

- `Core_Readonly_Action::checkPermission()` is the authorization boundary for manual lock state changes. `makeEditable` and the workflow/schema `install` mode are administrator-only. `makeReadonly` is allowed to administrators or to the current record owner when `Users_Privileges_Model::isPermitted($module, 'EditView', $record)` succeeds.
- `Core_Readonly_Model::isMakeReadonlyPermitted()` owns the shared lock decision used by the action and `Vtiger_DetailView_Model`. For non-administrators it verifies that the record belongs to the requested module before checking edit permission and ownership. Direct URLs must never bypass this predicate.
- `updateReadonlyForUser()` revalidates the manual lock at the write boundary and includes `smownerid` in a non-administrator's UPDATE, so reassignment between the action check and the write cannot let the former owner lock the record. Workflow task `VTReadonly` remains on `setReadonly()` as an internal automation path without a manual acting user.

## External redirects

- `Core_Redirect_Model` owns Defalto external destinations and builds application redirect routes. UI links use the relative `index.php?module=Core&view=Redirect&mode=<mode>` route; generated content that leaves the application uses `getRedirectUrl($mode, true)` so recipients first reach the public CRM instance and then the centrally managed destination.
- `Core_Redirect_View` delegates destination lookup to the model. Do not hard-code Defalto, upstream vtiger, store, documentation, social, or release URLs in application UI or generated content.
- Shared user-facing confirmations and support guidance must not expose upstream vtiger service domains or contacts; keep those values aligned across Core locales.

## Recurrence generation

- `Core_RecurringType_Model` in `modules/Core/models/RecurringType.php` owns shared recurrence request parsing, occurrence generation, and the `getRecurringObjValue()` request factory and is loaded through `Vtiger_Loader`. Runtime callers should use the Core model directly. `Vtiger_Functions::getRecurringObjValue()` remains a delegating compatibility facade. `include/utils/RecurringType.php` contains only the legacy `RecurringType` subclass for old integrations that explicitly include the historical file; never load that facade globally from `CommonUtils`, because doing so creates a parent-class autoload cycle.

## Style Guide

- `Core_StyleGuide_View` is the administrator-only live UI catalog at `index.php?module=Core&view=StyleGuide`; it extends `Vtiger_Footer_View` so the complete application header, styles, scripts, and footer wrap the technical Core page.
- `layouts/d1/modules/Core/StyleGuide.tpl` renders Bootstrap and Defalto components with the application's currently loaded resources. Keep examples presentation-only: no database state, module setup, or page-specific JavaScript is required.

## Server-side JavaScript message translations

- `vJSTranslate($key, $moduleName)` prepends the current user's language and delegates to `Vtiger_Language_Handler::getJSTranslatedString($language, $key, $module)`. Preserve the language-first argument order so module names cannot be read as translation keys.

## Inventory item block templates

- `Core_InventoryItemsBlock_Model` owns product-block templates in `df_inventoryitems_block`; do not use the generic related-block table or model for their list, edit or delete lifecycle. EMAILMaker, PDFMaker, and PDFMaker Pro share this single store; their old module-specific product-block tables are legacy data and unused by the runtime editor.
- Management screens may be hosted by another module (for example EMAILMaker through `EMAILMaker_ProductBlocks_View`). In that flow the request `module` is the UI host and `source_module` is the inventory module persisted with the template. Module-hosted routes keep their normal permission checks and page lifecycle.
- Compatibility routes: `ProductBlocks` opens `Core_InventoryItemsBlock_View` in list mode; `EditProductBlock` maps legacy `tplid` links to the shared editor.
- Rows with an empty `module` are global and offered for every inventory module; module-specific rows stay restricted to their source module. Creating a template while the manager filter is All persists a global row; selecting an inventory module first creates a module-specific row. `Core_TemplateFields_Helper::getInventoryItemsBlockFields()` passes the selected module to `getAllOptions()`, so editors receive global rows plus that module's rows only.
- `createTables()` inserts the two global starter templates only when `df_inventoryitems_block` has no rows; never overwrite or append defaults to a populated table.
- Variables: `$IB_INVENTORYITEM_SEQUENCE$` is the physical document-line sequence. `$PS_ROW_NO$` counts only rows with a product/service and resets for each rendered block (`replaceRecords()`); `$PS_ROW_TYPE$` is `Products`, `Services` or `Text`.
- Settings exposes the manager in the Inventory block at `index.php?module=Core&view=ProductBlocks` (`LBL_PRODUCTBLOCKTPL`); menu registration remains owned by `Settings_Vtiger_MenuItem_Model`.
- The Core-hosted manager requires an administrator and uses the basic application page lifecycle (`Vtiger_Basic_View`), because Core is a framework owner, not a permission-bearing entity module. It supplies an explicit breadcrumb label and URL; the shared Topbar must tolerate technical modules without a `Vtiger_Module_Model`.

## Entity persistence encoding

- `PearDatabase::query_result()` and `query_result_rowdata()` return HTML-encoded values. `CRMEntity::retrieve_entity_info()` keeps that public contract while registering the raw database value in `TrackableObject::setRetrievedValue()` when encoding changed it.
- `TrackableObject::getValueForSave()` returns the raw value only while the field still exactly matches its originally retrieved encoded value; explicitly changed values take the normal conversion path. Entity-table writes and the always-updated `vtiger_crmentity.description` both use it. Keep this boundary so a retrieve-and-save cycle cannot convert characters to named HTML entities or double-encode data. `Users` follows the same contract (see `modules/Users/MODULE.md`).
- `CRMEntity::insertIntoEntityTable()` treats integer or string `0` from an empty entity-reference selector as an empty value for generic and legacy entity-reference uitypes. The existing column conversion then persists `NULL`, preventing optional foreign keys from rejecting the owning entity row. Do not apply this rule to non-entity references such as owners, currencies, or document folders, where zero may follow a different validation contract.

## Shared quick preview

- `layouts/d1/modules/Core/resources/QuickPreview.js` (`Vtiger_QuickPreview_Js`, per the Core resource naming convention) owns modal-scoped initialization and record actions. It extends Index to reuse navigation and inventory template events.
- Never load it globally: declare `modules.Core.resources.QuickPreview` last in `getQuickPreviewHeaderScripts()` (Vtiger Detail view; overrides such as `Products_RecordQuickPreview_View`). The preview process only assigns that script list.
- Vtiger launchers (`Vtiger.js`) own the request and call static `registerPreview(container, context, params, inventory)` from the modal callback after scripts execute; no inline registration in Smarty. One controller per modal lives in `quickPreviewController` data; static `getInstance()` retrieves it and static `deleteRecord(url)` dispatches its action. Full-page Detail has no QuickPreview dependency.
- Delete links keep the shared `Vtiger_Detail_Js.deleteRecord()` entry point (no preview flags or class switching in the DetailView link model). Core registers one delete handler (`hasRecord`, `onSuccess`, `onError`): Detail owns confirmation and the `ajaxDelete` request through the standard request/CSRF layer; success closes only the deleted preview and refreshes the source. Preview details keep the target module's Detail class with scoped container, form and record; field metadata is escaped JSON in a hidden control parsed into container data, never a global variable.
- On replacement or native `hidden.bs.modal`, dispose the controller, tooltips, handlers, script elements and field metadata, and remove only its matching window class. Native listeners are used because the legacy overlay helper's jQuery `unbind()` would remove jQuery ones. Pending deletion callbacks keep their captured source context but must never close a newer preview.
- Failed or malformed responses never replace the active preview; only the latest pending request can render. Navigation uses the source module's list session only on that module's List screen; reference and custom-screen previews do not reuse list navigation.
- After deletion, hosts may implement `onQuickPreviewRecordDeleted(params)`; standard lists use `loadListViewRecords()`; deleting the full-page record uses the returned list URL; unknown screens reload their current URL (no safe shared partial-refresh API).
- Validate cancellation, repeated clicks, failed loads/deletes, stale response order, repeated initialization, ordinary lists, cross-module references, custom host hooks and inventory template navigation with node syntax checks and the ITS4You ScriptsValidator. No schema or installable module version is involved.

## List filter toolbar

- `Core_ListFilter_Model` supplies permitted base-module field metadata. `ListFilter.tpl`, `resources/ListFilter.js` (`Vtiger_ListFilter_Js`) and `ListFilter.css` live under the Core layout; the Vtiger list controller loads them and delegates requests to its existing search pipeline.
- Field metadata is built from `Vtiger_FilterRecordStructure_Model`, the structure used by the saved-list editor, so base fields and one level of permitted reference fields share visibility, labels, operators, relation identifiers and saved-view columns. Reuse the `(parent ; (Module) field)` identifier and cloned field's `reference_fieldname`; do not expand relations recursively. `getFieldGroups()` groups metadata by module block (block order kept, empty groups omitted) into escaped `optgroup` labels; the flat map stays the JavaScript lookup contract.
- `isFilterField()` accepts display types 1, 2 and 3 (as `CustomView::getColumnsListbyBlock()`), so line-item-only (5), password (4) and starred/tag (6) fields are excluded while inventory totals (3) remain. Apply it before building flat or grouped metadata, including metadata reused when saving toolbar filters.
- Applied conditions are the original two positional `search_params` groups (AND, OR), separate from the dropdown's draft inputs. Never rebuild applied state from visible chips or collapse the OR group into AND. Money stays a string in the user's format; dates keep the user's calendar format with timezone handling left to the server query path; datetime quick filters use whole-day ranges.
- Layout: the toolbar sits beside the column picker in the first header cell; only the funnel icon (`fa-solid fa-filter`, translated tooltip and hidden label) and active count show there, everything else is in the dropdown. The count includes saved-view and temporary conditions; the dropdown names the saved view and explains that clearing additional filters preserves its conditions. The `listFilterSavedEdit` button (class and edit-URL data attribute are used by a delegated handler; pen icon, white background/dark text for contrast in the alert) appears only when the view is editable. Saved conditions stay outside the toolbar search state. After applying or removing a condition, reopen the refreshed dropdown. Use fixed Popper positioning to escape the scrolling table. Filter inputs belong to the separate `listFilterForm` outside `listedit`; never nest filter and inline-edit forms, including dynamically created inputs. Unsupported existing conditions stay visible and removable.
- Operators: the operator container starts hidden with a disabled select; `updateOperators()` syncs both with the selected field, including resets and editing an applied condition.
- Input widgets:
  - Selects use `vtUtils.showSelect2ElementView()` with full width and the field wrapper as dropdown parent; scoped CSS keeps results in normal flow. Destroy replaced widgets, refresh programmatic selections with `change.select2`, and stop mousedown propagation from Apply/Cancel to Select2's body close handler. Validation opens invalid Select2 controls instead of focusing hidden native selects.
  - Date and time inputs use `vtUtils.registerEventForDateFields()` / `registerEventForTimeFields()` with the user's formats and shared validation; Between uses the single-input range calendar (`data-calendar-type="range"`), and original user-format dates are sent without UTC conversion. Destroy replaced pickers, hide them when closing, and detect calendar clicks through `composedPath()` as well as target ancestry (month navigation detaches the clicked control before Bootstrap handles the click). Quick date inputs use `AdvanceFilter_Field_Js` and the saved editor's renderer (numeric day/hour offsets, relative period quantity/unit, ranges); `lastperiod` keeps its `quantity|unit` value through list conversion and saved-view read/write.
  - Reference fields use the shared text operators (contains, does-not-contain compare display names) and offer `Vtiger_Popup_Js` with allowed reference modules from metadata (Select2 module selector for polymorphic references). Reopen the editor from the popup's `hidden.bs.modal`, deferred until the click finishes, for both selection and cancellation; preserve inputs and edit index.
  - Currency lists use a single-value Select2 (option values are currency IDs with translated names; operators: equality, inequality, empty, not-empty). The `currency_id` branch of `EnhancedQueryGenerator` compares IDs and still accepts legacy names.
  - Owner metadata keeps translated Users/Groups sections in `valueGroups` (Select2 optgroups, empty sections omitted) plus the flat `values` map for chip labels and restoring selections. Names are HTML-decoded before becoming option values; queries compare names. Re-selecting an owner field resumes its single editable AND condition; multiple or OR conditions stay separately editable through chips.
- Validate add/edit/cancel/remove/clear, empty-value operators, multi-selection, date ranges, AJAX failures, paging/sorting/export and switching saved views; run JavaScript syntax checks and ScriptsValidator, and lint `modules/Core/models/ListFilter.php`.
- Labels: `LBL_GROUP`, `LBL_DELETE` (PHP and JavaScript dictionaries) and `LBL_CONDITION` (accessible connector label) exist in every Core locale. Static markup uses `vtranslate()`, dynamically added markup `app.vtranslate()`.
- Global search in the top bar is rendered by `layouts/d1/modules/Core/partials/TopbarSearch.tpl`, included by `partials/Topbar.tpl`. Module selection uses `Vtiger_BasicSearch_Js` (`layouts/d1/modules/Vtiger/resources/BasicSearch.js`); search configuration belongs to GlobalSearch. Picker styling lives in `layouts/d1/skins/base/style.less` and the committed `style.css`: keep the dropdown scrollable within the viewport, allow for the extra search row below the `lg` breakpoint, and use the shared header height variables.

## Module-specific filter objects and query conditions

- `Core_Filter_Model::getInstance($moduleName)` resolves `<Module>_Filter_Model` from `modules/<Module>/models/Filter.php` through the standard loader (falling back to Core), creates a separate object per call and invokes protected `initialize(): void` after setting the module. Subclasses must extend Core and keep method signatures. UI rendering and query execution create independent objects, so configure shared behavior in the subclass, not by mutating one factory instance. Both UI paths use the source/list module's object, including for related fields.
- `Core_FilterOperator_Model::getForField()` delegates operator presentation to that object's `getOperators(Vtiger_Field_Model $field): array`; `getDefaultForField()` holds the common defaults built from Vtiger field/type/date definitions (no toolbar allowlists). Overrides may restrict operators or call `setFieldOperators($name, $translatedOperatorMap)` in `initialize()`; settings are object-local and not persisted. Example:

```php
class Example_Filter_Model extends Core_Filter_Model
{
    protected function initialize(): void
    {
        $this->setFieldOperators('subject', ['e' => vtranslate('LBL_EQUALS')]);
    }
}
```

- For metadata-dependent rules override `getOperators()` and delegate to the parent; for value/operator transformations override `getQueryCondition()` and pass the transformed condition to the parent.
- `Core_QueryGenerator_Model::parseAdvFilterList()` calls `getQueryCondition(array $condition): array` for every quick and saved criterion, then delegates escaping and SQL construction to the inherited parser. It removes empty groups, clears the connector after each group's last column and after the last non-empty group, never infers a group from a fixed key, and wraps the whole filter in a group using the incoming glue so OR groups cannot escape surrounding deleted/access/search constraints. Never repair finished SQL strings. Verify sparse group keys, trailing empty groups, empty criteria and repeated parser calls with AND glue.
- `getQueryCondition()` contract: input has `columnname`, `comparator`, `value` (user display format) and `column_condition`; keep connectors, related-field identifiers, currency strings and symbolic periods; stay deterministic, idempotent and write-free; do no timezone conversion. An override may map a custom operator to an existing supported one; adding a label alone does not implement SQL semantics. Related-block filters pass stored connectors unchanged to this parser.
- Normalization in the base implementation: time values become `HH:mm:ss` wall-clock; standalone `T` / `bw` criteria (not Calendar `time_start`/`time_end`, which keep their timezone path) return an array of separately normalized endpoints that both query parsers and `getConditionValue()` accept, so comma-handling flags cannot collapse the range (never send a comma-separated range to `getTimeValueWithSeconds()`; reapplying must preserve the array); `DT` fields with `bw`/`custom` and date-only bounds get whole-day bounds; date-only fields, relative periods and currency strings stay unchanged.
- The shared list/popup factories, list export, MiniList, RecycleBin, Import and related-block/summary-widget lists instantiate the Core query generator; legacy generators stay unchanged.

# Record action permissions

- `Core_RecordActionPermission_Model` owns `df_record_action_permission`: one row allows or denies one action (`action`, optional `action_value`) on one record (`crmid`, `module`) for `scope_type` all/user/group/role (`scope_id`). `source`/`source_ref` identify the writer (`workflow` + task id, a module name such as `Approvals` + phase; edit locks and readonly are planned sources); `reason` is a language key or text; `expires_time` is server-time `Y-m-d H:i:s` or NULL. `createTables()` is idempotent, listed in `Core_CreateTables_Config`, and registers the workflow task types through `Core_RecordActionPermissionTask_Helper::registerTaskTypes()`. Until the table exists `isInstalled()` is false and every action is permitted.
- Decision: rules only narrow profile and sharing permissions. The most specific matching level decides (user > group > role > all); on the same level deny wins; expired rules and rules of another module are ignored; a record without rules keeps standard permissions. An allow rule only cancels a less specific deny, it never grants a profile right.
- Entry points: `Users_Privileges_Model::getPermission()` (behind `isPermitted()`) calls `isPermissionActionPermitted()` right after `Core_Readonly_Model`, before the admin shortcut. `PERMISSION_ACTIONS` maps `EditView` and `Save` (MassSave) to the edit rule and `Delete` to the delete rule; the module parameter of the check is ignored because `Vtiger_Save_Action` may pass `source_module`, and non-entity modules (`Users`) are skipped. UI, mass edit and webservice update/revise/delete share this path; administrators are restricted too. Workflows, cron and imports that save without a permission check are not restricted.
- Copies: `getCopyDenyReason()` checks `Duplicate` on the duplicated record and `Convert` on every source record when both modules are inventory modules. The source records come from `getCopySourceRecordIds()` (`COPY_SOURCE_PARAMETERS`: `sourceRecord`, `quote_id`, `salesorder_id`, `invoice_id`), used by `Vtiger_Edit_View::checkPermission()` (with `isDuplicate`, through `getEditDenyReason()`, which also checks `EditView` of an edited record) and `Vtiger_Save_Action::checkPermission()` (new records only, with `duplicateFrom`), because `InventoryItem_CopyOnCreate_Model` and `SalesOrder`/`Invoice::save_module()` copy items from them. `Vtiger_Module_Model::isDuplicateOptionAllowed()` hides a denied duplicate option. Document conversion links and the item review modal belong to `InventoryItem_Conversion_Model`: `getLinkUrl()` hides the links and `checkAccess()` refuses the modal and `ConversionSave` with the reason.
- Line items: InventoryItem actions check `EditView` of the parent (`InventoryItem_ParentEntity_Model::requireEditableParent()`), which goes through `getPermission()`, so an `EditView` rule on the document locks its items as well; there is no separate items action.
- `getRuleRecordIds()` loads the ids of records with rules once per request (`SELECT DISTINCT crmid`), so checks of other records (related lists, popups, widgets, lists without `preload()`) cost no query; rules are expected to be few. Rules of a record are cached per request; `preload()` loads several records in one query; every write clears the record cache. Write only through `saveRule()`, `deleteBySource()`, `deleteRule()`, `deleteModuleSourceRules()` (every rule of a source in a module, e.g. when an approval rule is switched off). A reason key is translated in the record module, then in the source module (when the source is an active module), then in Core; a source without `LBL_RECORD_ACTION_SOURCE_<source>` is shown by its module name.
- Detail: `Vtiger_Detail_View::preProcess()` assigns `RECORD_DENIED_ACTIONS` (current user, one entry per action/value) and `RECORD_ACTION_RULES` (administrators); `layouts/d1/modules/Core/RecordActionPermissions.tpl` renders them in `DetailViewHeader.tpl`. Administrators remove a rule (`rule_id`) or all rules of the record (`remove_all`, `deleteRecordRules()`, every source) through `Core_RecordActionPermission_Action` (POST, CSRF, admin only, record must belong to the request module); `layouts/d1/modules/Core/resources/RecordActionPermission.js` (`Vtiger_RecordActionPermission_Js`, loaded by the detail view) asks for confirmation first.
- Denied requests: `Core_Controller_Action::checkPermission()` throws the reason from `getPermissionDenyReason()` instead of the generic `LBL_PERMISSION_DENIED` when a record rule caused the denial (edit, inline edit, delete). A denied edit form (edit, duplicate, conversion by a direct URL) is shown in the page layout: `Vtiger_Edit_View::checkPermission()` keeps the reason and `process()` renders `Core/RecordActionDeniedPage.tpl` instead of the form (`Faq_Edit_View` checks `isRecordActionDenied()` itself). This applies only to `view=Edit` without `mode` (not `EditSharingRecord`, not Reporting `renderTable`) for users who may see the records (`isViewPermitted()`), and the profile and sharing checks of the parent still run through `runWithoutRules()` (the rule layer is skipped only for that call); ajax requests and other cases get the exception (plain error page). A full (not ajax) save denied by `getChangeDenyReason()` posts the submitted values back to the edit view (`RedirectToEditView.tpl`, `recordActionDenied=1`), which shows the reason above the form (`RECORD_ACTION_DENY_REASON`, `partials/EditViewContents.tpl`).
- Mass actions: `Vtiger_MassDelete_Action` and `Vtiger_MassSave_Action` preload the rules, skip denied records and return `message` (`getSkippedMessage()`, count + distinct reasons); `List.js` shows it as an alert. MassSave reports `true` when nothing was skipped.
- List rows: `Vtiger_List_View::initializeListViewContents()` preloads the rules of the page; `ListViewRecordActions.tpl` hides Edit/Delete of denied rows and `List.js` refuses the row inline edit with the reason (`.listViewEntriesEditDenied`).
- `FieldEdit` (`action_value` = field name, empty = every field) and `StatusChange` (`action_value` = `field=value`, `getStatusValue()`, decoded picklist value): `getChangeDenyReason()` compares the submitted fields of a record model with `CRMEntity::column_fields` (the values loaded from the database) and `getValuesDenyReason()` checks only changed values (numbers numerically, text decoded and trimmed). Called from `Vtiger_Save_Action::saveRecord()` (full save and SaveAjax, existing records; module actions overriding `saveRecord()` — Appointments, ModComments, PriceBooks, ProjectTask — are not covered), `Vtiger_MassSave_Action` and webservice `vtws_update()`/`vtws_revise()` (`getWebserviceDenyReason()`, references `NxM` compared by id). `applyLockedFields()` marks the locked field models of the record structure handed to the template (`record_action_locked` = reason, `ajaxeditable` = 0; structures do not always share the instances of `Vtiger_Module_Model::getFields()`) in `Vtiger_Detail_View` (header, detail, summary) and `Vtiger_Edit_View`; `blocks/Fields.tpl` renders them read-only without an input, so they are not submitted. Templates and `isAjaxEditable()` read the lock through `Vtiger_Field_Model::isRecordActionLocked()` / `getRecordActionLockedReason()`. Picklist fields get `record_action_denied_values` (`getDeniedStatusValues()`, value => reason, the stored value excluded) and `uitypes/Picklist.tpl` renders those options disabled with the reason as the title. For the inline edit `Vtiger_Field_Model::getFieldInfo()` passes them as `recordActionDeniedValues` and `Vtiger/resources/Field.js` disables them; because the inline edit reads the module field info (`uimeta`, built in `Vtiger_Index_View::preProcess()`) and the header fields use the module field instances, `Vtiger_Detail_View::applyLockedModuleFields()` marks the module fields of a record with value rules and assigns `FIELDS_INFO` again.
- `PdfExport`: PDF Maker (free and Pro, their own changes, guarded by `class_exists('Core_RecordActionPermission_Model')`) removes denied records in `PDFMaker_checkGenerate_Model::getExportableRecords()` (all denied → exception with the reason), covering export, ZIP and preview; `PDFMaker_CreatePDFFromTemplate_Action::checkRecords()` (called by the PDF Maker JS before the download or preview) returns `denied`/`message`, so the user sees the reason or the skipped records instead of an error page; PDFs attached to emails (`ITS4YouEmails_Record_Model::savePDF()` for the email's `related_to` record, not through checkGenerate) are handled by `ITS4YouEmails_MassSaveAjax_View::saveEmails()`: when `isPdfAttachmentPermitted()` refuses the related record, that email is saved without `pdf_template_ids` and the result shows `PDF_SKIPPED_MESSAGE` (`LBL_RECORD_ACTION_PDF_SKIPPED`); `getPdfAttachmentMessage()` lets `ITS4YouEmails_ComposeEmail_View::retrievePDFTemplates()` and `EMAILMaker_IndexAjax_View::showComposeEmailForm()` drop the PDF templates when the export of every source record is denied and announce the records without a PDF (`RECORD_ACTION_PDF_SKIPPED_MESSAGE`); `PDFMaker_GetPDFActions_View` and `EMAILMaker_GetEMAILActions_View` render `Core/RecordActionDeniedButton.tpl` (disabled button with the reason, same container id) for `mode=getButtons` and `Core/RecordActionDenied.tpl` otherwise. `EmailSend`: `ITS4YouEmails_ComposeEmail_View::checkSendableRecords()` stops composing when every source record is denied and `ITS4YouEmails_MassSaveAjax_View::getSendableRecords()` skips denied source records when sending; when none is left, nothing is saved and the result shows the reason. Skipped records are announced in the EMAILMaker address step (`SelectEmailFields.tpl`), the compose form (`ComposeEmailForm.tpl`) and the send result (`ModalSendEmailResult.tpl`, `SKIPPED_MESSAGE`). Workflow emails are not restricted.
- The rules table (`getActiveRules()`) shows an allow rule without its own reason as `LBL_RECORD_ACTION_EXCEPTION` (`getRuleReasonLabel()`); deny reasons fall back to `LBL_RECORD_ACTION_DENIED`.
- Workflow tasks `RestrictRecordActions` (actions, fields for `FieldEdit` and values for `StatusChange` shown only when the action is selected (`registerRestrictRecordActionsEvents()` in `Settings/Workflows/resources/Edit.js`), `field=value` options for `StatusChange` from `Core_RecordActionPermissionTask_Helper::getFieldOptions()`/`getStatusOptions()`, allow/deny, members `All`/`Users:id`/`Groups:id`/`Roles:id`, reason; replaces the rules of the same task; `getActionValues()` decides the rule values per action) and `ClearRecordActions` (removes workflow rules, optionally per action). `Settings_Workflows_TaskAjax_Action` stores any posted `<field>[]` multi-select as an array. The task names are also in `$jsLanguageStrings` of `Settings/Workflows`, because `Edit.js` writes the task type of a newly added task with `app.vtranslate()`.
- Not covered yet: merging duplicates (`Vtiger_ProcessDuplicates_Action`), Accounts/Contacts transfer ownership, `vtws_create` of SalesOrder/Invoice with `quote_id`/`salesorder_id` (Convert), EmailSend rules of recipient records (only source records are checked). Locked fields are also marked in the address block templates (`AddressEditField.tpl`, `AddressEditFieldPair.tpl`), quick preview and `Vtiger_Field_Model::isAjaxEditable()`.
- Custom actions: `isActionPermitted()` and `saveRule()` accept any action string, so modules can store and check their own actions; only `getActions()` are offered in the workflow task.
- Validate with lint, the class loader check, and a scenario covering user/group/role/all levels, allow vs deny, an administrator, webservice update/revise/delete, duplicate and quote conversion, mass edit/delete, locked fields in edit/inline/mass edit, status values, PDF export and email, the workflow tasks and the banner removal.

# Attachment storage

- `Core_Storage_Model` resolves and creates the attachment directory: `$storage_directory` (may be absolute; unset or empty falls back to `storage/`) plus a dated `<year>/<month>/week<N>/` subpath, created recursively. The upload operation validates the actual write because PHP `is_writable()` can reject valid Windows paths.
- `decideFilePath()` and `CRMEntity::getAttachmentUploadPath()` delegate to it, so every writer that calls `decideFilePath()` shares the configured root. `getAttachmentFilePath()` resolves both legacy relative and new absolute paths stored in `vtiger_attachments.path`; keep that value readable by existing download and preview flows.
- Reporting and other temporary generated files use `initTemporaryFileDirectory()` (`$tmp_dir`, default `cache/images/`), never persistent attachment storage.

# HTML line breaks and workflow installation

- `Core_SimpleHtmlDom_Helper::convertNewlinesToHtml()` preserves newline/indentation runs immediately before opening or closing `p` tags (also entity-encoded) and applies `nl2br` elsewhere. It never deletes existing `br` tags or wrappers and does not parse, sanitize or decode HTML. Used by the Text UI type and EMAILMaker textarea conversion.
- `convertParagraphBreaks()` separately removes plain `br` runs before opening/closing `p` and after closing `p` (including before closing `body`/`html` wrappers followed by a paragraph). It preserves interior paragraph breaks, other text breaks, wrappers/attributes, comments and `pre`/`textarea`/`script`/`style` content, and is idempotent. It runs only on final workflow email HTML (`ITS4YouEmails_Record_Model`, source `WF`); explicit blank lines adjacent to paragraphs are intentionally removed there.
- `Core_Install_Model::updateWorkflowTask()` saves module-provided condition arrays through `Settings_Workflows_Record_Model`; `VTWorkflowManager::save()` normalizes supported conditions into the modern editor format. `updateWorkflowTasks()` skips definitions already present by module and workflow name. Explicit data migration calls `migrateWorkflowConditions()` with the module's `registerWorkflowTasks`: uniquely matched legacy definitions are regenerated from module defaults, modern customizations stay unchanged.

# OAuth mail providers

- `Core_Auth_Model` owns OAuth for IMAP/SMTP. `getProviderNameByServer()` is the single server-to-provider rule (`gmail.com` to `Google`, `office365.com` to `Microsoft`): `getServerHost()` strips protocol prefix, port, path and trailing dot, and the host must equal the domain or end with `.<domain>` (`gmail.com.example.org` and `xgmail.com` do not match). `isOAuthServer()` is used by Mail Scanner `MailBox::connect()`; `ITS4YouEmails_Mailer_Model::getProviderByServer()` and `Core_Auth_Action::url()` use the provider rule. Do not add new `str_contains($server, ...)` checks (`MailManager` `Connector::connect()` still has a legacy `gmail.com` check).
- `getProviderInstance()` returns `League\OAuth2\Client\Provider\Google`, or for Microsoft a League `GenericProvider` with Entra v2.0 endpoints (no extra Composer package). Tenant: `$microsoft_oauth_tenant` in `config.inc.php` (tenant ID or domain, needed for single-tenant app registrations), default `common`. Scopes: `offline_access`, `https://outlook.office.com/IMAP.AccessAsUser.All`, `https://outlook.office.com/SMTP.Send`.
- The Microsoft redirect URI is `<site_URL>/auth.php` without a query string (register exactly this in the app registration); Google keeps `auth.php?provider=Google`. `auth.php` reads the provider from the session.
- Known limitation: refreshed access tokens are stored by `updateAccessToken()` (update by `client_id`/`client_secret`), but rotated Microsoft refresh tokens are not; the stored one stays valid until its lifetime ends, then authorize again.

# Template relations

- `Core_TemplateRelation_Model` owns `df_template_rel` (`id`, `record_id`, `module`, `related_record_id`, `related_module`, `sequence`; UNIQUE `module`+`record_id`+`related_module`+`related_record_id`; KEYs on `module`+`record_id` and `related_module`+`related_record_id`): ordered links from templates, which are not CRM records, to records of another module. It is used instead of `vtiger_crmentityrel`, which core code looks up by id without the module.
- Use instance methods on `getInstance()`; every method names both modules: `getRelatedIds()` (one query, `ORDER BY sequence, id`, result keyed by template record id), `saveRelated()` (replaces one related module of a template, `sequence` from 1), `deleteByRecord()`, `deleteByRelated()`, `deleteByModule()`, `isInstalled()`. Writes and deletes go through `Core_DatabaseData_Model`.
- `createTables()` is idempotent and listed in `Core_CreateTables_Config`, so a fresh install and the system update (`Install_Utils_Model::installTables()`) create the table; there is no migration file. Until then `isInstalled()` is false and nothing is related.
- Current user: EMAILMaker to PDFMaker templates (`EMAILMaker_PDFTemplate_Model`).

# Database data: IN conditions

- `Core_DatabaseData_Model` search arrays (`selectData()`, `selectResult()`, `deleteData()`, `updateData()` and their `get*Query()`): a non-array value (including null, object, bool) is `column=?`; an array is `column IN (?,...)` (`getSearchCondition()`, with `getSearchParams()` building parameters in the same order). An empty array throws an `Exception` before any query is built, so callers handle empty lists themselves (as `Core_TemplateRelation_Model` does). Scalar searches produce the former SQL and parameters. A search without any column keeps the former delete/update statement, which the database refuses; it never deletes all rows.

# Database table lifecycle

- Configure `Core_DatabaseTable_Model` through `getTable($table, $tableId)` before schema operations. `dropTable()` performs an idempotent `DROP TABLE IF EXISTS` and clears cached column metadata for that table; callers must pass a trusted table name owned by their install or migration flow.

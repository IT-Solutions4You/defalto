# Inventory item images

- `InventoryItem_GetItemDetails_Action` obtains product image URLs through `Core_Storage_Model::getAttachmentPublicUrl()`. Never expose `vtiger_attachments.path` as a browser URL because attachment storage may be outside the web directory.
- Product image metadata remains owned by `Products_Record_Model`; InventoryItem only prepares item data for inventory editors.

# Read-only unit price and hidden purchase cost

- The edit record structure leaves out fields the profile may only view. `InventoryItem_PopupItemEdit_View` adds `price` back when it is viewable (`PRICE_READONLY`); an existing item with a catalogue price above 0 (`decideItemPriceAndPriceBook()` with the parent record's currency and price book) is `PRICE_LOCKED`. `PopupItemEdit.tpl` marks the input (`data-price-readonly`, `readonly`) and hides the price book picker; `InventoryItemDetail.js` `mapResultsToFields()` locks the price for a catalogue price and leaves it editable for a price on request (0).
- `CRMEntity::insertIntoEntityTable()` writes only fields with `readonly = 0` for a non-admin. `InventoryItem_SaveFromPopup_Action::setReadOnlyPrices()` sets a non-editable `price` (catalogue price for a new item or a changed product, otherwise the stored one; a catalogue price of 0 keeps the entered price) and a non-editable `purchase_cost` (`getItemPurchaseCost()`, converted to the parent's currency like `GetItemDetails`), then sets `isWorkFlowFieldUpdate` so the entity saves them. A price sent from the browser for a locked item is ignored.
- The items block of the parent detail (`modifiers/DetailView.php`) only displays values, so its columns follow the view permission, not the edit structure.
- Known gap: `GetItemDetails` and the `SaveFromPopup` response still send the purchase cost and margin to users without permission to those fields.

# Parent record permissions

- Items are separate `InventoryItem` records whose own permissions know nothing about the parent document (read-only flag, sharing rules, profile). Every client entry point that changes items checks `EditView` of the parent through `InventoryItem_ParentEntity_Model::requireEditableParent()` in `checkPermission()`: `SaveFromPopup` (`source_record`), `SaveItemsBlockDetail` (`for_record`), `DeleteProductLine` and `SortLineItems` (parent of each item, resolved by `InventoryItem_Module_Model::fetchParentIds()`) and the `PopupItemEdit` view (`source_record`). A new entry point that writes items must do the same.
- An existing item sent with a request must belong to the parent record the request is authorized for (`requireItemsOfParent()`); an id that is not an item is refused.
- `SaveItemsBlockDetail` runs only the methods listed in `$allowedModes`; never dispatch the `mode` request value to an arbitrary method.
- `InventoryItem_DetailView_Modifier` assigns `ITEMS_EDITABLE` (`isParentEditable()`); `layouts/d1/modules/Core/blockuitypes/InventoryItem.tpl` renders `data-items-readonly` from it and `InventoryItemDetail.js` then hides or disables the editing controls. This is convenience only, the server check is authoritative.

# Items widget in the summary

- The summary widget (`InventoryItem_Widget_View::showItems`, `ItemsWidget.tpl`) is registered with `headerActions=1` in `InventoryItem_Install_Model::$registerSummaryWidgets`; `updateSummaryWidgets()` rewrites the stored link URL on install and module update. `Vtiger_DetailView_Model` sets `headerActionsModule` from it and the shared `SummaryViewWidget.tpl` includes `SummaryWidgetHeaderActions.tpl` of that module.
- The widget URL sets `summaryFirst=1`, so the shared detail model keeps it first in the right summary column without overwriting the persisted widget sequence. `ItemsWidget.tpl` limits the item rows to a scrollable area; its column header and total row remain sticky while the grand total and margin stay visible below it.
- `layouts/d1/modules/InventoryItem/SummaryWidgetHeaderActions.tpl` renders the "Add" menu (Text, then `InventoryItem_ItemModules_Model::getItemModules()`) only when `InventoryItem_ParentEntity_Model::isParentEditable()` allows it and not in the list quick preview (`LIST_PREVIEW`). It carries `getItemPopupValues()` (currency, price book, region, overall discount of the parent) as data attributes, because the popup code otherwise reads them from the items block.
- `InventoryItemDetail.js`: `showItemPopup()` opens `PopupItemEdit` for the block (add, edit, duplicate) and for the widget; `getParentRecordValue()` / `getOverallDiscount()` read the block inputs, otherwise the widget data attributes. Without the items block `reloadInventoryItemsBlock()` reloads only the items widget (`Vtiger_Detail_Js::loadWidget()`), so the user stays in the summary.

# Record action permissions (Convert)

- `InventoryItem_Conversion_Model` is the single owner of document conversion, so it applies the `Convert` record rule of `Core_RecordActionPermission_Model`: `getLinkUrl()` returns false (no conversion link in the detail of Quotes, Sales Orders, Invoices and Purchase Orders) and `checkAccess()` throws the deny reason (item review modal and `ConversionSave`). A plain create view with `quote_id` / `salesorder_id` / `invoice_id` is checked when the form is opened (`Vtiger_Edit_View`, reason shown in the page layout) and when it is saved (`Vtiger_Save_Action`) through `getCopyDenyReason()`.
- `requireEditableParent()` throws the reason of the record rule that denies editing the parent (`getPermissionDenyReason()`), otherwise `LBL_PERMISSION_DENIED`; `Core/blockuitypes/InventoryItem.tpl` renders the add buttons hidden when `ITEMS_EDITABLE` is false, so they do not depend on the JS.

# Discount permissions

- Item discounts follow the profile permissions of the InventoryItem fields `discount` (family: `discount_type`, `discount`, `discount_amount`, `price_after_discount`) and `overall_discount` (family: `overall_discount`, `overall_discount_amount`, `price_after_overall_discount`). The overall discount also requires the same field of the parent module. Predicates live in `InventoryItem_ParentEntity_Model`: `isDiscountViewable()`, `isDiscountEditable()`, `isOverallDiscountViewable($parentId)`, `isOverallDiscountEditable($parentId)`. A deactivated field counts as neither viewable nor editable.
- `SaveFromPopup` ignores request values for protected discount fields (and other non-editable fields while any are protected), keeps the stored values, lets new items inherit the parent's overall discount and sets `isWorkFlowFieldUpdate` so recalculated values are written. `SaveItemsBlockDetail::saveOverallDiscount` refuses without edit permission; its item saves and `ParentEntity::updateTotals()` also set `isWorkFlowFieldUpdate` because totals are system-calculated.
- UI: `PopupItemEdit` (view and tpl) and the `DetailView` modifier assign `DISCOUNT_VIEWABLE`, `DISCOUNT_EDITABLE`, `OVERALL_DISCOUNT_VIEWABLE` (`OVERALL_DISCOUNT_EDITABLE` in the block). Non-viewable fields stay in the DOM as hidden inputs (`HIDDEN_DISCOUNT_COLUMNS` in `LineItemsContent.tpl`) because the popup and block JS calculations read them. The server check is authoritative.

# Simplified product block

- `InventoryItem_Module_Model::isSimplifiedBlock()` reads the `simplified_block` setting from the key-value table `df_inventoryitem_settings` (created by `InventoryItem_Install_Model::installTables()` on install and update). Settings > Inventory Items > Product block saves it through `Settings_InventoryItem_BlockSave_Action` (ajax, `Vtiger_Response`; `Index.js` shows the success notification).
- `Core_InventoryItem_BlockUIType` switches the templates: `blockuitypes/InventoryItemSimplifiedEdit.tpl` for the edit view and `blockuitypes/InventoryItemSimplified.tpl` (read-only) for the detail view. `InventoryItem_DetailView_Modifier` then assigns only `SIMPLIFIED_*` variables, and the summary widget (`Widget::showItems`) renders `SimplifiedItemsWidget.tpl`; the Add menu (`SummaryWidgetHeaderActions.tpl`) is hidden.
- Rows are posted as `simplified_items[index][id|deleted|productid|item_text|quantity|unit|price]` together with the marker `simplifiedItemsPosted=1`. `InventoryItem_CopyOnCreate_Model::run()` (parent `save_module`) calls `InventoryItem_SimplifiedItems_Model::saveFromRequest()`, which creates, updates and deletes the items and runs `updateTotals()`. Without the marker (inline and ajax saves of the parent) items are never touched. A static re-entrancy guard stops the parent save inside `updateTotals()` from saving the rows again.
- Only the five fields are handled; other fields of an existing item (tax, discounts) keep their stored values, so row total shown = quantity x price.
- The edit view shows the same Text / Products / Services buttons as the standard block (`ITEM_MODULES` from `InventoryItem_ItemModules_Model`, hidden by `ITEMS_EDITABLE`, both assigned in `InventoryItem_EditView_Modifier`). A button adds a row with `data-module` set; rows of Products and Services get jQuery UI autocomplete against `InventoryItem_PopupBasicAjax_Action` and then `InventoryItem_GetItemDetails_Action`. `PopupBasicAjax` works without `base_record` for a document being created: it reads `base_module`, `currency_id` and `pricebookid` from the request. The selected record is stored in `productid` (validated in `InventoryItem_SimplifiedItems_Model::getValidProductId()`: it must be an active item module the user can read; a row without a valid product is a text row stored with quantity, price and tax 0). Text rows are full width (`colspan` = `SIMPLIFIED_COLUMNS`) and a product or service row must be selected from the list (client validation on submit).
- Client behaviour is in `layouts/d1/modules/InventoryItem/resources/SimplifiedEdit.js` (add/remove rows, autocomplete, totals with the user's number format). The unit and tax selects have the `select2` class and are initialised with `vtUtils.showSelect2ElementView()` (`registerSelect2()`, also for rows added in the browser; options changed by script need `trigger('change.select2')`). The server recalculates every row in `InventoryItem_Record_Model::recalculate()`.
- Taxes: `InventoryItem_SimplifiedItems_Model::getTaxes()` returns the active simple taxes of the settings; `assignCommon()` assigns `SIMPLIFIED_TAXES` and `SIMPLIFIED_COLUMNS` (5, or 6 with the Tax column). Rows post `tax` (percentage) and `taxid`; `saveRows()` accepts only taxes from the settings, sets `tax` before `recalculate()` (tax amount per row, the totals come from `updateTotals()`) and stores the tax id with `saveTaxId()`. A saved percentage without a tax record (older items) is kept. Without taxes in the settings the block has no Tax column and a single Total. In the browser `fillTaxes()` offers the taxes of the selected product (by `region_id` of the document) and the footer shows without VAT / VAT / with VAT.

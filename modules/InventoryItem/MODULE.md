# Inventory item images

- `InventoryItem_GetItemDetails_Action` obtains product image URLs through `Core_Storage_Model::getAttachmentPublicUrl()`. Never expose `vtiger_attachments.path` as a browser URL because attachment storage may be outside the web directory.
- Product image metadata remains owned by `Products_Record_Model`; InventoryItem only prepares item data for inventory editors.

# Item unit

- `df_inventoryitem.unit` stores the untranslated picklist value of the product (`usageunit`) or service (`service_usageunit`). Show it through `InventoryItem_Utils_Helper::getUnitLabel()`, which searches the translation in the module of the item first and then in the other one (`fetchItems()` exposes it as `unit_display`). `getUnitValue()` maps a displayed unit back to the stored value and is applied when the item popup is saved, so a translated text is never persisted; free text is kept as typed.

# Item conversion between documents

- `InventoryItem_CopyOnCreate_Model::run()` copies the items of the source record when the target record is created. It is the only place that copies items between documents; header fields are mapped by `Core_Base_Mapping`.
- `df_inventoryitem_conversions` (`InventoryItem_Conversion_Model`) holds one row per source -> target module pair: `enabled` (show the action; not shown or editable in Settings and stays on; a separate extension will take over the action links), `use_modal` (review items in the modal, default on) and `columns` (item fields editable in the modal; supported: `quantity`, `price`) and `header_fields` (simple editable fields of the target module shown in the modal; see `isSelectableHeaderField()`). The table is created by `Core_CreateTables_Config` and `InventoryItem_Install_Model::registerConversions()`; rows cascade-delete with `vtiger_tab`.
- Installable modules (for example a CreditNote extension) declare their conversions from their install model with `InventoryItem_Conversion_Model::registerConversion($source, $target, $options)` and remove them with `deregisterConversion()`. Registration never overwrites existing rows, so administrator choices survive updates. The standard pairs are listed in `InventoryItem_Install_Model::$defaultConversions`.
- The link decision is made while the detail view is built: `InventoryItem_Conversion_Model::getLinkUrl()` returns the plain create url (not registered or modal off), `false` (action disabled) or a `javascript:InventoryItem_Conversion_Js.showModal(...)` url. Standard detail view models use `InventoryItem_DetailView_Trait::getConversionLinkUrl()`; link handlers of extensions call `getLinkUrl()` directly.
- Modal flow: `InventoryItem_ConversionModal_View` (renders product rows with quantity/price formatted by the `InventoryItem_Utils_Helper::fetchDecimals()` precision like the item popup; text rows are not shown and are always copied; shows the configured `header_fields` plus every field accepted by `InventoryItem_Conversion_Model::isMandatoryModalField()`; loads the generic `Vtiger_Edit_Js` for the field events and validates with `vtValidate`) -> `InventoryItem_ConversionSave_Action` (extends `Vtiger_Save_Action`: checks access, validates that every row belongs to the source record and every number is valid, keeps the result in `$_SESSION['inventoryitem_conversion'][target][sourceRecord]`, builds the target record with `Core_Base_Mapping::mapFields()`, field defaults, the posted fields and a server-side mandatory check, saves it and returns the detail view url; the browser then navigates there). `CopyOnCreate` consumes the stored rows in the target save and the action clears them in `finally`. The target edit view is not opened, so there is no modifier or edit view flag. Without the modal (`use_modal` off) the link opens the normal create view with the full items copied.
- Rows removed in the modal are skipped, changed `quantity`/`price` are set before `InventoryItem_Record_Model::save()`, which recalculates the row, so tax and per-row discounts of the source apply. A `Direct` discount amount is copied unchanged and is read-only in the modal.
- Prices in the modal are in the currency of the source record, which is also copied to the target record.
- Administrators edit the conversions in Settings > InventoryItem > Conversions (`Settings_InventoryItem_ConversionsSave_Action` -> `InventoryItem_Conversion_Model::saveSettings()`, AJAX). Values of `header_fields` are rendered with the standard field templates, prefilled by `Core_Base_Mapping` like the target create view, and posted to `ConversionSave` which applies them to the new record.
- Migration `20261019120000` registers the standard conversions and creates the conversion and mapping tables (`createTables()` is idempotent and adds missing columns).
- `df_inventoryitem_conversion_mappings` (`InventoryItem_ConversionMapping_Model`, created by `Core_CreateTables_Config` and migration `20261019120000`, cascade-deleted with its conversion) holds `target_field <- source_field` rows per conversion; an empty `source_field` means the target field is not copied. `Core_Base_Mapping::mapFields()` asks `getConfiguredMapping()` first: fields with a configured row skip the automatic same-name copy, the relational-field step and the static `$mapping`, then configured rows are applied last. Fields without a row keep the standard behavior, so extension modules get the mapping without code. Calculated and currency fields (`InventoryItem_Conversion_Model::isCalculatedHeaderField()`) are never mapped. The administrator edits the rows in Settings > InventoryItem > Conversions > Field mapping (`Settings_InventoryItem_ConversionMapping_View`, `ConversionMappingSave_Action`); the same mapping prefills the header fields of the item review modal. The mapping is edited as source -> target; `InventoryItem_ConversionMapping_Model::isCompatibleField()` (groups from `getCompatibilityGroup()`: text, number, reference fields with a common module, otherwise the same data type; simple values may go to a text field) filters the target selects in the modal and drops incompatible rows in `saveConversionMapping()`.

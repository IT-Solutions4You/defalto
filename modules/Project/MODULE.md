# Project runtime ownership

- Project is a system module installed by `Project_Install_Model extends Core_Install_Model`; it has no separate `$moduleVersion`. Runtime and resource changes use the application versions in `version.php`.
- Summary columns include the authorized task status immediately before progress, after the task name when available. Its col, header and cells share data-summary-all-only so status tabs hide them together; the trailing status-edit action remains separate.
- `Project_Record_Model::getSummaryInfo()` supplies detail, quick preview and the Key Metrics widget with exactly four metrics in order: open tasks, stored project progress, overdue tasks and completed tasks. Priority counts are not part of this summary; task priority remains available in task rows and filters.
- Key Metrics card spacing uses Bootstrap row gutters so wrapped cards retain vertical separation without extra padding below the last row.
- Key Metrics uses compact content-height cards below Bootstrap's lg breakpoint; Summary.css overrides the ratio pseudo-element and child positioning only at these widths. Desktop cards retain their square ratio.
- Summary paging reveals authorized matching rows in batches using Vtiger_Paging_Model::getPageLimit(), shared with standard lists, through widget data-summary-page-size. Show More expands the active tab/filter result without requests; totals count all matches. Tab/filter changes and widget replacement reset the limit to the list page size. Namespaced delegated handlers prevent duplicate expansion after registration.
- Summary filters are client-side over already authorized rendered rows, with no extra record queries. Model filter definitions and option keys derive only from viewable fields, permitted task rows and resolved visible milestones; inaccessible milestones use the same no-milestone fallback as the table. Multi-select status/owner/milestone/priority values OR within a category and AND across categories and the selected status tab. Filtered counts ignore the active tab; zero-result tabs remain selectable. Persist only filter keys and ISO date bounds per browser/user/project, restoring options only if they still exist. Chips, reset and empty state synchronize after AJAX refresh. Date filtering uses inclusive overlap of validated ISO calendar boundaries without time-zone conversion; one missing bound uses the other, undated tasks are excluded by an active date range, and reversed input ranges match nothing. Filter dates use the system dateField input-group/calendar and vtUtils datepicker in the user date format. Strict moment calendar parsing converts display values to ISO storage/filter bounds and back without UTC conversion. Invalid input and reversed ranges expose native validity feedback; calendar min/max limits follow the opposite boundary. Initialize once per input, and process onClose so shared Today/Clear buttons update filters. Keep the filter dropdown open for clicks in the shared datepicker popup.
- Summary status tabs above the table show one status or All with task counts, using the grouped model data. The selected status uses app.storage keyed by user and project; restore it after initial registration, widget post-load and direct refresh, defaulting to Open, then In Progress when Open has no rows, then All when neither status has rows. Match raw status values from escaped tab data attributes, never translated labels. The activeStatusOpen storage namespace supersedes earlier defaults; subsequent saved selections take precedence. All alone shows an additional status column with each group label and color, only when the status field is visible. Keep aria-selected, roving tabindex, panel labelling and row visibility synchronized. Arrow keys, Home and End activate tabs. Old collapse preferences are no longer consumed.
- Summary date ranges omit the repeated year and, within one month, the repeated month, following the user's date component order/separator. Same-day ranges show one full date; different years show both full dates. Missing/hidden boundaries keep the existing placeholder behavior. Full authorized dates remain in the range tooltip. Compacting operates on validated ISO calendar parts without time-zone conversion and does not alter deadline or overdue calculations.
- Task progress uses a fixed 110px column with a 56px bar with the numeric percentage in a Bootstrap tooltip initialized idempotently by vtUtils.enableTooltips during tab restoration on initial load and widget refresh, or an em dash without a percentage tooltip when unset. Priority uses a fixed-width slot before the task link: a solid danger flag for high, an outlined secondary flag for low and an empty slot for normal. The authorized priority label remains in the tooltip and accessible label; picklist colors are not used for these priority flags. Keep field visibility restrictions. The task widget header contains its title and create actions, without project progress.
- Summary assignees render only an initials avatar with the full name in its title and accessible label. The narrower assignee column gives the task name more room; unassigned values retain their explicit placeholder.
- Summary presentation consumes the active Defalto skin's Bootstrap color variables and standard widget header/footer, small buttons and compact table classes. Status tabs identify each status with a colored dot and use a 2px theme-primary underline for the active state, without boxed borders, and horizontal scrolling when space is limited. Keep module CSS limited to the grouped table layout, progress geometry and interaction states; do not restore an independent fixed purple palette or uppercase table headings.
- The Project summary owns the standard side-column `TaskSummaryWidget.tpl` shell, `ProjectTaskSummaryWidgetContents.tpl` and view-loaded `Summary.css`. `Project_SummaryTask_Model` projects all viewable tasks with Core QueryGenerator independently of related-list columns/limits, applies record/field visibility and Core status locks, and batch-resolves accessible same-project milestone names. It groups by visible status in picklist order, with configured closed statuses last; counts cover exactly these visible records. The AJAX body renders the task table, status tabs, filters and paging button without header statistics. Do not duplicate queries or leave a separate summary table above the task table. The header never repeats the project name or project progress. The first column heading remains visibly empty. Task and milestone name links open the shared Vtiger_Index_Js.showQuickPreviewForId record preview through a namespaced delegate; modified clicks retain their detail URL. Links use the skin body text color, with underlined hover/focus; closed tasks remain muted. Date-only ranges retain user formatting; overdue day counts compare valid deadlines to the user's local today using calendar differences, excluding configured closed statuses. Task progress is read-only; the narrow trailing action cell owns the status menu and retains normal SaveAjax status editing; Status tabs and avatars initialize through namespaced Detail delegates and widget post-load events. The shell header owns module/permission/relation-derived create actions, while the AJAX body renders the task overview below it. Header buttons delegate to standard Quick Create with the project prefilled; the supported callback refreshes this task widget after saving either module, without an extra relation write. Unsupported Quick Create uses the standard relation full-form URL. There is no duplicate footer action. The separate milestone widget is suppressed without deleting records or related tabs.
- Widget shell URLs use the shared Link model's already HTML-escaped `getUrl()` contract. Do not escape that value again: `&amp;` would survive in the DOM data URL and turn `view`/`mode` into incorrect request names. Display labels and raw action URLs still need normal escaping. Summary requests use the existing Core Widget → Project Detail delegation. Keep the task widget in the normal sequence-based left/right columns; its compact table scrolls horizontally when the widget is narrow.
- `Project_Detail_View::showChart()` owns the Chart tab. `Project_Chart_Model` projects related ProjectTask and ProjectMilestone records through `Core_QueryGenerator_Model` and batch DetailView permission checks, preserving sharing rules and field visibility. CRM task and milestone tables remain owned by their respective modules.
- Task bars use the ProjectTask status field's picklist colors, with the legacy Project status-color map as a fallback. Milestone deadline diamonds can move; dated milestone ranges have a derived fixed start and an editable end. Record/date-field permissions still apply. Only records with valid calendar dates are charted.
- getTaskRange projects tasks missing either date as an inclusive one-day range at the visible valid project start. This is display-only until a normal task save. It runs before milestone derivation, hierarchy, filters and print. Complete ranges stay unchanged; invalid ranges or missing dates without an available project start remain in unscheduled for correction. Never feed incomplete dates to DHTMLX.
- The Unscheduled panel uses the standard ProjectTask Edit overlay and SaveAjax endpoint; successful saves refresh the Chart tab so classification is recomputed from persisted values. Initialize the adapter even without a timeline so the panel works when every task is unscheduled. Empty-state task creation uses the ProjectTask module's CreateView permission and preselects the current project.
- `Project_Chart_Js` in the Project layout resources owns chart startup, zoom, quick edit and date dragging. It uses the locally pinned DHTMLX Community build. `Project_Detail_Js::loadGanttChart()` detaches chart event handlers before reinitializing after tab refreshes.
- The chart is a standard `Vtiger.Class` object, registered by `Project_Detail_Js::loadGanttChart()` through `registerEvents(container, state)` on initial detail startup and Chart-tab AJAX completion. There is no chart-level document startup handler. Container ownership and idempotent destroy remove delegated DOM listeners, Gantt events, markers and shortcuts before replacement. `Project_ExportChart_Js` initializes the standalone print page with its own view-loaded resources.
- Each adapter owns a fresh `Gantt.getGanttInstance()`, not the global `window.gantt` singleton. Teardown calls the library's `destructor()` after detaching adapter listeners, so mouse/keyboard/plugin bindings and datastores cannot outlive the replaced DOM. A saved task must remain draggable after any number of refreshes; do not reuse a detached instance for the next chart.
- Project detail content uses ordinary `app.request.post`, not global PJAX. It retains the current content on failed/empty/malformed chart responses, ignores superseded requests, captures chart state before teardown and initializes the replacement before resolving the load promise. Chart save callbacks call their parent Detail loader directly without simulating a tab click or re-registering related-list handlers. Switching to another detail tab also destroys the previous chart.
- Toolbar, filters and unscheduled actions delegate through the main chart container. Project detail widget/recent-record handlers use scoped namespaces on the detail container; repeated initialization does not add handlers. Tasks, milestones and projects share standard module Edit overlays. Repeated open/save requests are guarded; late open responses are ignored after chart teardown. Overlay forms own escaped field metadata and use the module Edit controller and SaveAjax, then close and refresh this chart without record navigation.
- Composer owns `dhtmlx/gantt` 10.0.3 as a custom package pinned to the official npm tarball's SHA-1 and upstream commit. Detail/print controllers load `vendor/dhtmlx/gantt/codebase/dhtmlxgantt.js` and CSS. Do not restore the bundled layout copy. Use a targeted Composer update; unrelated locked dependencies must remain unchanged.
- CRM start/end dates are inclusive date-only strings. Convert them to local calendar dates without UTC parsing; add one calendar day for DHTMLX's exclusive task end, and subtract it before display or saving. Never calculate day counts by dividing timestamp differences.
- Dragging delegates date persistence to the existing `ProjectTask_SaveTask_Action`; form editing uses the standard ProjectTask Edit overlay and SaveAjax. Keep ProjectTask's record validation and save lifecycle intact.
- ProjectTask owns the linked-milestone deadline. A rejected drag/resize follows the standard error rollback; do not duplicate the rule only against visible chart parent rows, since a milestone can be hidden or filtered.
- New ProjectTask saves strictly enforce the visible or hidden project's inclusive planned range as well as the inclusive milestone deadline and same-project relation. Existing outside-range records still render warnings. The Project detail view loads ProjectTask Edit so the chart form uses the same asynchronous validator as full task editing.
- Moves preserve calendar duration; resizes preserve the opposite boundary and clamp to at least one calendar day. ProjectTask's record model validates optional calendar boundaries before saving; SaveTask delegates to normal Vtiger save validation, including record field/status rules. Chart editability also checks date-field locks. Pending task IDs prevent repeat dragging while independent tasks remain editable. A successful save refreshes only the Chart tab to reload canonical dates, statuses and colors; current filters are carried into the replacement adapter.
- Project bounds use visible `startdate` and planned `targetenddate`, never actual completion dates. Outside-range tasks are warnings; neither project dates nor milestones are rewritten. Search, assignee and status filters apply to grid/timeline and the unscheduled panel. The standalone print controller reads `chart_search`, `chart_owner`, `chart_status` as display filters and rechecks record access.
- `Project_Dependency_Model` owns `df_project_dependency` (`id`, `projectid`, `sourceid`, `targetid`, unique directed pair per project). `Project_Install_Model::installTables()` installs it through normal installation/system migration. Until installed, chart viewing remains available and link editing is disabled with an explanation.
- `Project_Dependency_Action` is POST/CSRF protected; both endpoints must be editable, visible records of the same supported module (ProjectTask or ProjectMilestone) in the editable parent project. Only finish-to-start links are supported. Self-links, duplicate directed links and cycles are checked before writing; a unique key also rejects duplicate directed edges. There are no advisory database locks. Cycle validation does not serialize simultaneous requests. Deleted/reassigned endpoints are excluded from the active graph. Never create schema from runtime requests. Task and milestone pairs reuse the same dependency table; mixed task/milestone pairs are rejected.
- Dates are inclusive, so a finish-to-start successor must start strictly after the predecessor's stored end date. Violations mark links and successors without rescheduling. Only links whose endpoints are visible and scheduled are emitted to the browser; hidden endpoints must never leak through link metadata.
- `Project_ExportChart_View` checks Project record access and renders the same chart data and adapter in a standalone, read-only print page. Both view controllers own their script and CSS lists; templates do not introduce dependency paths.
- The read-only project row uses explicit planned boundaries with `auto_types=false`; it must not roll up child dates. Visible dated milestones parent linked tasks through `milestoneid`; remaining tasks parent directly to the project. Keep native tree expansion but suppress folder/file icons. No separate context navigation card is rendered.
- Grid tree content vertically centers the name only; do not render secondary status/progress labels in the left table. Status colors and stored progress remain on timeline bars and in their tooltips. Keep text truncation and parent expand/collapse controls; suppress depth spacers.
- Task/project/milestone payloads distinguish `can_edit_record` from date-field `readonly`: double-click/Enter opens standard module `Edit` with `displayMode=overlay`; project bars never drag, while milestone deadline changes post to `ProjectMilestone_SaveDate_Action`. The adapter scopes the normal edit controller and reference events to the form, submits it through existing `SaveAjax`, and refreshes chart data after success. Backend Edit/SaveAjax recheck permissions and record rules; read-only records navigate to details. Milestone moves do not move their child tasks. No module persistence or validation is duplicated in the chart.
- `Project_ChartPreference_Model` owns `df_project_chart_preference`, uniquely keyed by project/user. The POST action always takes the current user, sanitizes settings and preserves scale, filters, scroll, selected task and table visibility. The table has fixed width and an icon toggle; no reset button, width control or print-scope selector is rendered. Print defaults to the current view, with its period, filters and generation timestamp.
- Progress uses stored task percentages, independent of status colors. Closed-status metadata belongs to ProjectTask. Today is computed in the user's time zone; calendar-cell shading highlights its current day/week/month and a marker identifies the exact date. Marker/event cleanup is required when replacing the adapter.
- The performance acceptance target is 1,000 tasks within three seconds in the agreed test environment. Data-only timing cannot establish browser/database end-to-end performance.
- Validation: `php -l` for changed PHP; `node --check` for `resources/Chart.js` and `resources/Detail.js`; manually inspect the expected `Project_Chart_Js` / `Project_Detail_Js` classes and the scripts validator when installed. Verify inclusive end dates across UTC, Europe/Bratislava, America/New_York and Pacific/Kiritimati, including DST boundaries. Live save checks require an authenticated CRM with database access.

- View preference writes are serialized per project across adapter replacements, with the latest pending state coalesced. Late record/dependency/date save callbacks may refresh only the same project. Task record editing is independent of date-field drag permission. Snapshot projections resolve real field column metadata, including assignees.
- The pinned MIT library has no marker API. The adapter owns the today marker DOM node in `$task_data`, repositions it after Gantt renders and removes it on teardown; never call addMarker/deleteMarker.

- Task progress_text is empty: retain stored progress as the visual bar fill, without percentage labels inside bars.

- Project range text uses the visible project name without a translated type prefix; retain the generic Project fallback when the name field is hidden. Search/assignee/status controls live at the start of the same wrapping toolbar as zoom, table toggle and print actions, preserving their selectors and root delegates.

- Toolbar filters use in-control placeholders/default options and decorative input-group icons instead of visible labels above controls. Keep translated aria-labels for search, assignee and status.

- The assignee filter consumes the shared Core AssigneeSelect component with ProjectTask-accessible users/groups. Persist owner IDs as a comma-separated string so legacy single-owner preferences remain valid; grid/timeline, unscheduled rows and print all use membership matching. Print omits interactive filters but retains the selected owner labels in its header.
- Fresh opens choose scale by the inclusive visible planned project range: up to 30 calendar days uses month/day, 31–56 uses month/week, and longer or unavailable/invalid bounds use year/month. UTC ordinals of local calendar parts avoid DST errors. This overrides persisted scale; live adapter state passed during refresh preserves an actively selected scale. Printing retains its explicitly selected scale. Dependency instructions are in the toolbar help dropdown rather than beneath the timeline. Project bar text uses flex centering within its bordered content box.

- When filters exclude the selected task, unselect it before rendering: the library can otherwise retain the selected row outside the filtered hierarchy. Numeric comma-separated owner lists are validated and deduplicated without the old single-field 500-character truncation.

- Milestone chart rows use the earliest valid viewable linked task start (including partial unscheduled tasks) and the effective deadline as inclusive end. Derive before display filtering so filters do not change the range. Use task type with is_milestone_range=true, not automatic roll-up; retain module-based hierarchy, filter context, deadline saves and same-module dependencies. Missing starts or reversed legacy ranges render a deadline diamond. Existing overruns remain visible with a warning.

- The help dropdown has separate milestone-range and dependency sections and is available to read-only chart viewers as well. Keep tree-name flex centering scoped to .gantt_cell_tree; applying it to every gantt_tree_content stacks inline date warnings and clips dates.
- Task name cells render the assigned owner initials in the shared 24px avatar before ProjectTask names in the interactive grid, using Vtiger_AssigneeSelect_Js.getInitials(). Unknown/hidden owners have no avatar. Keep it inside the escaped/truncated name span and aria-hidden; project/milestone names and print output retain their existing presentation.

- The grid has name/tree, start date and calendar-day count columns. Retain owner data for avatar tooltips, owner filters and print filter metadata; do not render a separate assignee column.

- getCalendarDayCount() counts inclusive start/end calendar days through UTC ordinals of local date parts, preserving 23/25-hour dates. Point milestones have zero duration; one-day task/range rows have one day. The day-count tooltip retains the full user-formatted range; end dates remain inclusive in CRM.
- grid_blank returns empty markup alongside grid_folder/grid_file. Remove the unused leaf expander slot and tree indentation while retaining parent expand/collapse controls.

- grid_indent is empty as well: leaf avatars start at the cell padding without depth spacers. Hierarchy remains in parent IDs and expand/collapse controls rather than indentation.

- Dependency reads UNION the owning task/milestone tables with active typed CRM entities, excluding deleted or reassigned endpoints. Milestone edges use the displayed derived start and inclusive deadline for warnings; they never reschedule tasks or milestones.
- A missing/zero milestone date falls back to the visible planned project end for chart/print projection without writing the milestone record. With no valid project end either, there is no dated timeline row.




- Warning payloads retain every visible violated predecessor and every visible task past a milestone deadline, with inclusive ISO boundary dates. No hidden endpoints are included. The adapter formats these using the user date format. Warning details appear only in a standard scrollable modal opened by a native warning button in the grid or bar. Each escaped cause has a translated corrective suggestion. Banner summaries and warning tooltip text are suppressed. Root click delegation uses capture to prevent grid selection/drag/edit from intercepting warning clicks; teardown must remove listeners with the same capture flag.

- Immutable iteration configuration is declared in typed protected static properties on its owning class: Dependency recordTables also gates supported endpoint modules, and ChartPreference separates numeric limits from text settings. Keep request-specific IDs/dates as runtime values.

- `Project_Install_Model::getBlocks()` owns the `assigned_user_id` field label `LBL_PROJECT_MANAGER`; module language files translate it as Project manager. Core installation/update applies the label to existing fields without changing assignment storage or permissions.

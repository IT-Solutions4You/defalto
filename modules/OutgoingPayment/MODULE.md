# OutgoingPayment

- Owner: `OutgoingPayment_Install_Model extends Core_PaymentInstall_Model` installs `df_outgoingpayment`, `df_outgoingpaymentcf`, `df_outgoingpayment_integration`, `df_outgoingpayment_associated` and `df_outgoingpayment_setting`, numbering `PAYOUT`, history, comments, the Settings link, the payment handlers and the integrations of document modules. `OutgoingPayment::$moduleVersion` controls install and update versioning. Installable extension in the SALES app.
- The payment logic is shared with IncomingPayment and lives in Core (`Core_Payment…`, see the Payments base section of `modules/Core/MODULE.md`). This module contributes `OutgoingPayment_Config_Helper` (tables, numbering, labels, Related To order Vendors → Accounts, paid field order `paid` → `received`, PurchaseOrder integrated by default without a status change), the entity `OutgoingPayment extends Core_PaymentEntity_Model`, its language files and empty subclasses whose names Defalto resolves by module or stores in the database.
- Statuses Created, Waiting, Pending and `Paid` are shared with IncomingPayment (one picklist `vtiger_payment_status`, also `vtiger_payment_method`); this module translates `Paid` as "Paid" (sk "Zaplatená"). Uninstalling one payment module keeps the picklists the other one uses.
- A document module should be active in one payment module only until refunds and the net paid amount exist (phase 6): both integrations write the same paid field.
- Validation: `index.php?module=OutgoingPayment&view=Install&mode=install`, then create a payment from a purchase order (quick and full form), check `paid`, `balance` and the unchanged status of the order, delete and restore the payment, save the integration settings and run the core cron `PaymentStatus`.
- The direction field `payment_direction`, the document widgets and the menu visibility are handled in Core (`Core_PaymentWidget_Model`, `Core_PaymentMenu_Model`, see `modules/Core/MODULE.md`, Payments base). With Payments active the widget `OutgoingPayment` on documents is replaced by the common widget `Payments`.
- Refunds and the net paid amount are handled in Core (`Core_PaymentDocumentBalance_Model`, integration column `is_refund`, see `modules/Core/MODULE.md`, Payments base). Language keys `LBL_ADD_REFUND`, `LBL_REFUND` here and `LBL_REFUND*`, `LBL_TWO_PAYING_MODULES` in the Settings language file.
- Sales order payments on invoices and Potentials as a document module are handled in Core (`Core_PaymentSourceDocument_Model`, `Core_PaymentConfig_Helper::ADDITIONAL_DOCUMENT_MODULES`, see `modules/Core/MODULE.md`). Language key `LBL_PAYMENTS_FROM_SOURCE`.
- Several documents per payment, the split of the amount and the bulk payment come from Core (`Core_PaymentAllocation_Model`, `Core_PaymentBulk_Model`, see `modules/Core/MODULE.md`); `actions/Save.php` is the thin `Core_PaymentSave_Action`. Language keys `LBL_BULK_PAYMENT*`, `LBL_PAY_OFF`, `LBL_OPEN_AMOUNT`, `LBL_NOT_SPLIT`, JS keys `JS_PAYMENT_SPLIT*`; the list action label is in `Core.php`. The texts `LBL_SEVERAL_DOCUMENTS_PREMIUM` and `LBL_PREMIUM_MODAL_*` are prepared for a later paid edition and unused now.

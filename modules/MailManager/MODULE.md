# MailManager Module

## Purpose and Ownership

- Core module (registered in `Install_Utils_Model::$registerModules`, menu app `TOOLS`). It has no `$moduleVersion`; runtime changes bump only `version.php`.
- Personal IMAP mail client: one active account per user in `vtiger_mail_accounts` (`status = 1 AND set_default = 0`), owned by `MailManager_Mailbox_Model`. Passwords are stored with `include/utils/encryption.php` through `MailManager_Mailbox_Model::encrypt()/decrypt()`; the settings form renders `getPasswordPlaceholder()` and never the decrypted password.
- Sending, reply and forward are owned by ITS4YouEmails (`ITS4YouEmails_Record_Model::send()`); MailManager only opens its composer and links mails to CRM records through ITS4YouEmails records (`its4you_emails.mail_message_key = md5(Message-ID)`).

## Editions (Basic and Pro)

- `MailManager_Module_Model::isProEnabled()` is the single edition switch: Pro is available only while `Installer_License_Model::isMembershipActive()` is true. It reads the stored license state only; never call Installer license checks or read `df_licenses` elsewhere in MailManager.
- Appointments from a mail (I05): `MailManager_Appointment_Helper` is shared by Basic and Pro — `getReferenceValues()` (Accounts → `account_id`; Contacts → `contact_id` + its `account_id`; other modules → `parent_id` when its reference list accepts them) and `relate()` (fills empty references after the save; Pro `ProRelateActivity` uses it). Basic offers Appointments in `MailManager_Relation_View::linkToAvailableActions()`; `create_wizard` prefills the QuickCreate, `createAppointment()` saves through `Appointments_Save_Action::saveRecord()` (date/time/time zone, invitees, recurrence) and then associates the mail like any created record.
- `MailManager_List_View` delegates the root page (no `_operation`) to `MailManager_ProIndex_View` when Pro is enabled (`isProRootRequest()`); the URL stays `view=List`. Basic AJAX operations are never delegated. Without Membership every Basic code path runs unchanged.
- Pro controllers extend `MailManager_ProAbstract_View` / `MailManager_ProAbstract_Action`; their `checkPermission()` throws `LBL_PRO_MEMBERSHIP_REQUIRED` without Membership. Pro templates live in `layouts/d1/modules/MailManager/Pro/`, Pro scripts and styles in `resources/Pro*.js|css`.

## Pro Schema and Lifecycle

- Pro tables `df_mailmanager_*` are defined only in `MailManager_Install_Model::getProTableDefinitions()` and created by `installProTables()` (idempotent, `Core_DatabaseTable_Model`). `df_mailmanager_config` is the marker table and is created last; `isProSchemaInstalled()` checks it.
- A Basic installation never gets Pro tables: `installTables()` (run on every system update) calls `installProTables()` only when the Pro schema already exists, which also delivers later Pro schema changes to expired installations.
- `initializePro()` (first Pro start, from `MailManager_ProIndex_View::preProcess()` while `isProInitialized()` is false) runs under the MySQL lock `df_mailmanager_initialize`, creates the tables, seeds the default labels into an empty `df_mailmanager_label` and registers the `MailManagerProSync` cron (`$registerProCron`, `modules/MailManager/cron/ProSync.php`, every 15 minutes) and writes the config row `pro_initialized_at` last. The cron returns immediately without Membership or when the module is disabled; Pro data is never deleted on expiry.
- `installProTables()` re-applies every column definition (`ALTER TABLE … CHANGE`) on each system update; keep definitions stable and watch migration time on large mail stores.
- Pro settings are stored through `MailManager_ProConfig_Model` (`getValue()`, `saveValue()`).

## Pro Mail Engine (transport)

- `MailManager_ProTransport_Model::getForMailbox()` builds the driver from a `df_mailmanager_mailbox` row (secrets decrypted with `Encryption`). Providers `imap` (password `LOGIN`), `google` and `office365` (IMAP `AUTHENTICATE XOAUTH2` with `oauth_access_token`) all use `MailManager_ProImapTransport_Helper`; Gmail REST / Microsoft Graph drivers are not ported. The provider of a personal mailbox follows its Basic account (`MailManager_ProTransport_Model::getProviderForAccount()` → `Core_Auth_Model::getProviderNameByServer()`, X02).
- `MailManager_ProImapClient_Helper` is a socket IMAP client (SSL/STARTTLS, optional pinned certificate fingerprint, CONDSTORE). Read paths use `EXAMINE` and `BODY.PEEK`, so syncing never changes `\Seen`.
- `MailManager_ProMimeParser_Helper::parse()` returns `sent_at` in UTC and `getMessageKey()` returns the same `mail_message_key` as Basic (md5 of the Message-ID without brackets).
- `MailManager_ProHostGuard_Model::isAllowed()` limits non-admin users to public hosts and mail ports; hosts that do not resolve are refused.

## Pro Sync (local mail store)

- `MailManager_ProSync_Model::run()` (cron `MailManagerProSync`, `modules/MailManager/cron/ProSync.php`) syncs every due mailbox from `MailManager_ProMailbox_Model::getSyncMailboxes()`: folder list reconcile (`MailManager_ProFolder_Model::reconcile()`, new folders start with `sync_enabled = 0`), incremental import of folders with `sync_enabled = 1` (cursor `uidvalidity:lastUid`, first import limited by `sync_from`), read state and deletions from the server, threading by Message-ID / In-Reply-To / References. One named MySQL lock per mailbox (`df_mm_sync_*`) keeps the cron and on-demand syncs apart.
- Run budget (1.10.61): `ProSync::RUN_BUDGET` = 300 s (was 120; the task runs every 900 s, `STALE_CRON_SECONDS` 1800 and the scheduler lock do not depend on it). The mailboxes and the AI triage stop `DIGEST_RESERVE` = 60 s (at most a quarter of the run) before its end, so the digest lines (`ProWorkspaceDigestAi::prepareLines()`) always get time — an initial sync of new mailboxes plus a triage backlog took the whole 120 s at a customer (2026-10-21) and the Summary kept "line is being prepared". Reserve chosen over moving the digest before the triage: the lines are written from the triaged state of new mail, so they follow the triage. Topics and knowledge get no reserve (backlog work nobody waits for; they catch up on quiet runs). `MailManagerProScheduled` runs after `MailManagerProSync` in the same `cron.php` process, so in a run with a full sync it starts up to about 3 minutes later than before.
- Personal mailboxes linked to a Basic account (`account_id`) get server, user, encrypted password and Google token from `vtiger_mail_accounts` through `MailManager_ProMailbox_Model::getTransportRow()` on every connection; the Basic account must belong to `owner_userid` (`MailManager_Mailbox_Model::getAccountId()`).
- A failed mailbox sync stores `last_error`, increments `failed_attempts` and waits (`next_retry_at`, 5 minutes doubling up to 6 hours); a successful sync clears it.
- Every stored message gets `mail_message_key` (same as Basic). Not yet ported (later tasks): spam-sender filtering, conversation state, CRM comment log, auto-link, filing as ITS4YouEmails records and the AI stages.
- Trace file: `logs/mailmanager_pro_cron.log` (rotated at 200 kB); cron state rows `cron_stage`, `cron_last_ok`, `cron_last_error` in `df_mailmanager_config`.

## Pro Mailboxes, Sharing and Labels

- Basic account take-over: `MailManager_ProMailbox_Model::linkBasicAccounts()` runs in `initializePro()` for all active users and `linkBasicAccount()` on every Pro page visit for the current user. It creates one personal mailbox per Basic account (`account_id`, provider `google` for OAuth accounts, `smtp_mode = crm`, `sync_from` = `sync_from_days` config, default 90), disables it when the Basic account is gone and re-activates it when the account returns. Nothing is deleted. The first folder list of such a mailbox syncs INBOX and Sent (`MailManager_ProFolder_Model::DEFAULT_SYNC_TYPES`).
- Known limits: Pro always validates TLS certificates (a Basic account set to `novalidate-cert` with a self-signed server needs a trusted fingerprint in Pro); `SET NAMES utf8mb4` from `MailManager_ProInbox_Model::useUtf8mb4()` stays on the connection of the cron run.
- Admin mailbox management lives in `Settings_MailManager_Mailbox_Model` (create from the wizard, update, delete with all cached data). Release 1 creates IMAP mailboxes only; custom SMTP hosts pass `MailManager_ProHostGuard_Model` on every save; passwords are stored with `Encryption`.
- `MailManager_ProSharing_Model::accessCondition()` is the SQL condition for mailboxes a user may open (owner or a user member of `df_mailmanager_mailbox_access`, honoring `valid_until`). Group members are stored but not yet evaluated by this condition.
- Labels: `Settings_MailManager_Label_Model` (global, personal and per-user overrides); default labels are seeded by `initializePro()`. Labels of these models live in `languages/<locale>/Settings/MailManager.php`.

## Pro UI, Sending, CRM, AI and Settings

- UI: `MailManager_ProIndex_View` (rendered under `view=List`), `MailManager_ProIndexAjax_View` (modes threadList, conversation, crmPanel, composer, mySettings), `MailManager_ProAttachment_View`; templates `layouts/d1/modules/MailManager/Pro/`, JS `resources/ProIndex.js` composed from `window.MailManager_Pro*_Mixin` objects loaded by `ProIndex::getHeaderScripts()`. Pro JS reloads the page once when an AJAX call fails with `LBL_PRO_MEMBERSHIP_REQUIRED`.
- Sending (`MailManager_ProOutbox_Model`): an ITS4YouEmails record is built and sent with `ITS4YouEmails_Record_Model::send()`; flags `skip_save_email_to_sent_folder`, `skip_in_reply_to` and, for `smtp_mode = custom`, `skip_smtp_retrieval` with `setSMTP()`. The flags need the ITS4YouEmails hooks H1/H2 (handoff X01); until they exist, ITS4YouEmails still adds its own In-Reply-To and uses its own SMTP selection. The raw MIME is appended to the mailbox Sent folder, the original gets `\Answered`. Custom SMTP hosts are checked by `MailManager_ProHostGuard_Model` when the mailbox settings are saved (not on send, so an internal server set by the administrator works for all members).
- CRM: incoming mail of linked conversations is filed by `MailManager_ProEmailFiler_Model` as ITS4YouEmails records (`mail_message_key`, `relateEntities()`, reuses Basic's record with the same key); `MailManager_ProRelate_Model` keeps `df_mailmanager_rel`; Documents via `Core_Attachment_Model`; activities use Appointments. The record widget of the original extension is not part of Defalto.
- AI (`MailManager_ProAiConfig_Model`, providers in `helpers/ProAi*`): off until an administrator enables it with an own key (stored with `Encryption`); requires Membership only. Cron stages: triage, topics, knowledge.
- Settings: `Settings_MailManager_*` (Index, Edit/mailbox wizard, Detail, AISettings, SetupWizard, PurgeData). The setup wizard banner shows for administrators while `Settings_MailManager_SetupWizard_Model::isSetupPending()`. `PurgeData` deletes stored Pro mail and works without Membership on installations with the Pro schema. `MailManager_Module_Model::getSettingLinks()` adds the Pro / stored-data links.
- Basic shows a draft "Pro" button (`ModuleSidebar.tpl`, `resources/ProButton.js`) without Membership that opens the Installer premium modal with `LBL_PREMIUM_MODAL_SUBTITLE` and `LBL_PREMIUM_MODAL_ITEM_1..4`.
- Without Membership the Pro page views (`MailManager_ProAbstract_View`, `ProAddMailbox`, `Settings_MailManager_ProAbstract_View`, `AISettings`) call `MailManager_ProRequired_View::requirePro()`: a page load redirects to `view=ProRequired` (Settings for the admin pages, the module for My settings / Add mailbox; data `MailManager_ProRequired_Model`, template `ProRequired.tpl`), an AJAX call keeps the `LBL_PRO_MEMBERSHIP_REQUIRED` error. Pro actions are unchanged.
- The reply subject of Basic ("Re:" without a space, also before an existing "Re:") is built by ITS4YouEmails `ComposeEmail::retrieveEmailInfoFromMailManager()` — outside this module.

## Layering (I18a)

- Views and actions of the module and of `Settings/MailManager` only read and validate the request, check access (accessible mailbox, thread of the mailbox, `isPermitted`), call model methods and assign the result or emit it with `Vtiger_Response`. SQL, merging, sorting, filtering and domain decisions live in models; a model never reads `Vtiger_Request` and never returns a `Vtiger_Response`. `session_write_close()` stays in the action.
- Page data comes from `getViewData()`-style methods returning template variables: `MailManager_ProConversation_Model`, `MailManager_ProCrmPanel_Model`, `MailManager_ProComposer_Model`, `MailManager_ProInbox_Model::getIndexViewData()`, `MailManager_ProAiSettings_Model::getSettingsViewData()`, `Settings_MailManager_WizardView_Model::getViewData()` (request values as an array).
- User actions run as one model call returning the response array: `MailManager_ProServerMove_Model::moveThread()` / `deleteThread()`, `MailManager_ProThreadUpdate_Model::updateThread()` / `updateThreads()`, `MailManager_ProSync_Model::syncNow()`, `MailManager_ProTicketClose_Model::closeTicket()`, `MailManager_ProAiSettings_Model::saveSettings()` / `verifyApiKey()`, `Settings_MailManager_Wizard_Model::testImap()` / `testSmtp()` / `saveMailbox()`.
- Basic: `MailManager_Relate_Model` holds the mail linking (`MailManager_Relate_Action` only extends it for callers such as the HelpDesk handler), `MailManager_Upload_Model` the composer document upload, `MailManager_EmailFields_Model` the e-mail fields of the compose dialog.
- Behaviour checks of a refactor: render the views and run the actions with the old and the new classes against the same database inside a rolled-back transaction (fake IMAP transport) and compare the output byte for byte.

## Restore and unsynced folders

- Mail we move into a folder the sync does not scan (`sync_enabled = 0`: Trash, Spam, archives) loses its UID until that folder is loaded. `MailManager_ProServerMove_Model::adoptUnsyncedMail()` loads such folders of the thread (`syncFolderOnDemand()`, the same load as opening the folder) before `moveThread()` and `deleteThread()`; a failed load leaves the mail waiting (`LBL_MOVE_PENDING_SYNC`).
- Restore (`target=restore`) moves our own mail (`direction = out` or a draft) to the Sent folder its last move or delete took it from (`MailManager_ProHistory_Model::getLastSourcePaths()`), otherwise to the mailbox's Sent folder; received mail goes to the Inbox. The cache follows per UID (`MailManager_ProThread_Model::moveMessagesCache()`). A refused restore returns the conversation to the list in JS (`returnFailedThread()`).
- The composer is a custom overlay (z-index 9000), above the core z-index counter (`app.helper.getZIndex()` from 1051). Its errors show inside it (`showComposerError()` / `clearComposerError()`, the `.its4you-composer-error` bar of the sticky toolbar, `.its4you-composer-invalid` rows); `ProIndex.css` lifts core modals, bootbox confirmations and their backdrop (`body:has(> .its4you-composer-overlay:not(.hide))`) and notifications above it. Other windows of the module are Bootstrap modals of the core helper — notifications already show above them.
- PHP messages use `vtranslate()` with `LBL_` keys from `$languageStrings`; `vJSTranslate()` of the core shifts its arguments (PT09411), the `JS_` twins stay for the JS.

## Entry Points

- `index.php?module=MailManager&view=List` (`view=Index` extends `List`). Without `_operation` it renders `index.tpl`; otherwise `MailManager_List_View::$controllers` dispatches `_operation` (`mainui`, `folder`, `mail`, `relation`, `settings`, `search`) and `_operationarg` selects an exposed method. Unknown operations throw an `Exception`.
- `MailManager_Mail_View` requires write access (POST + CSRF) for `mark`, `move` and `delete`; other operations require read access.
- Frontend: `layouts/d1/modules/MailManager/*.tpl` and `resources/List.js` (`MailManager_List_Js`).

## IMAP and Folders

- `MailManager_Connector_Connector` uses Webklex php-imap (`vendor/webklex/php-imap`). `getFolders()` returns a flat list of every folder, including parents that have children (INBOX, Archives) and nested folders.
- Folder identity is the decoded full path (`Folder::$full_name`, e.g. `Archives/2026`); `MailManager_Folder_Model::getName()` returns it and `getLabel()` displays it. `retrieveBoxFolder()` looks folders up by full path and falls back to the plain name, because older `vtiger_mail_accounts.sent_folder` values and ITS4YouEmails store only the name.
- Mail lists are fetched newest first by server sequence and each page is sorted by mail date (`compareMailsByDateDesc()`); search uses the same order.

## Cache Tables

- `vtiger_mailmanager_mailrecord` and `vtiger_mailmanager_mailattachments` cache opened mails and their attachments. IMAP UIDs are unique only per folder, so every read and write uses `MailManager_Message_Model::getCacheConditions()` (user + UID + folder path when known). Rows without a folder (composer reads by UID only) match by user + UID.
- Attachment files live under the attachment storage path; `getAttachmentFilePath()` is the single rule for reading, downloading and pruning.
- `vtiger_mailmanager_mailrel` is legacy and no longer written.

## Validation

- `php8.3 -l` on touched PHP files (the CLI `php` on the development server is 7.2).
- Manual: folder list shows INBOX and nested folders; paging shows `1 - 20 of N`; open a mail in two folders with the same UID; reply/forward from a cached mail; download an attachment with a non-ASCII name; save settings without changing the password.
- OAuth mailboxes (T10, decision D7): Microsoft 365 / Google are personal mailboxes only. The user wizard step 2 (`Edit.tpl` OAuth variant, `MailboxWizard.js`) opens Core `auth.php` with the user's own OAuth application (`app.getOAuth2Url()` → `Core_Auth_Action`), checks the session tokens (`app.getOAuth2Tokens()`), and `MailManager_ProSaveOAuthAccount_Action` → `MailManager_ProOAuthAccount_Model::saveAccount()` tests the IMAP XOAUTH2 login, stores the tokens in the user's Basic account (`vtiger_mail_accounts`, refused when the user has another address there) and links it as the personal Pro mailbox. Access tokens are refreshed by the Basic account (`retrieveClientAccessToken()`); sending goes through the CRM outgoing server (`smtp_mode = crm`). The admin wizard only explains this; shared OAuth mailboxes are not supported.
- Label colors come only from the Defalto skin palette (`Settings_MailManager_Label_Model::PALETTE`, the `--dt-*` tokens and the secondary gray); `getPaletteColor()` maps any other color to the closest one on save and `MailManager_Install_Model::updateLabelColors()` (part of `installProTables()`) migrates stored labels.
- `ProMimeParser::parseDate()` removes comments such as `(Central European Summer Time)` and the redundant weekday before `strtotime()`, falls back to the topmost `Received` date and only then to the current time; otherwise such mails were sorted as just received.
- Translations: keys read by `app.vtranslate()` must be in `$jsLanguageStrings` of the module the page runs in (`MailManager` or `Settings:MailManager`); keys built dynamically (`LBL_STATE_*`, `LBL_PRIORITY_*`, `LBL_RULE_TYPE_*`, `LBL_AUTOLINK_*`, `LBL_DAY_*`, `LBL_HISTORY_*`, `LBL_AI_BLOCK_*`, `LBL_KIND_*`) are kept in `languages/*/MailManager.php` and `Settings/MailManager.php`.
- Browser notifications (I06, Pro only): `MailManager_Install_Model::$registerProCustomLinks` registers the HEADERSCRIPT `layouts/d1/modules/MailManager/resources/ProNotifier.js` from `installProTables()` (`updateProCustomLinks()`), so Basic-only installations never load it. The script asks `ProCheckNewMail` once a minute for all tabs together (localStorage lock and cursor), stops for the browser session (sessionStorage) when the answer is an error (no Pro, no access) or `enabled: false`. `MailManager_ProNotifier_Model` keeps the per-user switch in `MailManager_ProUserSetting_Model::NOTIFY` and reads `MailManager_ProThreadList_Model::getWorkspaceNewMessages()` (unread inbox mail of the last day, max 3 shown one by one). The switch is the Notifications tab of My settings (`ProSaveMyNotifications`).
- List tabs (I02): `MailManager_ProThreadList_Model::LIST_FILTERS` is the one list of tabs (the view validates against it, `Pro/Index.tpl` renders it, labels `LBL_TAB_<FILTER>` in both language files). `unanswered` = newest non-draft mail is received (`MailManager_ProThreadState_Model::lastInSql()`), own state not done and no closed driving record; `unlinked` = no live `df_mailmanager_rel` link (`noLinkSql()`). Both leave out mail nobody answers or files (`MailManager_ProThreadState_Model::notAutomatedSql()`: a cleanup label outside the Workspace — Spam, Newsletter — or a no-reply sender of the newest received mail). The per-user default tab is `MailManager_ProUserSetting_Model::LIST_TAB` (`getDefaultListTab()` / `saveDefaultListTab()`, My settings → Mail list, `ProSaveMyListTab`); `ProIndex.js` starts with it from `data-list-tab`.
- Attachment preview (I08): `MailManager_ProAttachment_Model::getPreviewType()` decides by the declared type only (`INLINE_TYPES` images → `image`, `application/pdf` → `pdf`, everything else download only); `ProThread::getThreadMessages()` adds `preview_type` and `is_ready` (the message has a `remote_uid` — mail sent from the CRM gets it with the Sent sync). `MailManager_ProAttachment_View` serves `disposition=inline` (images) and `disposition=preview` (PDF only: real type, inline, no CSP sandbox, nosniff kept); downloads stay `application/octet-stream` with the sandbox. The modal (`ProConversation.js` `openAttachmentPreview()`) shows PDFs in `libraries/jquery/pdfjs/web/viewer.html?file=` (same origin).
- Open/click tracking (I09): `MailManager_ProThread_Model::attachTracking()` adds `tracking` (opens, clicks, last access in the user's time) to outgoing messages with `source = 'crm'` whose `crm_emailid` is a `SENT` ITS4YouEmails record (one query: `its4you_emails.access_count/click_count`, `MAX(its4you_emails_access.access_time)`, stored in server time = UTC). Counting without `related_to` needs ITS4YouEmails X05 (tracker handler); without it only mail with a related record counts.
- EMAIL Maker templates (I10): `MailManager_ProTemplate_Model` lists `EMAILMaker_EMAILMaker_Model::getAvailableTemplatesArray($module, false, $recordId, false, true)` for the conversation's end record (`MailManager_ProEmailFiler_Model::getEndRecord()`, only when the user may see it) and fills one template (`ProFillTemplate`: `EMAILMaker_EMAILContent_Model::getInstanceById()` → `getContent()`; the recipient from `resolveRecipientRecords()`; only a template offered for that record). EMAIL Maker keeps static state — one template per request. Template Documents travel as `document_attachments` and are read by `MailManager_ProOutgoingAttachment_Model::collectDocumentAttachments()` (internal files, DetailView permission, upload limit); drafts do not keep them.
- Drag & drop (I11): `ProThreadList.js` `registerThreadDrag()` makes list rows jQuery UI draggables on the first hover (rows are re-rendered by every list load) and the sidebar folders / labels droppables on the first drag. A ticked row carries the selection. Folder → `undoableThreadAction(ids, 'folder', folderId)` (open mailbox only, `JS_MOVE_OTHER_MAILBOX`); label → `ProUpdateThread` for one, `bulkUpdateRequest(ids, {op: 'label'})` for more, the row chip from the hidden chip in the sidebar item. Dropping on a CRM record is a later step.
- Per-user settings: `MailManager_ProUserSetting_Model` is the one store of a user's own settings (rows `user.<id>.<setting>` in `df_mailmanager_config`; constants NOTIFY, LIST_TAB, SEND_DELAY; `SEND_DELAYS` = 0/5/10/20 s).
- Undo Send (I12): client side only — `ProComposer.js` `delayComposerSend()` hides the composer for the user's `SEND_DELAY` (`data-send-delay`), Undo shows it again; `pagehide` posts at once with `fetch(keepalive)`. Mail with uploaded files, a body over 60 KB (keepalive limit 64 KB) and scheduled mail are never delayed. A new composer first sends the waiting mail and opens only when it went out; a failed one brings its own composer back (the post is tied to its overlay).
- Send later (I12): `MailManager_ProOutbox_Model::send()` saves the ITS4YouEmails record (`saveEmailRecord()`, SAVED with all attachments) and either sends it (`deliver()`: `deliverEmailRecord()` + Sent copy, cache, flags, draft, state, history, ticket comment) or stores a `df_mailmanager_scheduled` row (UTC `scheduled_at`, `payload` = the deliver context) through `MailManager_ProScheduled_Model::add()`. The cron task `MailManagerProScheduled` (`cron/ProScheduled.php`, 60 s; real precision = how often the system runs `cron.php`) calls `processDue()`: atomic claim (`status` waiting → sending, `claimed_at`), `deliver()` as the scheduling user (`current_user` swapped, mailbox access re-checked), status sent / failed with `error`. A row whose ITS4YouEmails record is already `SENT` (an error after the SMTP send, a run that died) becomes sent and can never be sent, moved or cancelled again; a send claimed over 30 min ago without a sent record is reported failed. Times: `MailManager_ProMailFormat_Model::userInputToUtc()` / `utcToUserInput()` treat the datetime-local value as the user's CRM time zone; in a DST gap PHP moves the time forward an hour, an ambiguous hour takes the later (standard-time) moment. `registerMissingProCron()` (from `installProTables()`) adds the task on existing installations.
- The mailbox wizard (`MailboxWizard.js`) posts every step to Settings actions under `parent=Settings` and to the `Pro*` module actions otherwise; a user's own mailbox is saved by `MailManager_ProSaveMailbox_Action`, which overrides `Settings_MailManager_SaveMailbox_Action::getMailboxInput()` to force `personal` and no members (a `$request->set()` would not reach `getRaw()`). Editing a mailbox is Settings only.
- Scheduled mail without Membership: the cron task runs while `MailManager_ProScheduled_Model::isSendingAllowed()` (module active + Pro schema installed, the same rule as PurgeData) — mail scheduled before the Membership ended (for example a reached user limit) still goes out. The chain `processDue()` → `deliver()` → ITS4YouEmails / mailbox SMTP / Sent copy / history / cache checks no Membership (ITS4YouEmails adds its "Sent via Defalto CRM" footer without one). Scheduling, rescheduling and cancelling stay Pro actions; the sync cron (`MailManagerProSync`: sync, triage, topics, knowledge, digest) still needs Membership.
- AI agents (I13): `df_mailmanager_aiagent` (model `MailManager_ProAiAgent_Model`, table in `getProTableDefinitions()`, migration `schema/migrations/2026/10/20261016170000.php`) holds the agents — name, type (fast / quality / deep), provider, model, effort, extra instructions, input limit. Each task of `MailManager_ProAiAgent_Model::TASKS` has one agent in `df_mailmanager_config` `ai_task_<task>`; usage-log features map to tasks (`getTaskForFeature()`: language → translate, solution → summary). `MailManager_ProAiClient_Model::complete()` runs every call on the agent of its task (`getForFeature()`, an inactive one falls back to the first active agent): the agent's provider with that provider's key, its model, its effort where `supportsEffort()` (Claude `output_config.effort` for the 4.5+/5.x models, OpenAI `reasoning_effort` for reasoning models, Gemini none), its instructions appended AFTER our system prompt, input capped at `max_input_tokens` × 3 characters; `verify` / `agenttest` calls are direct. The usage log stores `agentid`. Keys: one per provider, `ai_api_key_<provider>` encrypted (the single key of before belongs to `ai_provider`); keys are never sent back to the page. `ensureDefaults()` (install, migration and the first visit of the AI settings) creates "Fast" and "Quality" from the former `ai_provider` / `ai_model` and gives each task the agent of its type — idempotent, nothing changes without the admin. Cascade: `ai_triage_cascade` + `ai_triage_fallback` (an agent); the triage JSON carries `confidence`, below 0.6 the fallback agent sorts again (`triage_strong`).
- Model catalog (I13): `MailManager_ProAiCatalog_Model::CATALOG` — per provider and agent type the recommended model first, then alternatives, with a translated description and a price level 1–3 (Claude Haiku / Sonnet / Opus 5.5; OpenAI gpt-6-luna, gpt-5.4-mini/nano / gpt-6-sol, gpt-6.1-sol, gpt-5.5 / gpt-6-astra; Gemini 2.5 flash, flash-lite / pro). Update it with the module version, names checked against the providers' model lists. The agent form shows the catalog models the verified key has on top, all current models (`MailManager_ProAiProvider_Helper::filterCurrent()`: no dated snapshots, old generations per provider `getObsoletePattern()`, special-purpose models) only under "Show all"; a pick outside the catalog of the agent's type gets a badge (`getFit()`). ## Attachment storage

- MailManager upload actions use the shared `decideFilePath()` attachment directory. Saved-message attachment reads and cleanup resolve stored relative or absolute paths through `Core_Storage_Model::getFilePath()`.
- `vtiger_mailmanager_mailattachments.path` follows the same physical storage policy as `vtiger_attachments.path`, while its table and message lifecycle remain owned by MailManager.
- The cache rule of Basic is `MailManager_Message_Model::getAttachmentFilePath()` (folder + `<attachid>_<sanitized name>` through `Core_Storage_Model::getFilePath()`), used for reading, downloading and pruning.
- Mail Manager Pro writes every file through `Core_Attachment_Model` (sent mail attachments `ProOutbox`, Documents from attachments `ProDocumentFiler`, filed e-mails `ProEmailFiler`, `Relate`) and the Basic upload through `decideFilePath()`; it reads Documents through `Core_Storage_Model::getAttachmentFilePath()` (CRM documents attached in the composer `ProOutgoingAttachment::collectDocumentAttachments()`, knowledge files `ProKnowledge`). Mail attachments of Pro are fetched from the IMAP server on demand and never stored as files.

# ProjectMilestone runtime ownership

- ProjectMilestone is a system entity module installed by `ProjectMilestone_Install_Model extends Core_Install_Model`; it has no independent module version. Entity data uses `vtiger_projectmilestone`, `vtiger_projectmilestonecf` and `vtiger_crmentity` through the normal CRM lifecycle.
- The standard module defines status and deadline fields but no stored percentage/progress field. The Project chart projects milestone dates/ranges without a milestone percentage. Do not infer a numeric progress field from the In progress status label or introduce a new field merely to align task/project percentages.
- The `projectid` relation identifies the project. ProjectTask's `milestoneid` relation places tasks beneath a visible, dated milestone in the Project chart. A milestone date is an inclusive deadline. The chart derives a range start from the earliest viewable linked task start; task edits never rewrite the stored deadline.
- ProjectTask form/save validation requires a selected milestone to share the task's project. Both known task dates must be on/before its deadline and within the project's planned bounds; these checks remain ProjectTask-owned and do not modify the milestone.
- ProjectTask validates known task dates against the linked milestone deadline; equality is allowed. ProjectMilestone_Record_Model::save() validates its calendar date and rejects a deadline earlier than ProjectTask_Record_Model::getLatestMilestoneTaskDate(), independently of chart filters/sharing. Missing/zero task dates do not constrain the deadline. It never reschedules tasks.
- `ProjectMilestone_SaveDate_Action` inherits the normal Save action's request/record/CSRF checks, field/status rules and history, checks submitted field editability and returns JSON. Dragging changes only `projectmilestonedate`, blocks repeated moves while pending and restores the previous date on failure. No advisory locks or dependency cascades are used.
- The Project chart owns double-click/Enter editing and uses the existing Vtiger Edit overlay and SaveAjax endpoints with module `ProjectMilestone`. Module permissions, field locks, validation and history remain in standard CRM flows. The Project adapter refreshes chart data after saving without navigating away.
- Validation: check editable/read-only milestone access, normal and chart form saves, date display and task hierarchy after the chart refresh. Live persistence requires an authenticated CRM/database.

- ProjectMilestone_Module_Model::searchRecord() owns project-scoped autocomplete. For a Project parent it uses Core QueryGenerator to restrict module, project and name, limits results to 100 and batch checks DetailView permission. Other search contexts delegate to the parent. Do not use the base parent-search query, which does not filter its entity result by module or parent.

- Range starts are derived presentation values and never persisted. Moving a milestone range or its right edge changes only the stored deadline; its left edge is fixed. Without a valid visible task start it remains a deadline diamond. A legacy start later than the deadline also falls back to the diamond with a warning rather than rendering a reversed range.

- Missing/zero milestone dates fall back to the visible planned project end in the Project chart/print projection only. Dependency storage and permissions remain Project-owned; milestone-to-milestone finish/start links reuse the existing dependency table, require editable date fields and do not reschedule any record.

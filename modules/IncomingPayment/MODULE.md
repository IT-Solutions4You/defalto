# IncomingPayment

- Owner: `IncomingPayment_Install_Model` installs `df_incomingpayment`, `df_incomingpaymentcf`, `df_incomingpayment_integration` and `df_incomingpayment_associated`, registers numbering (`PAYIN`), history, comments, the Settings link and the payment handlers. Statuses are updated by the core cron `PaymentStatus` (`Core_PaymentStatus_Model`); `migrate()` removes the former module cron `IncomingPaymentStatus`. `IncomingPayment::$moduleVersion` controls install and update versioning. The module is an installable extension (not listed in `Install_Utils_Model::$registerModules`).
- The payment logic is shared with the other payment modules and lives in Core (`Core_Payment…`, see the Payments section of `modules/Core/MODULE.md`). This module keeps `IncomingPayment_Config_Helper extends Core_PaymentConfig_Helper` (module, tables, numbering `PAYIN`, labels, Related To order Accounts → Vendors, paid field order `received` → `paid`, Invoice integrated by default), the entity `IncomingPayment extends Core_PaymentEntity_Model` (tables, list fields), `IncomingPayment_Install_Model extends Core_PaymentInstall_Model` (migrations of earlier installations only), its language files and empty subclasses whose names Defalto resolves by module (views, Settings, Module, Record, uitype, handlers and modifier stored in the database). `IncomingPayment_<Name>` below means that subclass; its logic is in the matching `Core_Payment<Name>` class.
- One model per table: `IncomingPayment_Integration_Model` (integration configuration per document module), `IncomingPayment_Setting_Model` (module-wide settings in `df_incomingpayment_setting`, one row per name, cached per request), `IncomingPayment_Associated_Model` (payment to document association with the applied amount), `IncomingPayment_DocumentSync_Model` (payment-side queries and the document recalculation). Each sets `$table` and `$tableId` from the configuration; the SQL is in their Core base classes.
- Final status: `Paid` (`Core_PaymentConfig_Helper::STATUS_PAID`), shared by all payment modules; this module translates it as "Received" (sk "Prijatá"). `migratePaidStatus()` (run from `preInstallTables()` and `migrate()`) renamed the former value `Received` in place: the picklist value (id, order, color, role assignments stay), the payments, the history and the conditions of saved filters and workflows.
- Fields follow the shared payment names (also used by OutgoingPayment and the Payments list): `payment_amount`, `payment_date`, `payment_method`, `transaction_id`, `reference_id`, `reference_no`, `related_to`, `contact_id`, plus `payment_no`, `payment_name`, `payment_status`, `due_date`. `payment_amount` is the core amount with its own currency (uitype 35): the core keeps its hidden fields `payment_amount_currency_id` and `payment_amount_conversion_rate` and the column `payment_amount_base` (`Core_AmountCurrency_Model`, see `modules/Core/MODULE.md`); the read-only field `payment_amount_base` (uitype 72, displaytype 2) shows that column in the base currency. The payment has no record currency field of its own.
- Field renames of earlier installations (`IncomingPayment_Install_Model::LEGACY_FIELD_NAMES`, e.g. `paymentamount`, `currency_id`, `conversion_rate`, `payamount_main`, `relationid`) run in `renameLegacyFields()` at the start of `installTables()`, because `mode=update` does not call `migrate()`, keeps the uitype of existing fields and creates the fields right after `installTables()`; `migrate()` calls it again. It renames the column (`Core_DatabaseTable_Model::renameColumn()`) and the `vtiger_field` row in place, so the field id and everything bound to it stay (profiles, `vtiger_relatedlists.relationfieldid`, `vtiger_fieldmodulerel`), the picklist table `vtiger_paymethod` with its sequence table and `vtiger_picklist` name (skipped when another module uses the picklist), saved filter columns and conditions (`df_incomingpayment:<column>:<field>:` prefix, also in the Payments filters), workflow conditions, picklist dependencies and ModTracker history. `convertAmountField()` sets uitype 35 and hides the former currency and rate fields and removes them from saved filters. Workflow task contents (Update Fields values, e-mail and template variables) and data of extensions (Reporting, PDFMaker, EMAILMaker) are not migrated. Verified on the test instance: field ids, amounts, base amounts, rates and document paid amounts unchanged after the update; a second update run changes nothing.
- Save flow: `IncomingPayment_PaymentSave_Handler` on `vtiger.entity.beforesave` calls `Core_PaymentValues_Helper::validateReferences()`, which enforces the reference limit. The currency (the user's currency when missing) and the rate (kept on an edit unless the currency changed) of the amount are set by the core in `CRMEntity::saveentity()` for every save path, import included. The handler does not copy the organisation or the contact of the reference document (decided 2026-11-03: not a Defalto standard); only `Core_PaymentPrefill_Helper` prefills them when the payment is created from a document. `IncomingPayment::save_module()` calls `IncomingPayment_DocumentSync_Model::handlePaymentSave()`, which writes the read-only derived columns (`payment_status`, `reference_no`, computed by `getReadonlyValues()`) with a direct update, then stores the association and recalculates the previous and the current reference documents. `payment_amount_base` is written by the core before `save_module()` and stored unrounded (displayed rounded).
- `reference_id` (Reference) is a core multi reference field (uitype 34, `Core_Multireference_UIType`, `text` column with ids like `12;15`). `df_incomingpayment_associated` stays the source of the applied amounts; the column serves the form, search and history. `IncomingPayment_Config_Helper::REFERENCE_LIMIT` (1) limits the edit form through `IncomingPayment_Multireference_UIType::getMaximumRecords()` and is enforced in the before-save handler (`validateReferences()` throws `LBL_ONE_DOCUMENT_PER_PAYMENT`, which a full-form save shows as a bare JSON error page, so the form limit matters); import skips that event, so `getDocumentAmounts()` applies the whole amount to the first existing document only. `reference_no` lists the numbers of all referenced documents. `migrate()` converts an older uitype 10 field (`migrateRelationField()`, 0 becomes NULL) and `installTables()` drops the former int index first (`dropLegacyRelationIndex()`), because the column becomes `text`.
- `CRMEntity::insertIntoEntityTable()` writes only fields with `displaytype` 1, 3, 4 and 6 (edit mode: 1, 3, 6). Values set on displaytype 2 fields in a before-save handler are silently dropped (verified on the first live save: status and amounts stayed NULL), which is why the read-only columns are updated in `save_module()`. It runs inside `saveentity()`, so it also covers import (bulk mode, no events) and the workflow Update Fields task (`ModTracker_History_Helper::saveRecord()` calls `saveentity()` without events), and it runs before the after-save handlers, so workflow conditions and the ModTracker delta see the new values. Do not move this logic to an after-save handler.
- Entity data values in the before-save event are in the format the save action received them: amounts are plain numbers (the entity save casts them with `(float)`), dates are in the user format or `Y-m-d`. Use `Core_PaymentCalculation_Helper::parseAmount()` and `Core_PaymentStatus_Helper::normalizeDate()` for both cases.
- Status rules (`Core_PaymentStatus_Helper`): payment date today or earlier → `Paid`; payment date in the future → `Waiting`; no payment date and due date not passed → `Waiting`; due date passed → `Pending`; no dates → `Created`. Only `Paid` payments (`Core_PaymentConfig_Helper::getPaidStatuses()`) count as paid. Date-only fields are compared with the current user's calendar date and are never time-zone converted. The core cron `PaymentStatus` calls `IncomingPayment_DocumentSync_Model::updateOpenStatuses()`, which re-saves every open payment whose status changed with the calendar; it must not enable `$VTIGER_BULK_SAVE_MODE`, because bulk mode skips the before-save events and the module handlers (`CRMEntity::save()`, `VTEventTrigger`). Import needs no special handling, because `save_module()` runs in bulk mode too and the core sets the currency and rate of the amount in `saveentity()`.
- `IncomingPayment_RelatedSave_Handler` is called by the events manager for every module's final after-save (the handler-module mapping is not applied at trigger time), so it returns early for modules that are not inventory modules before loading the integration configuration. `IncomingPayment_Integration_Model::retrieveAll()` caches the rows per request; `saveFromRequest()` and `installDefaults()` clear the cache.
- Underpayment threshold: one plain number for all document modules (`IncomingPayment_Setting_Model::getUnderpaymentThreshold()`, default 0), compared in the document currency without conversion. `Core_PaymentDocument_Helper::isPaid()` gives the paid status when something was received and the balance is at most the threshold; the paid and balance fields keep the real amounts. A document without a received payment is never paid. Saving a changed threshold in Settings recalculates every document with payments (`recalculateAllDocuments()`).
- Document recalculation (`IncomingPayment_DocumentSync_Model::recalculateDocument()`): sums `partial_amount` of received, non-deleted payments applied to the document, converts payments in another currency through the base currency using the rate stored on the payment and the rate stored on the document, then `Core_PaymentDocument_Helper::updateDocument()` writes the paid and balance fields directly and saves the document through its record model only for a status change (history, workflows and the document's own handlers run; `InventoryItem_CopyOnCreate_Model` ignores edit-mode saves). A static guard in `IncomingPayment_DocumentSync_Model` prevents the `IncomingPayment_RelatedSave_Handler` recursion. The balance is `total - paid` without a lower limit, the same formula as `InvoiceHandler`, so an overpaid document shows a negative balance.
- Invoice: `modules/Invoice/InvoiceHandler.php` recomputes `balance = grand_total - received` on invoice saves made from the Invoice module (`$currentModule === 'Invoice'`). `IncomingPayment_RelatedSave_Handler` runs on `aftersave.final`, after it, and writes `received` and `balance` from the payments, so both stay consistent. While the integration is active the configured paid field (`received`) is read-only (`displaytype` 2, written through `Vtiger_Field::getFieldTable()`) and editable again when the integration is deactivated. Persisted amounts are rounded to `Core_PaymentCalculation_Helper::STORED_DECIMALS`, not to the user's decimal setting.
- The summary widget URL carries `relatedModule=IncomingPayment` so `Vtiger_DetailView_Model::getWidgets()` translates the widget title through this module's language file; the core then also renders its own "Add" quick-create action in the widget header. `AddPaymentButton.tpl` (`DETAILVIEWADVANCED`, next to the More menu; `updateIntegrations()` also removes the older `DETAILVIEWBASIC` row, because a module update does not call `deleteCustomLinks()`) opens the quick create form and falls back to the full form when the module is not in the quick create menu; `AddPaymentMoreLink.tpl` (`DETAILVIEW`, the More menu) opens the full form. Both are templates because the core translates link labels through the document module, and extension labels live only in this module's language files. `IncomingPayment_QuickCreateAjax_View` prefills from the `reference_id` in the request, which both the button and the widget action send (`relatedField=reference_id` in the widget URL). Every prefilled field, the contact included, must be in `$blocksQuickCreateFields`, because the quick form submits only its own fields; a module update writes these quick create flags to the existing fields again. After a save the button reloads the page; the widget action refreshes only the widget, so the document header stays stale until a reload.
- Integration configuration is edited on `index.php?module=IncomingPayment&parent=Settings&view=Index` (`Settings_IncomingPayment_Index_View`, `Settings_IncomingPayment_IntegrationSave_Action`). Available modules are all active modules from the InventoryItem registry (`InventoryItem_Utils_Helper::getInventoryItemModules()`, table `df_inventoryitem_modules`), so a module registered with `registerInventoryModule()` appears without any change here. Defaults are derived from the module fields by `Core_PaymentIntegrationFields_Helper::getDefaultConfig()` (first picklist named `*status` or `*stage`, reference field to Accounts or Vendors, `grand_total`, `received` or `paid`, `balance`) and every module starts inactive; `IncomingPayment_Config_Helper::getIntegrationOverrides()` activates Invoice with the Paid and Created statuses. Saving calls `IncomingPayment_Install_Model::updateIntegrations(false)` before the new configuration is stored (so the old paid field becomes editable again) and `updateIntegrations()` after it, which register per active module: related list `Incoming Payments` (`get_dependents_list` on `reference_id`), the reverse related list of the module on the payment (`IncomingPayment::get_associated_documents()`, read from `df_incomingpayment_associated`, no add or select actions), the template links `AddPaymentButton.tpl` and `AddPaymentMoreLink.tpl`, the summary widget `IncomingPayment` (`IncomingPayment_Widget_View::showPayments`), the `IncomingPayment_RelatedSave_Handler` and the module in the reference list of `reference_id`. Missing paid or balance fields of a document module are created by `IncomingPayment_Integration_Model::createAmountFields()` in the first block outside `LBL_ITEM_DETAILS`, because that block renders only the document items. They stay on the document module when the integration is switched off.
- `updateIntegrations()` temporarily replaces the install model's `register*` arrays and restores them, so the module's own related lists and handlers stay registered. The own related lists include `Incoming Payments` on Accounts and Vendors (`get_dependents_list` on `related_to`) and on Contacts (on `contact_id`); they do not depend on the integration.
- `postInstall()` calls `updateSummaryWidgets()` once more after `Core_Install_Model::postInstall()` cleared the module cache. Observed on the first install: only the Invoice widget existed and the module's own key fields, documents and comments widgets were missing, because the default widgets depend on module state cached earlier in the same request. The call upserts by label, so it is harmless on updates.
- The payment has no VAT or category fields: `migrate()` deletes the older `vat_amount`, `total_without_vat` and `category` fields; deleting the picklist `category` also drops its `vtiger_category` table through the core `FieldEventHandler`. Restoring a payment recomputes its read-only values (`IncomingPayment_PaymentDelete_Handler`). Deleting an integrated document: `CRMEntity::unlinkDependencies()` removes it from `reference_id` (`Core_Relation_Model::deleteMultiReferenceDependencies()`), then `IncomingPayment_RelatedDelete_Handler` (`vtiger.entity.afterdelete`, registered per active integration) calls `IncomingPayment_DocumentSync_Model::handleDocumentDelete()`, which deletes the association rows of the document and refreshes `reference_no` of its payments. Before the delete, `IncomingPayment_DeleteWarnings_Modifier` (registered per active integration by `updateDeleteWarnings()` as the `DeleteWarningsAction` modifier) adds the linked payment count to the core delete confirmation (`Core_DeleteWarnings_Action`, see `modules/Core/MODULE.md`). Restoring the document links nothing back (decided); the same handler (`vtiger.entity.afterrestore`) only recalculates the restored document, so its paid amount, balance and status no longer show the removed payments. A changed event list of this handler takes effect after the integration is saved again in Settings or the module is updated. The payment form rejects negative amounts, so a refund cannot be entered by hand.
- `IncomingPayment_Edit_View` prefills a payment created from a document (`sourceModule`, `sourceRecord`): open amount (total minus paid), currency, due date, organisation and contact (`Core_PaymentPrefill_Helper`). The helper checks that the record belongs to the module and that the user may view it. Amounts are set on the request as plain decimals (unit price fields are cast with `(float)`), dates in the user format; `Vtiger_Edit_View` converts them with `getDBInsertValue()`. Configured field names are validated against `^[a-z][a-z0-9_]*$` before they are stored or used to create columns.
- Validation: `php -l` on changed PHP files, `check_change.py` from the defalto-coding skill, dev install `index.php?module=IncomingPayment&view=Install&mode=install` (later `mode=update`), then: create a payment from an invoice, check `received`, `balance` and the status of the invoice, delete and restore the payment, run the core cron `PaymentStatus`, and change the integration in Settings.
- Component names resolved by `Vtiger_Loader` are reserved: `<Module>_Relation_Model` is instantiated by `Vtiger_Relation_Model::getAllRelations()` for every related list, so `modules/IncomingPayment/models/Relation.php` must stay a plain subclass of `Vtiger_Relation_Model`. Module logic uses non-core names (`DocumentSync`, `Integration`, `Associated`). Verified on the first live detail view (fatal `Call to undefined method IncomingPayment_Relation_Model::setParentModuleModel()` while the module logic still used that name).
- The module is an installable extension, so `addCustomLinks()` calls `updateToCustomModule()` (keeps `vtiger_tab.source = 'custom'`, `customized = 1`) instead of Core's `updateToStandardModule()`: `Installer_IndexAjax_View::extensionUninstall()` refuses modules whose source is not `custom`. `deleteModule()` is overridden to run `updateSummaryWidgets(false)` and `deleteCustomLinks()` first: the pre-uninstall event fires only inside `parent::deleteModule()`, after the field rows are gone, and `Vtiger_Field::deleteForModule()` does not clean `vtiger_fieldmodulerel`. `deleteCustomLinks()` therefore runs twice on this path and must stay idempotent.
- Updating an installed module does not rewrite `uitype`, `typeofdata` or labels of existing fields, keeps their `block`, `sequence` and `masseditable` (`Core_Install_Model::$fieldKeySkippedForUpdate`) and adds picklist values only with `picklist_overwrite`; such changes need migration code that also runs on `mode=update` (see `renameLegacyFields()`). `mode=update` does not call `migrate()`; it runs through `mode=migrate` and the system migration. `deleteField()` also drops the column through the core `FieldEventHandler`, so a following `dropColumn()` fails (verified live).
- The document's paid and balance fields (Invoice `received`, `balance`) are displaytype 2 while the integration is active, so `Core_PaymentDocument_Helper::updateDocument()` writes them through `IncomingPayment_DocumentSync_Model::updateRecordColumns()` (direct UPDATE on the field's table, mirrored on the record model) and saves the record only for the status change. Verified live: a record save with `received`/`balance` set left both columns at 0 while the status changed to Paid.
- Currency symbols from `vtiger_currency_info` are HTML entities (`&euro;`); `Core_PaymentCalculation_Helper::formatAmount()` decodes them because templates escape the output again. `PearDatabase::fetchByAssoc()` HTML-encodes by default, so rows that are compared with record values or escaped in templates are fetched with `fetchByAssoc($result, -1, false)`.
- `IncomingPayment_Record_Model::getCurrencyId()` returns the currency of `payment_amount` (raw list column or hidden field value, base currency when missing), and `getFieldCurrencyId()` shows `payment_amount_base` (`FIELD_AMOUNT_BASE`) in the base currency. The payment table has no `currency_id` column, so the core fallback `fetchCurrencyId()` would return 1.
- Known limit: after an inline edit of a payment date the core updates only the edited field in the page, so the status in the detail header stays stale until a reload.
- Header link: `IncomingPayment_Module_Model::getCustomViewUrl()` (used only by the module title in `layouts/d1/modules/Core/partials/Topbar.tpl`) returns the Payments list URL while the Payments module is active and permitted, so the title on a payment detail leads back to Payments with its last filter, page and sorting. `IncomingPayment_Detail_View` and `IncomingPayment_Edit_View` assign `MODULE_BREADCRUMB_LABEL` from `getBreadcrumbLabel()`, so the title reads "Payments". Without Payments both keep the module's own list and name.

# IncomingPayment

- Owner: `IncomingPayment_Install_Model` installs `df_incomingpayment`, `df_incomingpaymentcf`, `df_incomingpayment_integration` and `df_incomingpayment_associated`, registers numbering (`PAYIN`), history, comments, the Settings link, the daily cron `IncomingPaymentStatus` and the payment handlers. `IncomingPayment::$moduleVersion` controls install and update versioning. The module is an installable extension (not listed in `Install_Utils_Model::$registerModules`).
- Shared identifiers (module, tables, field names, statuses, event names, integration defaults) live only in `IncomingPayment_Config_Helper`. The code is written so that the shared parts (`Calculation`, `Status`, `Document`, `DocumentSync`, `Integration`, `Associated`) can later move into a common `Payments` module used by an `OutgoingPayment` module.
- One model per table: `IncomingPayment_Integration_Model` (integration configuration per document module), `IncomingPayment_Associated_Model` (payment to document association with the applied amount), `IncomingPayment_DocumentSync_Model` (payment-side queries and the document recalculation). All SQL lives in these models.
- Save flow: `IncomingPayment_PaymentSave_Handler` on `vtiger.entity.beforesave` calls `IncomingPayment_PaymentValues_Helper::setEditableValues()`, which sets the currency fallback, the rate (only for a new payment, a changed currency or a missing rate; an edit keeps the stored rate) and the missing organisation or contact into the entity data. `IncomingPayment::save_module()` calls `IncomingPayment_DocumentSync_Model::handlePaymentSave()`, which writes the read-only derived columns (`conversion_rate`, `payment_status`, `payamount_main`, `associated_no`, computed by `getReadonlyValues()`) with a direct update, then stores the association and recalculates the previous and the current reference documents.
- `relationid` (Reference) is a core multi reference field (uitype 34, `Core_Multireference_UIType`, `text` column with ids like `12;15`). `df_incomingpayment_associated` stays the source of the applied amounts; the column serves the form, search and history. `IncomingPayment_Config_Helper::REFERENCE_LIMIT` (1) limits the edit form through `IncomingPayment_Multireference_UIType::getMaximumRecords()` and is enforced in the before-save handler (`setEditableValues()` throws `LBL_ONE_DOCUMENT_PER_PAYMENT`, which a full-form save shows as a bare JSON error page, so the form limit matters); import skips that event, so `getDocumentAmounts()` applies the whole amount to the first existing document only. `associated_no` lists the numbers of all referenced documents. `migrate()` converts an older uitype 10 field (`migrateRelationField()`, 0 becomes NULL) and `installTables()` drops the former int index first (`dropLegacyRelationIndex()`), because the column becomes `text`.
- `CRMEntity::insertIntoEntityTable()` writes only fields with `displaytype` 1, 3, 4 and 6 (edit mode: 1, 3, 6). Values set on displaytype 2 fields in a before-save handler are silently dropped (verified on the first live save: status and amounts stayed NULL), which is why the read-only columns are updated in `save_module()`. It runs inside `saveentity()`, so it also covers import (bulk mode, no events) and the workflow Update Fields task (`ModTracker_History_Helper::saveRecord()` calls `saveentity()` without events), and it runs before the after-save handlers, so workflow conditions and the ModTracker delta see the new values. Do not move this logic to an after-save handler.
- Entity data values in the before-save event are in the format the save action received them: amounts are plain numbers (the entity save casts them with `(float)`), dates are in the user format or `Y-m-d`. Use `IncomingPayment_Calculation_Helper::parseAmount()` and `IncomingPayment_Status_Helper::normalizeDate()` for both cases.
- Status rules (`IncomingPayment_Status_Helper`): payment date today or earlier → `Received`; payment date in the future → `Waiting`; no payment date and due date not passed → `Waiting`; due date passed → `Pending`; no dates → `Created`. Only `Received` payments (`IncomingPayment_Config_Helper::getPaidStatuses()`) count as paid. Date-only fields are compared with the current user's calendar date and are never time-zone converted. The cron `modules/IncomingPayment/cron/Status.php` re-saves every open payment whose status changed with the calendar; it must not enable `$VTIGER_BULK_SAVE_MODE`, because bulk mode skips the before-save events and the module handlers (`CRMEntity::save()`, `VTEventTrigger`). Import needs no special handling, because `save_module()` runs in bulk mode too; it takes the current rate there (`$refreshRate`), because the before-save event does not fire.
- `IncomingPayment_RelatedSave_Handler` is called by the events manager for every module's final after-save (the handler-module mapping is not applied at trigger time), so it returns early for modules that are not inventory modules before loading the integration configuration. `IncomingPayment_Integration_Model::retrieveAll()` caches the rows per request; `saveFromRequest()` and `installDefaults()` clear the cache.
- Document recalculation (`IncomingPayment_DocumentSync_Model::recalculateDocument()`): sums `partial_amount` of received, non-deleted payments applied to the document, converts payments in another currency through the base currency using the rate stored on the payment and the rate stored on the document, then `IncomingPayment_Document_Helper::updateDocument()` writes the paid and balance fields directly and saves the document through its record model only for a status change (history, workflows and the document's own handlers run; `InventoryItem_CopyOnCreate_Model` ignores edit-mode saves). A static guard in `IncomingPayment_DocumentSync_Model` prevents the `IncomingPayment_RelatedSave_Handler` recursion. The balance is `total - paid` without a lower limit, the same formula as `InvoiceHandler`, so an overpaid document shows a negative balance.
- Invoice: `modules/Invoice/InvoiceHandler.php` recomputes `balance = grand_total - received` on invoice saves made from the Invoice module (`$currentModule === 'Invoice'`). `IncomingPayment_RelatedSave_Handler` runs on `aftersave.final`, after it, and writes `received` and `balance` from the payments, so both stay consistent. While the integration is active the configured paid field (`received`) is read-only (`displaytype` 2, written through `Vtiger_Field::getFieldTable()`) and editable again when the integration is deactivated. Persisted amounts are rounded to `IncomingPayment_Calculation_Helper::STORED_DECIMALS`, not to the user's decimal setting.
- The summary widget URL carries `relatedModule=IncomingPayment` so `Vtiger_DetailView_Model::getWidgets()` translates the widget title through this module's language file; the core then also renders its own "Add" quick-create action in the widget header. `AddPaymentButton.tpl` (`DETAILVIEWADVANCED`, next to the More menu; `updateIntegrations()` also removes the older `DETAILVIEWBASIC` row, because a module update does not call `deleteCustomLinks()`) opens the quick create form and falls back to the full form when the module is not in the quick create menu; `AddPaymentMoreLink.tpl` (`DETAILVIEW`, the More menu) opens the full form. Both are templates because the core translates link labels through the document module, and extension labels live only in this module's language files. `IncomingPayment_QuickCreateAjax_View` prefills from the `relationid` in the request, which both the button and the widget action send (`relatedField=relationid` in the widget URL). After a save the button reloads the page; the widget action refreshes only the widget, so the document header stays stale until a reload.
- Integration configuration is edited on `index.php?module=IncomingPayment&parent=Settings&view=Index` (`Settings_IncomingPayment_Index_View`, `Settings_IncomingPayment_IntegrationSave_Action`). Available modules are all active modules from the InventoryItem registry (`InventoryItem_Utils_Helper::getInventoryItemModules()`, table `df_inventoryitem_modules`), so a module registered with `registerInventoryModule()` appears without any change here. Defaults are derived from the module fields by `IncomingPayment_IntegrationFields_Helper::getDefaultConfig()` (first picklist named `*status` or `*stage`, reference field to Accounts or Vendors, `grand_total`, `received` or `paid`, `balance`) and every module starts inactive; `IncomingPayment_Config_Helper::getIntegrationOverrides()` activates Invoice with the Paid and Created statuses. Saving calls `IncomingPayment_Install_Model::updateIntegrations(false)` before the new configuration is stored (so the old paid field becomes editable again) and `updateIntegrations()` after it, which register per active module: related list `Incoming Payments` (`get_dependents_list` on `relationid`), the reverse related list of the module on the payment (`IncomingPayment::get_associated_documents()`, read from `df_incomingpayment_associated`, no add or select actions), the template links `AddPaymentButton.tpl` and `AddPaymentMoreLink.tpl`, the summary widget `IncomingPayment` (`IncomingPayment_Widget_View::showPayments`), the `IncomingPayment_RelatedSave_Handler` and the module in the reference list of `relationid`. Missing paid or balance fields of a document module are created by `IncomingPayment_Integration_Model::createAmountFields()` in the first block outside `LBL_ITEM_DETAILS`, because that block renders only the document items. They stay on the document module when the integration is switched off.
- `updateIntegrations()` temporarily replaces the install model's `register*` arrays and restores them, so the module's own related lists and handlers stay registered.
- `postInstall()` calls `updateSummaryWidgets()` once more after `Core_Install_Model::postInstall()` cleared the module cache. Observed on the first install: only the Invoice widget existed and the module's own key fields, documents and comments widgets were missing, because the default widgets depend on module state cached earlier in the same request. The call upserts by label, so it is harmless on updates.
- The payment has no VAT or category fields: `migrate()` deletes the older `vat_amount`, `total_without_vat` and `category` fields; deleting the picklist `category` also drops its `vtiger_category` table through the core `FieldEventHandler`. Restoring a payment recomputes its read-only values (`IncomingPayment_PaymentDelete_Handler`). Known limit: `CRMEntity::unlinkDependencies()` removes a deleted document from `relationid` (`Core_Relation_Model::deleteMultiReferenceDependencies()`) and does not put it back on restore; the association row stays until the payment is saved again. The payment form rejects negative amounts, so a refund cannot be entered by hand.
- `IncomingPayment_Edit_View` prefills a payment created from a document (`sourceModule`, `sourceRecord`): open amount (total minus paid), currency, due date, organisation and contact (`IncomingPayment_Prefill_Helper`). The helper checks that the record belongs to the module and that the user may view it. Amounts are set on the request as plain decimals (unit price fields are cast with `(float)`), dates in the user format; `Vtiger_Edit_View` converts them with `getDBInsertValue()`. Configured field names are validated against `^[a-z][a-z0-9_]*$` before they are stored or used to create columns.
- Validation: `php -l` on changed PHP files, `check_change.py` from the defalto-coding skill, dev install `index.php?module=IncomingPayment&view=Install&mode=install` (later `mode=update`), then: create a payment from an invoice, check `received`, `balance` and the status of the invoice, delete and restore the payment, run the cron `IncomingPaymentStatus`, and change the integration in Settings.
- Component names resolved by `Vtiger_Loader` are reserved: `<Module>_Relation_Model` is instantiated by `Vtiger_Relation_Model::getAllRelations()` for every related list, so `modules/IncomingPayment/models/Relation.php` must stay a plain subclass of `Vtiger_Relation_Model`. Module logic uses non-core names (`DocumentSync`, `Integration`, `Associated`). Verified on the first live detail view (fatal `Call to undefined method IncomingPayment_Relation_Model::setParentModuleModel()` while the module logic still used that name).
- The module is an installable extension, so `addCustomLinks()` calls `updateToCustomModule()` (keeps `vtiger_tab.source = 'custom'`, `customized = 1`) instead of Core's `updateToStandardModule()`: `Installer_IndexAjax_View::extensionUninstall()` refuses modules whose source is not `custom`. `deleteModule()` is overridden to run `updateSummaryWidgets(false)` and `deleteCustomLinks()` first: the pre-uninstall event fires only inside `parent::deleteModule()`, after the field rows are gone, and `Vtiger_Field::deleteForModule()` does not clean `vtiger_fieldmodulerel`. `deleteCustomLinks()` therefore runs twice on this path and must stay idempotent.
- Updating an installed module does not rewrite `uitype`, `typeofdata` or labels of existing fields, keeps their `block`, `sequence` and `masseditable` (`Core_Install_Model::$fieldKeySkippedForUpdate`) and adds picklist values only with `picklist_overwrite`; such changes need `migrate()` code. `mode=update` does not call `migrate()`; it runs through `mode=migrate` and the system migration. `deleteField()` also drops the column through the core `FieldEventHandler`, so a following `dropColumn()` fails (verified live).
- The document's paid and balance fields (Invoice `received`, `balance`) are displaytype 2 while the integration is active, so `IncomingPayment_Document_Helper::updateDocument()` writes them through `IncomingPayment_DocumentSync_Model::updateRecordColumns()` (direct UPDATE on the field's table, mirrored on the record model) and saves the record only for the status change. Verified live: a record save with `received`/`balance` set left both columns at 0 while the status changed to Paid.
- Currency symbols from `vtiger_currency_info` are HTML entities (`&euro;`); `IncomingPayment_Calculation_Helper::formatAmount()` decodes them because templates escape the output again. `PearDatabase::fetchByAssoc()` HTML-encodes by default, so rows that are compared with record values or escaped in templates are fetched with `fetchByAssoc($result, -1, false)`.
- Known limit: after an inline edit of a payment date the core updates only the edited field in the page, so the status in the detail header stays stale until a reload.
